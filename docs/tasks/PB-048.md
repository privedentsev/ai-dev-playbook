## Задача

### Цель и границы

Перевести update на выборочную подготовку кандидатного комплекта и будущего документного состояния. Явно изменить контракт продуктовых проверок и обеспечить переход со старой установки. Не выполнять автоматический verify продукта внутри транзакции.

### Контекст

[Спецификация](../specs/scoped-file-operations.md): R-05–07,14–16; AC-04–05,09. [Design](../designs/scoped-file-operations.md), [ADR-0005](../adr/0005-scoped-file-operations.md), [план](../plans/scoped-file-operations.md).

Область файлов: updating.py, миграции/updates.json, manifest/install/init/adopt при необходимости, правила update/verification, тестовые локальные релизы и совместимость restore.

Подготовлено Codex / GPT-6 Astra по поручению инженера 2026-10-26. Выполнение не разрешено. Перед стартом нужны отдельное поручение, актуальное состояние зависимостей и назначение исполнителя. Никаких обязательств по пилоту на реальном большом проекте.

### Критерии приёмки

- [ ] AC-01: Новый update не копирует корень проекта; готовит кандидатный комплект и новые управляемые файлы, использует FutureView для мигрированных настроек/документов. Отсутствующая зависимость кандидата отклоняется до записи без полного copytree fallback.
- [ ] AC-02: Preview явно показывает миграцию storage: missing → 15, валидное значение сохраняется, invalid отклоняется. Новые init/self-project и переход через старый CLI проверены; восстановление не требует уже мигрированной конфигурации.
- [ ] AC-03: Контракт update явно отделяет структурную совместимость от продуктового verify. Настроенные shell/verification-команды не запускаются скрыто на основном проекте, отсутствие их результата не выдаётся за passed; preview/итог дают отдельный шаг verify.
- [ ] AC-04: Поздний backup, final checks, pending, потоковая запись и автономный restore сохраняют прежние гарантии; SIGKILL/ошибка миграции/повреждённый релиз не оставляют ложный success.
- [ ] AC-05: Старые backup и pending восстанавливаются; старые сохранённые планы требуют пересоздания. Поведение legacy updater на переходном релизе документировано и проверено локальным fixture, без обещания изменения старого кода.
- [ ] AC-06: План/receipt нового update совместимы с единым retention-контрактом; целевые сценарии, verify и передача не требуют внешнего проекта.

### План

1. Зафиксировать изменение update-контракта и ограниченную среду запуска кандидатного CLI.
2. Перевести подготовку, миграции и recovery; подключить регистрацию планов и терминальные состояния.
3. Проверить локальный переход legacy → candidate, новый init, keep-конфликты и отказ продуктовой команды как отдельный verify-сценарий.
4. Перед финальным verify зарегистрировать материалы, подготовить in_review и индекс; после изменения файлов комплекта актуализировать self-manifest.
5. Выполнить целевые проверки и `python3 ai-dev-playbook/scripts/playbook.py verify PB-048`. Записать EXEC/CHECK/HANDOFF с командами, результатами и ограничениями; зарегистрировать handoff. Независимая приёмка проводится отдельно.

### Ресурсы

Python 3.10+ и стандартная библиотека; локальные временные проекты. Точная среда и policy_revision фиксируются при старте, бюджет не задан. Исполнитель пока не назначен.

Проверки: Локально собранные/зафиксированные артефакты, temporary installations, spy-команда с записью sentinel для доказательства отсутствия скрытого запуска, SIGKILL и прежние restore fixtures.

Материалы: `docs/tasks/PB-048-evidence/` и зарегистрированные отчёты verify; сейчас материалы реализации не создаются. `index --all`, `check --ready`, `git diff --check` проверяют структуру отдельно от поведения.
