## Цель и границы

Подключить политику к verify: read-only preflight, реальные command-прогоны, ручные результаты, candidate snapshot и reuse. Новые handoff/close остаются в PB-034.

## Область изменений

verification.py, playbook.py (verify), доверенный реестр и отчёты v2. Preflight проверяет готовность перед дорогими subprocess; не требует будущих отчётов.

## Условия готовности

План/границы согласованы инженером; зависимости завершены; поля/интерфейсы соответствующего этапа однозначны. Исполнитель назначается только при старте. Изменение требований/архитектуры возвращается к соответствующему этапу, не решается скрытым расширением задачи.

## План

1. Подключить read-only готовность и объяснение плана.
2. Реализовать command и manual pipelines с immutable-отчётами.
3. Добавить reuse, прогнать subprocess-матрицу и legacy-регрессию.

## Приёмка

- [ ] verify --preflight не пишет/не запускает команды и показывает ID, обязательность, актуальность, ошибки и способы исправления.
- [ ] Обычный verify до снимка согласованно исправляет разрешённый производный индекс или отказывает с понятной причиной; план не правится молча.
- [ ] Исполняется только разрешённый argv из реестра, сохраняются реальные returncode/timeout и before/after. Изменение входов во время прогона выявлено.
- [ ] Ручной сценарий связан с предъявленным snapshot; правка после предъявления требует нового просмотра. Нет браузера/подтверждения — not_run, а не passed.
- [ ] Свежие независимые результаты переиспользуются без повторного процесса, failed остаётся историей. v1 verify работает по старому контракту.
- [ ] Самопроверка и handoff зарегистрированы, независимая приёмка выполнена в отдельной сессии либо инженером перед закрытием.

## Проверки и доказательства

Subprocess-счётчики запусков; stale during run, timeout, отказ неизвестной команды; manual candidate до/после изменения; preflight input hashes. Предлагаемые tests/test_verification_v2.py и tests/test_verification_preflight.py.

Команды основы: целевые `python3 -m unittest discover -s tests -p '<согласованный файл тестов>' -v`, затем настроенный `python3 ai-dev-playbook/scripts/playbook.py verify PB-033` по действующему на этапе контракту. Перед запуском проверить argv/inputs и готовность служебных данных. Проверить `index --all`, `check --ready`, `git diff --check`; после изменения файлов комплекта выполнить `adopt . --force --apply` до финального прогона. Существующий timeout не обходить скрытым изменением runner: заранее согласовать настройку при необходимости.

Материалы: `docs/tasks/PB-033-evidence/` и зарегистрированные verify-прогоны. Неизменяемые отчёты не переписывать. Структурные проверки не являются доказательством поведения CLI.

## Ресурсы

## Уточнение после PB-051–053

[PB-054](../archive/tasks/PB-054.md) добавляет базовый preflight переносимости материалов и явный reuse полного legacy-отчёта. Здесь остаются v2-применимость, coverage, ручные результаты и независимые наборы входов. Использовать общие проверки PB-054; не вводить второй несовместимый валидатор. До subprocess выявлять неучтённые материалы, не переносимые ссылки, ошибки статуса/индекса; не требовать будущие отчёты. Причина каждого повторного запуска должна показывать изменившиеся значимые входы/команду/политику/среду. CHANGELOG и другие результаты задачи не исключать из снимка ради экономии.

Дополнительная приёмка: неизменный полный legacy-отчёт и выборочный v2-result различаются; новое обязательное правило, неизвестная зависимость и failed не обходятся reuse. Проверка, читающая документы/evidence, сохраняет эти зависимости.
