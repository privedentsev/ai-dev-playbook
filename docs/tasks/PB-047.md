## Задача

### Цель и границы

Ввести обязательную настройку хранения и явную идентичность/действительность сохранённых планов. Подготовить безопасный revoke для будущего GC. Само удаление истории в этой задаче не включать.

### Контекст

[Спецификация](../specs/scoped-file-operations.md): R-09,13–14; AC-05,07–08. [Design](../designs/scoped-file-operations.md), [ADR-0005](../adr/0005-scoped-file-operations.md), [план](../plans/scoped-file-operations.md).

Область файлов: Валидатор project.json, шаблон и self-config, CLI storage configure, реестр планов, lifecycle plan/save/apply и схема квитанций; тесты.

Подготовлено Codex / GPT-6 Astra по поручению инженера 2026-10-26. Выполнение не разрешено. Перед стартом нужны отдельное поручение, актуальное состояние зависимостей и назначение исполнителя. Никаких обязательств по пилоту на реальном большом проекте.

### Критерии приёмки

- [ ] AC-01: storage.backup_retention_count — обязательный int >=1 без bool/default; отсутствующее/некорректное значение даёт понятный отказ обычных write-команд до побочных записей. В шаблон и self-project внесено явное 15.
- [ ] AC-02: Явный bootstrap storage configure с preview/apply позволяет добавить/исправить настройку восстанавливаемо; status/restore доступны при missing/invalid. Прерывание bootstrap не блокирует восстановление.
- [ ] AC-03: Уникальный ID выдачи отделён от digest плана. Preview read-only, save регистрирует ID/digest под gate; внешняя копия с неизвестным/отозванным ID, подмена JSON и потеря/повреждение реестра отклоняются без автоматической регистрации.
- [ ] AC-04: Повтор completed сверяет реальное состояние; drift не выдаёт ложный already_completed. Fresh-запрос при корректном итоговом состоянии даёт no-op; повтор целевого состояния после отката требует новой операции и не воспроизводит PB-042.
- [ ] AC-05: Revoke/expire повторяемы и устойчивы к прерыванию; после отзыва ни сохранившийся receipt, ни внешняя копия плана не разрешают apply. История выданных IDs не требует бессрочных tombstones.
- [ ] AC-06: Legacy-планы не импортируются молча; их пересоздание объяснено пользователю. Проверены подмена, rollback, stale plan, смена конфигурации и конкурентные действия; verify/передача готовы.

### План

1. Определить версии конфигурации/реестра и добавить строгую валидацию с узким bootstrap.
2. Ввести выдачу, регистрацию, проверку и отзыв планов для нового протокола; сохранить read-only preview.
3. Закрепить replay/no-op/drift/expire/registry corruption регрессиями и документировать будущий API очистки.
4. Перед финальным verify зарегистрировать материалы, подготовить in_review и индекс; после изменения файлов комплекта актуализировать self-manifest.
5. Выполнить целевые проверки и `python3 ai-dev-playbook/scripts/playbook.py verify PB-047`. Записать EXEC/CHECK/HANDOFF с командами, результатами и ограничениями; зарегистрировать handoff. Независимая приёмка проводится отдельно.

### Ресурсы

Python 3.10+ и стандартная библиотека; локальные временные проекты. Точная среда и policy_revision фиксируются при старте, бюджет не задан. Исполнитель пока не назначен.

Проверки: Матрица JSON-настройки и saved-plan replay, включая внешнюю копию JSON, удалённую квитанцию при revoked ID, corrupt registry, fresh повтор index и одновременный apply/expire.
