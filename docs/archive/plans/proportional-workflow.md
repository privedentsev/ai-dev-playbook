## 1. Результат и границы

Внедрить соразмерные маршруты, выбор автоматических/ручных проверок под задачу, согласованную передачу и раздельный учёт свежести, сохранив старые проекты и восстановление операций.

Источники: [спецификация](../../specs/proportional-workflow.md), [design](../../designs/proportional-workflow.md), [ADR-0003](../../adr/0003-task-scoped-verification.md). Автор планирования: Codex / GPT-6.1 Sol.

Инженер разрешил планирование после представления design. План и draft-карточки не разрешают реализацию. Новые правила ещё не действуют; подготовка проверяется текущими index/check, а реализация до подключения новой механики — текущим runner.

Не входят: универсальные профили, новый тип карточек, публикация сайта, внешняя интеграция CI, commit/push/merge/release.

## 3. Проверки, доказательства и приёмка

Каждая подзадача: целевые unit/subprocess-сценарии → настроенный verify по действующему контракту → handoff/in_review → независимый аудит отдельной сессией либо инженер → accept/close. До внедрения новой модели её облегчения нельзя использовать для обхода текущих проверок.

Команды основы: `python3 -m unittest discover -s tests -v`, `python3 ai-dev-playbook/scripts/playbook.py index --all`, `python3 ai-dev-playbook/scripts/playbook.py check --ready`, `python3 ai-dev-playbook/scripts/playbook.py verify <ID>`, `git diff --check`. Конкретные целевые команды — в карточках, имена новых тестовых файлов будущие. Перед дорогим запуском проверить статус/индекс/материалы, чтобы не повторять ошибку PB-030. Если штатный лимит недостаточен, согласованно настроить его до прогона с фиксацией; не менять входы после проверки.

| Критерии спецификации | Основной владелец | Подтверждение |
|---|---|---|
| AC-01–03 | PB-031, PB-035 | Обычная карточка, выбор/повышение маршрута, итерации |
| AC-04–06 | PB-032, PB-033 | Применимость, coverage, ручной путь, отрицательные результаты |
| AC-07,10 | PB-033, PB-034 | Preflight, единая передача, явная приёмка |
| AC-08–09 | PB-032–PB-034 | Смена значимых/служебных входов, независимый reuse |
| AC-11 | PB-034, PB-036 | SIGKILL, восстановление, конкуренция, immutable |
| AC-12 | PB-031, PB-036 | Старые/новые схемы, update и legacy-команды |
| AC-13 | PB-032, PB-036 | Регрессия отделена от локального close, без ложной блокировки внешних систем |
| AC-14 | PB-035, PB-037 | Старые маршруты, аудит блока, руководство и Git-ограничения |

PB-037 повторяет полный набор AC-01–14 на изолированных проектах. AUDIT-007 независимо воспроизводит существенные сценарии и негативные случаи; зелёные тесты не заменяют проверку достаточности.

Критерий эффективности: локальная визуальная задача проходит без несвязанных проверок после явной настройки проекта; служебные переходы не вызывают повторного теста реализации. Считать число запусков и команд переходов, не обещать универсальный бюджет токенов/секунд.

## 4. Сопровождающие материалы

Материалы подзадач — `docs/tasks/<ID>-evidence/` и зарегистрированные verify-прогоны; архивируются с соответствующей карточкой. Создавать каталоги только при появлении доказательств.

Общие спецификация, design, план, материалы общей матрицы и итоговой приёмки закреплены за AUDIT-007. Общие материалы не переносятся при закрытии отдельной подзадачи; owner/used_by регистрируются до появления ссылок. Принятый ADR остаётся актуальным документом.

Immutable-отчёты сохраняются побайтно. После переноса проверить ссылки, move-map и relocation hashes. Отчёт с историческим входом не переписывается ради новой актуальности.

## 5. Риски, миграция и восстановление

Риски: неполный scope/паттерны, неверная ручная привязка, обход обязательной проверки, ослабление race/recovery-защит, повторные прогоны из-за некорректной проекции. Для каждого предусмотрены негативные сценарии.

Все эксперименты прерывания/update — во временных копиях, без секретов и записи в чужие проекты. Порядок gate → специализированный lock сохраняется. При неуспехе выполняется штатный restore, а не ручное удаление pending.

Legacy-путь сохраняется. Новая схема включается явно после проверки совместимости; старые обязательные команды переносятся как always. Ослабление/сужение обязательности — отдельное инженерское решение. Поддерживаемые версии и migrate/downgrade отказы фиксируются в PB-036 до ready; публикация релиза не входит.

При изменении файлов комплекта актуализировать self-manifest: `python3 ai-dev-playbook/scripts/playbook.py adopt . --force --apply`. Планирование сейчас не меняет комплект и не требует adopt.

## 6. Критерии завершения и архивирования плана

Все PB-031–PB-037 приняты и закрыты штатным CLI; все AC независимо подтверждены в AUDIT-007; нет блокирующих замечаний; руководство/правила/архитектура соответствуют итоговому поведению; update/restore и legacy проверены.

После явной приёмки инженера/аудитора зарегистрировать принятие изменения спецификации через штатный promote_change с протоколом нужной ревизии, обновить действующий контракт, закрыть AUDIT-007 и архивировать план/общие материалы по проверенному lifecycle-плану. Не архивировать действующие спецификации, design и ADR автоматически только потому, что блок завершён. После переноса — check --ready, ссылки/relocation, git diff --check. Никакого автоматического commit/push/release.

PB-031–PB-037 завершены. Повторный аудит AUDIT-007 подтвердил матрицу; архивирование плана выполняется совместно с приёмкой требований и закрытием AUDIT-007.
