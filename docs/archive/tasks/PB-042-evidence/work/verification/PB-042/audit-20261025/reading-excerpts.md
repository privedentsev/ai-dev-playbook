44: - При переходе к спецификации выводы переносятся непосредственно в требования; для маленькой задачи — сразу в карточку. Отдельная заметка обсуждения в этом случае не обязательна.
45: 
46: ### 2. Спецификация (`spec`)
47: - Цель: зафиксировать проверяемые требования, пользовательские сценарии, граничные случаи и критерии приёмки.
48: - Создаётся через `playbook.py document create spec <тема> [--apply]` в `docs/specs/`.
49: - Действующее поведение отделено от планируемого: в блоке `changes` метаданных фиксируются отдельные предложения изменений (`draft → approved → implemented → accepted → cancelled`).
50: - Фиксируется влияние на существующие документы: какие требования добавляются, изменяются или отменяются.
51: - Согласование спецификации само по себе **не разрешает кодирование**.
52: 
53: ### 3. Проектирование (`design`)
54: - Цель: определить архитектуру, интерфейсы, форматы данных, риски, совместимость и стратегию восстановления.
55: - Документ design создаётся в `docs/designs/` через `playbook.py document create design <тема> [--apply]`.
56: - Принципиальные архитектурные решения фиксируются в ADR (`docs/adr/NNNN-<тема>.md`) через `playbook.py document create adr <номер>-<тема> [--apply]`.
57: - Принятый ADR не переписывается: при изменении решения создаётся новый ADR, а прежний помечается заменённым (`replaces`) и архивируется только после фактической утраты силы.
58: - Этап проектирования не запускает кодирование.
59: 
60: ### 4. Планирование (`plan`)
61: - Цель: составить исполнимый план этапов, зависимостей, уровней проверок и доказательств.
62: - Для нескольких связанных задач создаётся план в `docs/plans/` через `playbook.py document create plan <тема> [--apply]`. Статусы выполнения задач в план не копируются: их единственным источником остаются карточки.
63: - Для маленькой задачи план находится непосредственно в карточке задачи.
64: - Отдельный план архивируется только после завершения всех его задач и успешного итогового аудита блока.
65: 
66: ### 5. Постановка задач (`tasks`)
67: - Цель: сформировать карточки задач с уникальным ID по шаблону [task.md](../templates/task.md) в `docs/tasks/`.
68: - Карточка создаётся в статусе `draft`. Переход в `ready` требует согласованных границ, понятной приёмки, проверок и завершённых зависимостей.
69: - Крупная задача разделяется на подзадачи, и одновременно заводится общая карточка типа `AUDIT` с зависимостью от всех подзадач блока.
70: 
71: ### 6. Выполнение (`implementation`)
72: - Исполнитель проверяет готовность карточки, ветку и ресурсы, заполняет поля `Executor:` и `Model:` точными именами и переводит карточку в `in_progress`.
73: - Реализует код, пишет постоянные тесты, готовит черновик изменений в документации и регистрирует сопровождающие материалы.
74: - Изменение согласованного поведения требует возврата к спецификации, изменение архитектуры — к проектированию.
75: - Исполнитель **не закрывает** задачу сам и **не архивирует** документы, приёмка которых ещё не проведена.
76: 
77: ### 7. Проверка (`verify`)
78: - Проводится исполнителем: запуск автоматических тестов, регрессионных и пользовательских сценариев.
79: - При настроенном runner запускается `playbook.py verify <ID>`, сохраняющий отчёты и отпечатки входов в `work/verification/`.
80: - Доказательства сохраняются в каталоге материалов задачи `docs/tasks/<ID>-evidence/`.
81: - Исполнитель регистрирует передачу командой `playbook.py lifecycle handoff <ID> --summary "..."` и переводит карточку в `in_review`.
82: - Передача содержит описание изменений, границы приёмки, отчёты проверок и команды воспроизведения, достаточные для независимого аудита в новой сессии без чтения истории переписки. Исполнитель завершает работу на этом шаге.
83: 
84: ### 8. Аудит (`audit`)
85: - Запускается в **отдельной сессии** независимым агентом либо проводится лично инженером.
86: - Аудитор проверяет требования, код, тесты, свежесть входов и воспроизводимость доказательств.
87: - Протокол фиксируется в карточке строкой атрибуции `## Аудит <время со смещением>; исполнитель: <имя>; модель: <фактическая модель>.`
88: - При наличии замечаний карточка возвращается `in_review → in_progress` на исправление исполнителю.
89: - При успешной приёмке аудитор регистрирует приёмку: `playbook.py lifecycle accept <ID> --result accepted --kind acceptance`.
90: - Закрытие карточки и перенос её материалов выполняет аудитор или инженер через CLI: `playbook.py close <ID>` (или через `lifecycle plan` + `apply`). Отдельного режима закрытия нет.
91: - Для крупного блока аудит блока проверяет совместную работу подзадач, регистрирует приёмку и архивирует общие документы блока (`promote_change`, архивирование плана и общих материалов).
92: 
93: ## Отмена, откладывание и возобновление
94: 
95: - Отмена задачи: переводится в `cancelled` с фиксацией причины через `playbook.py close <ID> --status cancelled`. Зависимость от отменённой задачи не считается выполненной.
96: - Отмена/откладывание документа: фиксируется статус `cancelled` или `deferred` в метаданных документа.
97: - Возобновление работы (`reopen`): для закрытой задачи выполняется через `lifecycle plan` с действием `reopen`. Карточка возвращается в `docs/tasks/`, статус сбрасывается, зависящие активные работы возвращаются в `blocked`.

103: 2. Проверить результаты проверок и зафиксировать следующий шаг.
104: 3. При аудите контрольная точка обязательна: результаты проверки обязательно сохраняются в проекте с точной строкой атрибуции; итоговый ответ содержит ссылку на сохранённые результаты.

18: ## Источники истины
19: 
20: - **Действующие и планируемые требования**:
21:   - Принятая спецификация и design описывают **текущее фактическое поведение** системы.
22:   - Планируемые изменения оформляются в разделе предложений и регистрируются в блоке `changes` метаданных документа (`draft → approved → implemented → accepted → cancelled`). Действующее описание не перезаписывается до фактической реализации и независимой приёмки (`promote_change`).
23:   - При частичном изменении возможностей (например, прекращении поддержки одного формата) обновляется действующая редакция общей спецификации. Документ не архивируется, пока он описывает сохраняющие силу требования.
24: - **Архитектурные решения (ADR)**:
25:   - Фиксируют контекст, выбранный вариант и обоснование.
26:   - Принятый ADR не редактируется под новое решение. При смене подхода создаётся новый ADR со ссылкой `replaces` на прежний. Прежний ADR архивируется только после того, как описанный механизм фактически выведен из эксплуатации.
27: - **Планы реализации**:
28:   - Фиксируют порядок, этапы и проверки для блока задач.
29:   - Статусы выполнения задач в план не копируются: единственный источник статуса задачи — её карточка. Отдельный план архивируется после завершения всех задач и приёмки блока.
30: - **Карточка задачи**:
31:   - Единственный источник статуса задачи, исполнителя, модели, дат, записей передачи (`handoff`) и приёмки (`acceptance`).
32: - **Сопровождающие материалы**:
33:   - Каждый материал (отчёт runner, лог, снимок) принадлежит ровно одному владельцу (`owner`).
34:   - Общие доказательства блока закрепляются за общим аудитом или планом блока и не архивируются до завершения всей группы задач.
35:   - Неизменяемые доказательства (`immutable: true`) не редактируются при переносе; CLI сохраняет карту соответствия исходных и архивных путей (`move-map`).

38:   - Архив не входит в обязательное чтение активной задачи: он читается по явным ссылкам, при аудите, расследовании регрессий и восстановлении контекста.
