### A-03 — P1: сверка индекса теряет утраченный legacy-failed по UUID

Критерии: AC-01, AC-02, AC-03.

`checks_select._latest_better` при равном времени/seq консервативно выбирает failed. Однако `checks_results.load_results` (180–184) при сверке со свидетельством индекса отбрасывает status и сравнивает только полный ключ с UUID: индексный failed с меньшим UUID не считается потерянным, если остался passed с большим UUID. Но `checks_results.update_index` (114–115) и сохранение прежних записей в `rebuild_index` (238–240) продолжают сравнивать полный `result_order_key`, включая result_id. В результате существующий legacy-индекс с большим UUID старого passed остаётся passed даже после того, как чтение результатов уже обнаружило failed и недоказуемую историю.

Минимальное воспроизведение: `python3 work/verification/PB-074/audit-02/probe_legacy_loss.py . clean`. После реальных passed → failed результаты переводятся в legacy-фикстуру с равным временем и без run_seq, индекс удаляется и штатно перестраивается **в корректный failed**. После удаления только failed-файла project gate становится ok=true/covered, task gate ok=true/not_applicable; task stale ok=true, attempts_after_stale=2. Индекс продолжает хранить failed. Новый реальный seq-passed восстанавливает покрытие (attempts_total=3). [Результат с корректным индексом](legacy-loss-clean.json). Поэтому дефект не зависит от неверного исходного индекса.

Дополнительное воспроизведение старого индекса: `python3 work/verification/PB-074/audit-02/probe_legacy_loss.py .`. Проба использует реальный runner и реальные subprocess command на временном проекте без Git. Выполняет passed → failed с управляемым одинаковым finished_at, UUID `fff…` → `000…`; переводит результат в совместимую legacy-фикстуру без run_seq и восстанавливает старый индекс штатным update_index в порядке исполнения. Модульная проверка payments не имеет applicability=always. Входы/политика не меняются.

До утраты failed project gate закрыт и сообщает corrupt. Штатный rebuild на полной паре результатов всё равно сохраняет passed из прежнего индекса. Затем удаляется только failed-запись: индекс больше не содержит свидетельства о ней, оставшийся passed объявляется пригодным. Факт: **project gate ok=true/covered**, **task gate ok=true/not_applicable**, **task stale ok=true**, attempts_after_stale=2 — без нового исполнения. [Полный результат](legacy-loss.json), [код пробы](probe_legacy_loss.py).

Контроль: `python3 work/verification/PB-074/audit-02/probe_legacy_loss.py . forward` меняет только UUID-порядок. Индекс хранит failed, оба gate остаются закрыты, task stale реально повторяет проверку и получает failed (attempts_after_stale=3). После нового фактического passed обе фикстуры восстанавливают project gate; итоговый счётчик 3 против 4. [Контроль](legacy-loss-control.json).

Влияние: комбинация двух исправляемых случаев — неоднозначного legacy-порядка и утраты записи — всё ещё даёт ложную готовность task и project gate по старому passed. Это локальная диагностика; protected-доверие и реальный CLI release-ready новой пробой не подтверждались.

Критерий исправления: единый консервативный порядок/свидетельство неоднозначности должны действовать также при записи, сверке и rebuild индекса. Уже обнаруженный непокрывающий исход не должен исчезать после потери его файла и rebuild, пока нет нового фактического успешного доказательства. Постоянная регрессия должна использовать существующий старый индекс, оба UUID-порядка, rebuild до/после утраты, task/project gate, stale и восстановление seq-прогоном.
