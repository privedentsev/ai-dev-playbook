## Задача

### Цель и границы

Устранить A-04 (P1) и A-05 (P2) повторного аудита AUDIT-009: потерю задачного обязательства после повреждения/удаления записи последнего failed и ложную готовность на неоднозначной старой истории без run_seq. Сохранить выбор по зависимостям, законный reuse, legacy/opt-in и честные границы local/protected. Архив PB-057–064/PB-073 и их материалы не переоткрывать и не переписывать. Реализация этой задачи не выполняется в сессии аудита.

### Контекст

[AUDIT-009](AUDIT-009.md), [повторный протокол audit-02](AUDIT-009-evidence/audit-02/report.md), [команды и результаты](AUDIT-009-evidence/audit-02/commands.json). Предыдущее исправление: [PB-073](../archive/tasks/PB-073.md), уже done/accepted; её историческую приёмку не менять. Незавершённая AUDIT-009 не задаётся зависимостью: исправление должно быть доступно до повторной приёмки блока.

Требования: [R-11, R-16, R-19; AC-05, AC-09, AC-10](../specs/dependency-aware-verification.md), [design §5–6](../designs/dependency-aware-verification.md). Повторный аудит выполнен на 6311aa96f59db025b4fde3919775e03760193b3a, macOS 27.2.1 / Python 3.14.6. 328 адресных тестов прошли; собственные составные сценарии ниже выявили остаточные дефекты.

Воспроизведение из корня репозитория:
- [A-04](AUDIT-009-evidence/audit-02/report.md#a-04): `python3 docs/tasks/AUDIT-009-evidence/audit-02/probe_corrupt_obligation.py . corrupt` и тот же вызов с `delete`. Реальный CLI на временном проекте без Git: project passed → project failed → повреждение/удаление записи failed. До потери истории task gate закрыт, после — ok=true/not_applicable; task stale rc=0 без нового исполнения, счётчик остаётся 2. Release-ready в этом сценарии честно отклонён.
- [A-05](AUDIT-009-evidence/audit-02/report.md#a-05): `python3 docs/tasks/AUDIT-009-evidence/audit-02/probe_legacy_equal.py .`. Реальные процессы passed → failed, управляемое одинаковое время, UUID в обратном лексикографическом порядке. Новые seq-записи блокируют gate; совместимая фикстура старых записей без run_seq после rebuild индекса выбирает старый passed и даёт project gate.ok=true. Это явная фикстура legacy-формата; естественное совпадение часов и реальная миграция рабочего проекта не заявляются.

Пробы печатают наблюдения; rc=0 их собственного процесса не означает успешное поведение продукта. Полные JSON, логи и ограничения принадлежат AUDIT-009. Старые доказательства не изменять. Чужие docs/index.md, docs/plans/index.md и draft verification-process-readiness.md сохранять.

### Критерии приёмки

- [x] AC-01: Известный check_id с повреждённой/утраченной историей остаётся непокрытым обязательством независимо от пустого diff и от удаления непригодных результатов из расчёта reuse. В обеих CLI-пробах A-04 task run/status/gate/handoff не объявляют готовность без нового успешного доказательства; stale повторяет проверку либо явно блокируется. Регрессии не подменяют модульную применимость always. Свидетельство утраты переживает rebuild индекса, повторный stale и запуск другой задачи; после восстановления целостности истории и нового реального passed покрытие и законный cross-task reuse восстанавливаются.
- [x] AC-02: Неоднозначный порядок нескольких legacy-записей без run_seq с одинаковым finished_at не разрешается выбором UUID в пользу passed. При отсутствии доказуемого последнего успешного исполнения gate/reuse требуют новый фактический прогон или безопасно блокируются. Проверены оба лексикографических порядка UUID, отсутствие/перестройка производного индекса, новая seq-запись после старой истории и корректное восстановление успешным прогоном. Однозначная старая история и порядок новых seq-записей сохраняются.
- [x] AC-03: Поведенческие регрессии доказывают task-покрытие для failed/timeout/blocked/manual, повреждённых и удалённых исходов; product release/protected не регрессируют. Изменения, среда и результаты отражены в документации и EXEC/CHECK/HANDOFF; выполнены относящиеся к изменению checks_* и lifecycle/legacy-проверки, index/check --ready и штатный verify, self-manifest обновлён после правок комплекта. Архив и исходные материалы аудита побайтно сохранены.

### План

1. Прочитать AUDIT-009 audit-02 и историческую передачу PB-073, воспроизвести A-04/A-05 на текущем кандидате. Проверить границы передачи знаний о corrupt_ids между results, selector, runner/status и gate.
2. Сохранить недоказанные обязательства до пригодного покрытия; консервативно обработать неоднозначную legacy-историю. Не обходить проблему изменением политики/выключением reuse или подменой source-проверок always.
3. Добавить постоянные реальные CLI/adapter-регрессии критериев, включая пустой diff после успешного baseline, поздний failed, порчу/удаление, rebuild и другую задачу. Проверить восстановление после успешного фактического исполнения.
4. Обновить связанные документы и self-manifest, зарегистрировать новые доказательства, выполнить проверки и штатные preflight/verify/handoff по актуальному контракту. Структурные проверки не выдавать за поведение CLI.
5. Передать PB-074 независимому аудитору; затем повторить AUDIT-009. Самостоятельно приёмку/закрытие исправления не выполнять; commit/push/release требуют отдельного поручения.

### Ресурсы

Python stdlib, временные проекты без Git, реальные CLI/subprocess и управляемые часы для фикстур истории. resources.policy_revision=2, бюджеты проекта null; исходный self-project остаётся legacy без checks_policy. Внешняя песочница может мешать sandbox-exec: такую ошибку отличать от дефекта продукта. Реальная отдельная OS/CI identity аудитом не подтверждена; local-диагностику не объявлять protected-эксплуатацией. Новые материалы: `docs/tasks/PB-074-evidence/`; исходные контрпримеры — зарегистрированный каталог `docs/tasks/AUDIT-009-evidence/audit-02/`.
