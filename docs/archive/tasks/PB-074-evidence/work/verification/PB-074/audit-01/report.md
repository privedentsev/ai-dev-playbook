### A-01 — P1: утрата каталога results снимает известное обязательство

Критерии: AC-01, AC-03.

`checks_results.load_results`, строки 139–141: отсутствие каталога возвращает пустую историю до чтения сохранённого `results-index.json`. Известный failed исчезает из обязательств при пустом diff. `checks_plan` также пропускает загрузку при отсутствии каталога (playbook.py:1601).

Воспроизведение: `python3 work/verification/PB-074/audit-01/probe_history_loss.py . directory`. Во временном проекте без Git выполняются реальные `project force`: passed → failed. Удаляется только `work/checks/results`, а baseline и индекс остаются. Никакие определения/входы проверки не изменяются.

Факт: до удаления task gate `ok=false`; после удаления и штатного rebuild индекса — `ok=true`, payment `not_applicable`. `checks plan` и `checks status` снимают обязательство; task stale возвращает rc=0, счётчик реальных исполнений остаётся 2. Release-ready по-прежнему возвращает rc=1.

Влияние: ложная готовность задачного gate без нового доказательства после утраты всей истории, несмотря на сохранившееся свидетельство failed в индексе. Это остаточный случай исправляемого A-04, а не проверка защищённого режима.

Критерий исправления: проверять свидетельства индекса независимо от наличия каталога results; утрата каталога должна оставлять check_id непокрытым до реального успешного исполнения. Добавить постоянный CLI-сценарий с rebuild, повторным stale и другой задачей.

Доказательства: [directory.json](directory.json), [проба](probe_history_loss.py).

### A-02 — P2: checks plan переиспользует результат недоказуемой истории

Критерии: AC-01, AC-03.

`playbook.checks_plan` (playbook.py:1605–1615) передаёт одновременно `corrupt_ids` и старые пригодные результаты; runner/status/gate предварительно исключают такие check_id. В `checks_select.plan` (659–674) corrupt-флаг добавляет обязательство, но последующий evaluate_reuse снова превращает его в reused по старому passed.

Воспроизведение: `python3 work/verification/PB-074/audit-01/probe_history_loss.py . delete`. Те же реальные passed → failed, затем удаление только failed-записи с сохранённым индексом; штатный rebuild сохраняет свидетельство утраты.

Факт: `checks plan DEV-01` показывает `payment: reused`, `run=0, reused=1`, оценку 0с и ссылку на старый passed, одновременно сообщая о недоказуемой истории. `checks status` показывает `payment: run`, gate остаётся `ok=false`; реальный task stale выполняет проверку (attempts=3) и возвращает rc=1.

Влияние: read-only план сообщает непригодное покрытие и неверную стоимость, противоречит фактическому runner/status/gate и заявлению EXEC/HANDOFF о едином поведении. Сам фактический gate в этом сценарии готовность не открывает.

Критерий исправления: corrupt_ids должны запрещать reuse в общем планировщике либо в каждом вызывающем пути; добавить CLI-регрессию plan/status/run на одинаковом состоянии повреждённой и утраченной истории, сохранив законный reuse после восстановления.

Доказательства: [delete.json](delete.json), [проба](probe_history_loss.py).
