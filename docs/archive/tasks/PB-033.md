## Область изменений

verification.py, playbook.py (verify), доверенный реестр и отчёты v2. Preflight проверяет готовность перед дорогими subprocess; не требует будущих отчётов.

## Условия готовности

План/границы согласованы инженером; зависимости завершены; поля/интерфейсы соответствующего этапа однозначны. Исполнитель назначается только при старте. Изменение требований/архитектуры возвращается к соответствующему этапу, не решается скрытым расширением задачи.

## План

1. Подключить read-only готовность и объяснение плана.
2. Реализовать command и manual pipelines с immutable-отчётами.
3. Добавить reuse, прогнать subprocess-матрицу и legacy-регрессию.

## Приёмка

- [x] verify --preflight не пишет/не запускает команды и показывает ID, обязательность, актуальность, ошибки и способы исправления.
- [x] Обычный verify до снимка согласованно исправляет разрешённый производный индекс или отказывает с понятной причиной; план не правится молча.
- [x] Исполняется только разрешённый argv из реестра, сохраняются реальные returncode/timeout и before/after. Изменение входов во время прогона выявлено.
- [x] Ручной сценарий связан с предъявленным snapshot; правка после предъявления требует нового просмотра. Нет браузера/подтверждения — not_run, а не passed.
- [x] Свежие независимые результаты переиспользуются без повторного процесса, failed остаётся историей. v1 verify работает по старому контракту.
- [ ] Самопроверка и handoff зарегистрированы, независимая приёмка выполнена в отдельной сессии либо инженером перед закрытием.

## Проверки и доказательства

Subprocess-счётчики запусков; stale during run, timeout, отказ неизвестной команды; manual candidate до/после изменения; preflight input hashes. Предлагаемые tests/test_verification_v2.py и tests/test_verification_preflight.py.

Команды основы: целевые `python3 -m unittest discover -s tests -p '<согласованный файл тестов>' -v`, затем настроенный `python3 ai-dev-playbook/scripts/playbook.py verify PB-033` по действующему на этапе контракту. Перед запуском проверить argv/inputs и готовность служебных данных. Проверить `index --all`, `check --ready`, `git diff --check`; после изменения файлов комплекта выполнить `adopt . --force --apply` до финального прогона. Существующий timeout не обходить скрытым изменением runner: заранее согласовать настройку при необходимости.

Материалы: `docs/tasks/PB-033-evidence/` и зарегистрированные verify-прогоны. Неизменяемые отчёты не переписывать. Структурные проверки не являются доказательством поведения CLI.

План реализации:
1. Preflight v2 и объяснение плана:
   - Проверка готовности задачи v2 (схема, маршрут, план проверок, зависимости, статус ready/in_progress/in_review, известные материалы, пути).
   - Вычисление обязательности и применимости (через `verification_policy.required_checks`), отображение ID, обязательности, актуальности, ошибок и действий по исправлению.
   - Read-only режим: отсутствие записей и запусков команд.
   - Разрешённая синхронизация/проверка индексов до снимка проверок.
2. Command runner v2 и subprocess-матрица:
   - Исполнение только разрешённого argv из реестра доверенной конфигурации (`task_workflow.checks`).
   - Фиксация реальных exit_code / returncode, timeout, snapshot_before и snapshot_after.
   - Обнаружение изменения входов во время прогона (`snapshot_before != snapshot_after` для значимых входов).
   - Формирование immutable-отчёта v2 по спецификации (`report_version: 2`).
3. Manual runner v2 и candidate snapshot:
   - Привязка ручного сценария к предъявленному candidate snapshot.
   - Изменение файлов после предъявления требует нового просмотра.
   - При отсутствии подтверждения / браузера статус фиксируется как `not_run`, а не `passed`.
   - Регистрация ручного результата (`verify ID --record-manual <FILE>` или соответствующий CLI-параметр).
4. Reuse и регрессия:
   - Повторное использование свежих независимых результатов (`reusable` из `verification_policy`) без повторного запуска процесса.
   - Неизменность истории: `failed` остаётся в истории и не заменяется молча.
   - Сохранение полной обратной совместимости для задач и конфигураций v1 (legacy verify работает по старому контракту).
5. Тестирование и верификация:
   - Разработка постоянных целевых unit/subprocess тестов (`tests/test_verification_v2.py`, `tests/test_verification_preflight.py`).
