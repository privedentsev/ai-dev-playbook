## A-04 — Порча или удаление failed стирает обязательство задачи

Серьёзность: **P1**, блокирует приёмку. Критерии AUDIT-009: AC-01, AC-02, AC-03. Требования спецификации: R-11, R-16, R-19; сквозные AC-09/AC-10. Речь о надёжности fail-closed local-диагностики, а не о заявлении обхода protected-границы.

### Воспроизведение

Из корня репозитория:

```bash
python3 docs/tasks/AUDIT-009-evidence/audit-02/probe_corrupt_obligation.py . corrupt
python3 docs/tasks/AUDIT-009-evidence/audit-02/probe_corrupt_obligation.py . delete
```

Скрипт создаёт отдельный временный проект без Git. Политика валидна и принята реальным `setup apply`: проверка `payment` связана с модулем `payments`, не имеет `applicability=always`. Команда исполняется реальными подпроцессами, счётчик находится вне учитываемых входов; первая попытка успешна, следующие завершаются кодом 1. История портится только внутри временного проекта.

1. `checks run DEV-01 --scope project --mode force`: **rc=0/passed**, записан текущий baseline.
2. Повторный project force без изменения учитываемых файлов: **rc=1/failed**, счётчик равен 2.
3. До вмешательства `checks_gate.evaluate(scope=task)` возвращает **ok=false**, `payment=uncovered`: исправление PB-073 работает на целой истории.
4. Вариант `corrupt`: последний `work/checks/results/<run>/payment.json` заменяется на `{`. Вариант `delete`: этот файл удаляется при сохранённом results-index.
5. После этого task gate возвращает **ok=true**, `covered=[]`, `uncovered=[]`, `payment=not_applicable`. Диагностика прямо сообщает: «история недоказуема», «повреждённая история check_id ['payment']».
6. `checks status DEV-01` показывает `payment: not_applicable`, покрытие 0/0. Следующий `checks run DEV-01 --scope task --mode stale`: **rc=0/not_applicable**, счётчик всё ещё **2** — команда не исполнялась заново.
7. `checks release-ready DEV-01` в том же состоянии честно возвращает **rc=1/uncovered**. Подтверждённый дефект относится к task-scope.

Полные реальные команды, коды, stdout/stderr и вердикты: [повреждение JSON](probe-corrupt.json), [удаление файла](probe-deleted.json). Проба печатает наблюдения; rc=0 её собственного процесса не является успешной проверкой продукта.

### Причина и влияние

`checks_results.load_results` корректно помечает check_id как повреждённый, в том числе по свидетельству производного индекса об удалённой поздней записи. Но `checks_runner.execute` (около строк 300–322) и `checks_gate.evaluate` (около строк 226–237) удаляют **всю** историю этих check_id до вызова selector, не передавая в него сам набор `corrupt_ids` как открытые обязательства.

При пустом diff селектор начинает с `not_applicable`. Новое правило PB-073 в `checks_select.plan` (около строк 605–620) возвращает такую проверку в `run` только при существующем последнем результате из UNRESOLVED_RESULT_STATUSES. После фильтрации результата уже нет; правило не срабатывает. Запрет reuse превращается в полное исключение проверки из задачного набора. Итоговый gate допускает нулевое покрытие, несмотря на признанную недоказуемость истории.

Предыдущие регрессии `test_a03_corrupt_latest_failed_blocks_reuse`/`test_a06_deleted_latest_failed_blocks_reuse` проходят, но не покрывают этот составной случай: актуальный baseline, модульная применимость без always и потеря последнего failed перед оценкой task gate.

Влияние: обычная потеря/порча записи результата снимает блокировку задачи, которую до этого удерживал реальный failed. Повторный stale не восстанавливает доказательство. Это нарушает явный контракт безопасной обработки повреждённой истории; предупреждение trust_mode=local не заменяет его.

### Критерий исправления

Сохранять обязательство известного check_id с недоказуемой историей независимо от diff и от отбрасывания непригодных результатов. Task run/status/gate/handoff не могут объявлять готовность без нового успешного доказательства. Проверить обе CLI-пробы без always-применимости, повторные stale, rebuild индекса, запуск другой задачи, последующее реальное исправление и законный reuse. Project release/protected не должны регрессировать. Детальная постановка — PB-074.

## A-05 — Старые записи без run_seq всё ещё допускают старый passed при равном времени

Серьёзность: **P2**. Критерии AUDIT-009: AC-01, AC-03. Требования R-11/R-19, сквозные AC-05/AC-10. Это остаточный сценарий исходного A-02 на формате истории, существовавшем до PB-073; новые записи с разными run_seq работают корректно.

Воспроизведение: `python3 docs/tasks/AUDIT-009-evidence/audit-02/probe_legacy_equal.py .`. Временный проект, реальные подпроцессы команды, явная always-применимость, одинаковые управляемые часы. Сначала passed с run ID `fff…`, затем failed с `000…`. На новых seq-записях gate закрыт. Для совместимого legacy-формата у обеих записей убирается поле evidence.run_seq; производный индекс удаляется и штатно перестраивается. Это явно сконструированная фикстура старого формата, а не заявление о естественном совпадении часов или о фактически выполненной миграции рабочего проекта.

Факт: обе записи валидны, история не помечена повреждённой, latest выбирает **passed** из `fff…`, project gate.ok=**true**. [Полный JSON](probe-legacy-equal.json). Последовательность фактических исполнений осталась passed → failed, но для старого формата не доказана по метаданным.

Причина: `result_order_key` в checks_select.py использует `(finished_at, run_seq, result_id)`, для каждой legacy-записи run_seq=-1. При равном finished_at обеих старых записей выбирается лексикографический UUID. В документации к функции такие записи намеренно поддержаны, но неоднозначность их взаимного порядка не приводит к консервативному решению.

Влияние: после обновления сохранённая история старого формата с одинаковыми метками допускает готовность по старому успеху, хотя более позднее исполнение упало. Исправление A-02 для новых seq-записей не разрешает доверять произвольному UUID как порядку старых исполнений. Это local-диагностика, не protected-эксплуатация.

Критерий исправления: неоднозначные одинаковые метки старых записей не дают готовность/успешный reuse по выбранному UUID. Без доказанного порядка требуется новый реальный успешный прогон либо безопасная блокировка; проверить оба порядка UUID, реконструкцию индекса и восстановление новым seq-исполнением, сохраняя совместимость с однозначной старой историей. Постановка — PB-074 AC-02.
