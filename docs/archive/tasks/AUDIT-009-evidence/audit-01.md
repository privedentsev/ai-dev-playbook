## Полномочия и готовность

Инженер разрешил независимый аудит и отдельную задачу исправлений, запретил исправления и переоткрытие архива. Зависимости PB-057–064 имеют done и историческую accepted-приёмку. У AUDIT-009 нет HANDOFF/актуальной CLI-передачи; исходный `verify --audit-ready` отклонён в draft, после начала — «аудит требует in_review». Это техническая неготовность собственной итоговой карточки, не основание выдумывать passed/HANDOFF или принимать блок. Содержательный аудит выполнен и зафиксирован отдельным принадлежащим карточке протоколом; CHECK отражает отрицательный результат, диагностическая запись lifecycle не является acceptance.

## A-01 — Обязательство исчезает после неуспешного прогона

Серьёзность: **P1**, блокирует приёмку. Критерии AUDIT-009: AC-01, AC-03; спецификация R-08, R-11–12, R-16; AC-05, AC-09.

Условие: валидная local-политика, проверка привязана к модулю `payments`, отдельная `applicability=always` не объявлена. Это разрешённая политика; постоянно выполнять все проверки политикой always нельзя считать исправлением выбора по зависимостям.

Воспроизведение из корня: `python3 docs/tasks/AUDIT-009-evidence/probe_cli_obligations.py .`.

Факт:

1. Во временном проекте без Git `setup apply` успешно принимает политику.
2. Первый `checks run DEV-01 --scope task --mode stale`: rc=1, реальная команда выполнена и вернула failed.
3. `checks status DEV-01`: payment=not_applicable, рядом показан последний failed; покрытие области задачи 0/0.
4. Повторный тот же `checks run`: rc=0, payment=not_applicable. Счётчик реальных исполнений остался **1**.
5. Единый `checks_gate.evaluate(scope=task)` возвращает **ok=true**, covered=[], uncovered=[], payment=not_applicable. У этой проверки никогда не было passed. Project `release-ready` в том же состоянии возвращает rc=1.

Причина: `checks_runner.py:64–91` читает общий baseline `work/checks/snapshot.json`; строка 539 безусловно обновляет его и при failed. При следующей оценке diff пуст, а `checks_select.plan` оценивает свежесть/последний исход только уже выбранных `run` (строки 558–560); утраченное обязательство не восстанавливается. Финальный `ok` исключает not_applicable из непокрытых.

Влияние: task-scope объявляет успех без требуемого доказательства, и общий gate допускает готовность задачи после реального failed. Контрпример не требует подделки файлов, ключей или отчётов; объяснение «local не защищён от владельца» его не устраняет.

Критерий исправления: сохранять обязательства задачи до пригодного покрытия; одинаковые CLI-команды после failed/timeout/blocked/неподтверждённой manual не теряют проверку через сдвиг baseline. Проверить task gate/handoff, запуск другой задачи, успешное исправление и законный reuse. Подробная приёмка — PB-073 AC-01.

## A-02 — Равное время скрывает более поздний failed

Серьёзность: **P2**. Критерии AUDIT-009: AC-01, AC-03; спецификация R-11; AC-05.

Воспроизведение: `python3 docs/tasks/AUDIT-009-evidence/probe_equal_timestamps.py .`.

Управляемые условия: одинаковый `now=2026-11-16T03:00:00.000000+00:00`, первый run ID `000…`, второй `fff…`; это тест порядка событий, а не утверждение о частоте естественного совпадения микросекунд. Проверка имеет явную always-применимость, поэтому A-01 здесь исключён. Команда исполняется двумя реальными подпроцессами с неизменёнными учитываемыми входами: сначала passed, затем failed.

Факт: первый force ok=true, второй force ok=false; затем latest выбирает первый passed, project gate.ok=true/covered=[payment]. Обе записи валидны, corrupt_ids пуст.

Причина: `checks_select.py:409–417` и `checks_results.py:92–98` используют строгое сравнение `finished_at >`, а загрузка истории идёт по лексикографическим именам каталогов, не по порядку фактических исполнений. Ветка protected имеет отдельный exec_seq, но локальная история им не пользуется.

Влияние: при равных метках времени (либо соответствующей потере порядка часов) локальный gate может подтвердить старый успех после неуспеха. Лексикографический порядок UUID не является порядком исполнения.

Критерий исправления: устойчивый согласованный порядок исходных исполнений в store/index/rebuild/selector/gate; поздний failed/timeout блокирует passed, последующий успешный запуск восстанавливает покрытие при обоих порядках имён. Подробная приёмка — PB-073 AC-02.

## A-03 — Архивирование ломает воспроизведение self-pilot

Серьёзность: **P2**, препятствует проверке AC-11. Критерии AUDIT-009: AC-01, AC-03; спецификация AC-11.

Воспроизведение: `python3 docs/archive/tasks/PB-064-evidence/self_pilot.py . /tmp/audit009-pilot-plan --plan-only`.

Факт: rc=1, FileNotFoundError при чтении `copy_a_legacy/docs/tasks/PB-064.md`. Команда использует реальный существующий путь архивированного скрипта; ошибка не сводится к неверному пути запуска. [Журнал](pilot-plan.log).

Причина: `docs/archive/tasks/PB-064-evidence/self_pilot.py:79–82` жёстко ожидает активную карточку и в следующих строках активный evidence/sidecar. После штатного close эти объекты находятся в архиве. Инструкции в архивированном matrix/pilot-report также приводят старый путь запуска.

Влияние: текущий итоговый аудитор не может воспроизвести пилот и проверить измерения; plan-only и полный запуск падают в одной подготовке ещё до сравнительных прогонов. Исторические цифры не опровергаются, но актуальная воспроизводимость отсутствует.

Критерий исправления: новый активный воспроизводимый инструмент/материал, работающий после закрытия PB-064, доступные инструкции, plan-only и полный измеренный сценарий на временных копиях без изменений архива и основной конфигурации. Подробная приёмка — PB-073 AC-03.

## Ограничения и следующий шаг

Полный legacy verify (~весь suite) заново не запускался: реализация не менялась, целевой набор проверен независимо.
