## Задача

### Цель и границы

Жизненный цикл и релиз. playbook.py/lifecycle.py, CLI modes/checkpoint и consumer gate, правила жизненного цикла. Не публиковать релиз и не создавать автоматические коммиты.

### Контекст

[Спецификация](../specs/dependency-aware-verification.md): R-08,12,16–18,20; сценарии AC-05,08–09. [Design](../designs/dependency-aware-verification.md), [ADR-0006](../adr/0006-dependency-aware-verification.md), [план](../plans/dependency-aware-verification.md).

Подготовлено по поручению инженера 2026-11-07. Выполнение пока не разрешено. Перед стартом: принятие технического проекта, завершённые зависимости, актуальный card show/handoff затрагиваемых работ и назначение исполнителя. Исходные чужие изменения сохранять.

### Критерии приёмки

- [ ] AC-01: Handoff/accept/release-ready используют один selector+coverage; текущие байты сверяются с проверенным candidate. В protected режиме local/поддельные отчёты не закрывают обязательства.
- [ ] AC-02: Release требует весь актуальный набор с cross-task reuse, force запускает всё; commit не триггер авторизации. Самостоятельная проверка/релиз владеют обычной карточкой, запуск в текущей задаче не создаёт новую.
- [ ] AC-03: Manual и новые сценарии приёмки не заменяются старым suite; stale передачи, перенос evidence, concurrent edits, restore и запреты внешнего release проверены.
- [ ] AC-04: Целевые поведенческие проверки и связанные регрессии пройдены; документация и self-manifest актуальны, EXEC/CHECK/HANDOFF содержат реальные доказательства и ограничения; передача зарегистрирована штатным CLI.

### План

1. Уточнить фактические интерфейсы зависимостей и связать изменения с критериями этой карточки.
2. Реализовать ограниченный объём, добавить постоянные позитивные и негативные проверки критериев AC-01–03; не подменять их структурной проверкой.
3. Обновить затронутые документы/шаблоны и self-manifest при изменениях комплекта; выполнить адресные проверки, index и check --ready.
4. Подготовить материалы и пройти действующие preflight/verify/handoff. До явного opt-in использовать прежний контракт; не отключать полный legacy suite ради экономии.
5. Записать EXEC/CHECK/HANDOFF и передать независимому аудитору; самостоятельно не закрывать.

### Ресурсы

Python и стандартная библиотека для основного CLI; локальные временные проекты и subprocess-счётчики. Новые зависимости защищённого executor обосновать в рамках принятого design. Фактические среда, policy_revision и бюджет фиксируются при старте; доступность отдельной OS/CI identity не предполагается.

Материалы: `docs/tasks/PB-062-evidence/`; команды воспроизведения и отчёты принадлежат этой карточке. Общие материалы и сквозная матрица — AUDIT-009/PB-064.

#### A-01 — Замечание
Серьёзность: P1
Критерии: AC-01, AC-02, AC-03
Проблема: protected-gate принимает квитанцию после истечения TTL внешней зависимости. `_protected_receipts` проверяет подпись и candidate, но не свежесть исходного executable-result; `_protected_verdict` возвращает ему covered.
Воспроизведение: из корня выполнить `python3 work/verification/PB-062/audit-01/probe_ttl.py` вне вложенного sandbox; политика требует api с TTL 60 секунд, реальный verifier выдаёт passed, evaluate вызывается с now=2099-01-01 и подменой только probe OS-границы.
Факт: ok=true, covered=[probe], uncovered=[], rejections=[].
Влияние: handoff/accept/release-ready могут признать просроченное внешнее доказательство пригодным; нарушена свежесть актуального набора по AC-05 спецификации.
Критерий исправления: protected consumer проверяет TTL/always_run и значимые привязки доверенного исходного результата по общему контракту свежести; просроченный результат не покрывает обязательство. Добавлены поведенческие регрессии для run и aggregate receipts.
