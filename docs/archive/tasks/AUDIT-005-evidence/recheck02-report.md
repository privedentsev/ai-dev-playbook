## A6 — High: неполный индекс пропускает часть пред-образа

**Воспроизведение:** `test_remaining_A6_incomplete_index_false_success`. Реальный subprocess получает SIGKILL после первой фактической записи обновления 0.0.2→0.0.3. В `backup_index.json` удаляется только VERSION из массива `backed`; файл backup/VERSION и его запись в `hashes` сохраняются. `update restore` возвращает 0, снимает pending, но VERSION остаётся 0.0.3, а project.json/manifest возвращены к 0.0.2. Следующий check падает.

**Причина:** `_read_backup_index` (`updating.py:743–774`) проверяет файлы только из backed; соответствие множества backed множеству hashes/фактических копий не проверяется. Частичный или пустой backed может объявить достаточным неполное восстановление. В автономном скрипте используется та же неполная проверка состава.

**Влияние:** сохранён полный пред-образ, но повреждение метаданных оставляет смешанное состояние и снимает защитный маркер с сообщением об успехе. Это продолжение исходного A6, а не новая независимая находка.

**Критерий исправления:** валидировать целостность и полноту индекса до любых изменений: согласованность backed/hashes/набора копий, отсутствие повторов и пересечения backed/added; если поддерживается старый формат без hashes, его гарантии должны быть явно отделены. При неполном/противоречивом индексе CLI и standalone возвращают ненулевой код, сохраняют pending и не меняют проект. После восстановления корректного индекса — полный возврат и проверка пред-образа. Добавить сценарии пропущенного элемента и пустого backed при существующих копиях.

Размещение: [PB-018](../../archive/tasks/PB-018.md). Статус находки — открыт.

## A7 — High: старый автономный restore использует чужой pending

**Воспроизведение:** `test_remaining_A7_standalone_ignores_pending_owner`. Первая операция 0.0.2→0.0.3 реально прерывается SIGKILL, восстанавливается, затем обновление до 0.0.3 успешно повторяется. Старая операция с её restore.py остаётся на диске. Следующее обновление 0.0.3→0.0.4 прерывается SIGKILL после первой записи — pending принадлежит новой операции. Запуск **старого** restore.py возвращает 0, восстанавливает 0.0.2 вместо пред-образа 0.0.3 и удаляет pending новой операции. Маркер вручную не редактировался; использованы реальные операции.

**Причина:** автономный `RESTORE_SCRIPT` (`updating.py:804–886`) берёт общую файловую блокировку, но не сверяет op_id/op_dir текущего pending со своим каталогом. В конце pending удаляется без проверки владельца. `_release_pending` защищает apply, но автономное восстановление им не пользуется и не воспроизводит его проверку.

**Влияние:** штатный восстановитель из другого каталога откатывает не ту операцию и скрывает актуальную незавершённую транзакцию. Исправление обхода живой блокировки подтверждено, требование принадлежности операции выполнено не полностью.

**Критерий исправления:** до записи сверять владельца и путь операции pending с выбранной резервной копией; несовпадение должно давать отказ без изменения файлов/маркера. Снимать только собственный маркер. Определить отдельно поведение при отсутствии pending, не подменяя восстановление текущей операции неявным откатом старой. Проверить ошибочный старый restore.py и правильный текущий restore.py на двух последовательных обновлениях с реальным SIGKILL; актуальная операция должна полностью восстановиться до своей исходной версии.

Размещение: [PB-019](../../archive/tasks/PB-019.md), совместная область с PB-018. PB-019 возвращён в in_progress, A7 открыт.
