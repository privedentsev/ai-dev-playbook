## Задача

### Цель и границы

Runner и результаты. verification.py, cache/result index, unittest adapter, отчёты и постоянные негативные тесты. Подпись локальной записи не выдавать за доверенное выполнение.

### Контекст

[Спецификация](../specs/dependency-aware-verification.md): R-11–15; сценарии AC-04–07. [Design](../designs/dependency-aware-verification.md), [ADR-0006](../adr/0006-dependency-aware-verification.md), [план](../plans/dependency-aware-verification.md).

Подготовлено по поручению инженера 2026-11-07. Выполнение пока не разрешено. Перед стартом: принятие технического проекта, завершённые зависимости, актуальный card show/handoff затрагиваемых работ и назначение исполнителя. Исходные чужие изменения сохранять.

### Критерии приёмки

- [x] AC-01: Unittest адаптер сравнивает expected/actual IDs, count и outcomes/subtests; exit 0/zero, unexpected skip, missing/duplicate IDs и crash не проходят. Понятные descriptions выводятся с IDs; command/manual отличимы.
- [x] AC-02: Freshness учитывает входы, closure, адаптер, команду, политику, среду и внешнюю TTL/version. Независимые результаты reused; поздний failed не скрывается; история/индекс восстанавливаемы без ложного reuse.
- [x] AC-03: Cross-task reuse изолирован по project/trust; task requirements не теряются. Force выполняет все выбранные проверки; stale только без пригодного успеха; snapshot/race/corrupt history проверены.
- [x] AC-04: Целевые поведенческие проверки и связанные регрессии пройдены; документация и self-manifest актуальны, EXEC/CHECK/HANDOFF содержат реальные доказательства и ограничения; передача зарегистрирована штатным CLI.

### План

1. Уточнить фактические интерфейсы зависимостей и связать изменения с критериями этой карточки.
2. Реализовать ограниченный объём, добавить постоянные позитивные и негативные проверки критериев AC-01–03; не подменять их структурной проверкой.
3. Обновить затронутые документы/шаблоны и self-manifest при изменениях комплекта; выполнить адресные проверки, index и check --ready.
4. Подготовить материалы и пройти действующие preflight/verify/handoff. До явного opt-in использовать прежний контракт; не отключать полный legacy suite ради экономии.
5. Записать EXEC/CHECK/HANDOFF и передать независимому аудитору; самостоятельно не закрывать.

### Ресурсы

Python и стандартная библиотека для основного CLI; локальные временные проекты и subprocess-счётчики. Новые зависимости защищённого executor обосновать в рамках принятого design. Фактические среда, policy_revision и бюджет фиксируются при старте; доступность отдельной OS/CI identity не предполагается.

Материалы: `docs/tasks/PB-060-evidence/`; команды воспроизведения и отчёты принадлежат этой карточке. Общие материалы и сквозная матрица — AUDIT-009/PB-064.

Изменения: runner и результаты по design §6–7 и spec R-11–15. `checks_unittest.py` — адаптер protocol 1: отображает одобренный argv на выбор unittest (`-m unittest discover|имена`; `-k` и чужие команды отклоняются), исполняет suite в подпроцессе и пишет JSON-отчёт expected/actual через события TestResult, включая провальные subtests; `verdict` отклоняет нулевой набор, тест вне каталога, пропавший ID закреплённой группы, повторный/неожиданный/незавершённый ID, skip и expected_failure вне допусков, unexpected_success, crash и несогласованный отчёт. `checks_results.py` — append-only `work/checks/results/<run_id>/<check_id>.json` и производный `results-index.json`; повреждённые записи пропускаются, индекс пересобирается из проверенных записей, последний по finished_at решает. `checks_runner.py` — `checks run` (scope task/project × mode stale/force, checkpoint) и `checks status`: результаты схемы 1 с полным binding (policy/definition/closure/input/environment digests, adapter/runner, task_requirements_digest при входе task_projection), reuse — отдельной строкой с указателем на исходный результат; внешняя свежесть always_run/ttl/version, снимок входов до/после команды — мутация даёт blocked (локальный режим честно слабее изоляции PB-061); manual — not_run; код выхода 0 только при полном покрытии. checks_select дополнен `binding_environment` (внешние факты required_environment в привязке) и прокидкой projections/environment в evaluate_reuse/plan — проверки с входами projection/environment теперь доказуемо свежи. Компромиссы: `group` записи каталога привязана к id проверки или модуля; adapter-identity у command — argv-command; заблокированные результаты пишутся с нулевым input_digest как явно недоказанные.
