## A-01 — P1: разный run_seq не доказывает порядок перекрывающихся исполнений

`checks_runner.execute` выделяет номер всему прогону до исполнения проверок (checks_runner.py:308–312). После публикации первой проверки A следующий прогон B получает больший номер, хотя вторая проверка A ещё выполняется. `_latest_better` безусловно предпочитает больший номер (checks_select.py:489–492).

Проба `python3 work/verification/PB-078/audit-01/probe_overlap.py .` создаёт временный проект без Git и две command-проверки. A публикует первую passed/seq=0, затем вторая блокируется на внешнем маркере. B получает seq=1 и завершается passed; после этого A освобождается и завершается failed/seq=0. История и UUID не редактируются, часы не подменяются. Маркеры и окружение управляют только исходом subprocess.

Факт в overlap.json: failed A завершился после passed B, но выбран passed/seq=1; project gate.ok=true; stale reused=2, новых исполнений нет; corrupt=[] . Перекрывающиеся исполнения с различными seq ошибочно объявлены упорядоченными. Консервативная ветка равного seq не помогает. Нарушен AC-02: старый успех скрывает недоказанное обязательство при перекрытии.

Требуется доказуемый порядок с учётом перекрытий либо сериализация; до его доказательства ошибка не должна скрываться успехом. Регрессия должна использовать реальные перекрывающиеся прогоны с разными seq и проверять gate/stale/index/rebuild, затем восстановление покрытия новым неперекрывающимся успешным запуском.
