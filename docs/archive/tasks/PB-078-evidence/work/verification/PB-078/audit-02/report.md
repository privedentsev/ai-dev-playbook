## A-02 — P1: утрата блокирующей записи не обнаруживается по состоянию индекса

`checks_results._claim_unaccounted` сверяет только запись-победителя верхнего уровня, игнорируя order.nf и остальные компоненты состояния. `_choose_order_state` при этом использует максимум finished_at всех неуспехов, который может принадлежать другой записи. Поэтому сохранённый индекс не предотвращает готовность после утраты такого блокирующего результата. `rebuild_index` тем же сравнением стирает свидетельство утраты.

Воспроизведение: `python3 work/verification/PB-078/audit-02/probe_loss.py .`.
Временный проект без Git, настоящая subprocess-команда со счётчиком. Три force-прогона с управляемым now: failed seq=0/12:00, failed seq=1/10:00, passed seq=2/11:00. Часы ОС не меняются, UUID и содержимое результатов не редактируются. До утраты gate=false, выбран failed seq=1; индекс хранит order.nf=12:00. Удаляется только файл failed seq=0.

Факт (loss.json): после утраты corrupt=[], gate=true, выбран passed seq=2; после rebuild то же. Stale reused=1, passed=0, счётчик реальных попыток остаётся 3. Потеря истории превращает открытое обязательство в разрешение старого reuse. Нарушен AC-02.

Исправление: сверять все существенные компоненты состояния, сохранять свидетельства утраты при rebuild и резерв максимального seq; недоказанную историю блокировать или перезапускать. Добавить регрессию с несколькими неуспехами, у которых максимумы seq и finished_at принадлежат разным записям; проверить load/gate/stale/rebuild и восстановление покрытия новым реальным прогоном.
