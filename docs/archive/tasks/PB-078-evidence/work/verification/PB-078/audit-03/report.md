## A-03 — P2: rebuild теряет перекрытый утраченный nf после успешного восстановления

В `checks_results.rebuild_index` прежнее состояние сохраняется только при `_claim_unaccounted == True`. После покрывающего passed эта функция подавляет флаг утраты; rebuild заменяет состояние вычисленным только по сохранившимся файлам и уменьшает nf. Runner автоматически вызывает rebuild в конце execute (checks_runner.py:573), поэтому свидетельство исчезает сразу после успешного восстановления покрытия.

Это противоречит design §6 и EXEC-03/HANDOFF-03: уже перекрытые утраченные максимумы должны оставаться в состоянии и блокировать поздние passed с противоречащей меткой. Постоянный тест `test_a02_loss_without_winner_change_keeps_max` проверяет обновление индекса через store/update, но не вызывает rebuild между восстанавливающим passed и следующим прогоном.

Проба: `python3 work/verification/PB-078/audit-03/probe_healed_rebuild.py .`. Настоящие subprocess в временном проекте без Git; управляемый runner now, без изменения часов ОС и UUID. failed seq0/12:00, failed seq1/10:00, passed seq2/11:00; удаляется файл seq0. Утрата обнаружена и первоначальный rebuild корректно сохраняет её. Новый реальный passed seq3/12:00:01 восстанавливает gate, но автоматический rebuild уменьшает nf с 12:00 до 10:00. Passed seq4/11:30 теперь даёт gate=true, corrupt=[] (healed-rebuild.json).

Контроль: `python3 work/verification/PB-078/audit-03/probe_healed_control.py .` выполняет ту же последовательность, сохраняя файл seq0: nf остаётся 12:00 и тот же passed seq4/11:30 даёт gate=false (healed-control.json). Таким образом утрата записи меняет последующее покрытие при одинаковых исходах и часах.

Критерий исправления: отделить подавление corrupt после доказанного успеха от сохранения значимого состояния порядка. Rebuild, включая автоматический вызов runner, не должен терять сохранённые максимумы. Регрессия: утрата → восстановление успехом → rebuild → откат часов/новый passed; gate/stale/index должны оставаться согласованными с документированным контрактом.
