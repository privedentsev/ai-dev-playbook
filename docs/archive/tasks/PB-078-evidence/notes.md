## Адресные регрессии

- `tests/test_checks_run.py::Audit009PB78RegressionTest` — 9 тестов:
  seq-порядок при откате и согласованных часах, seq против legacy,
  консервативный равный `run_seq >= 0`, сохранённый legacy-порядок
  по `finished_at`, индекс/rebuild/свидетельство утраты, сквозной
  subprocess-счётчик с управляемыми часами и восстановлением новым
  passed, перекрывающиеся прогоны с различными `run_seq` (A-01
  аудита PB-078), утрата nf-компонента с раздельными максимумами
  seq/finished_at — с и без смены победителя, с исцелением
  passed и сохранением блокирующего nf (A-02 аудита PB-078).
- `tests/test_checks_gate.py::ProtectedLatestOutcomeTest` —
  protected-режим: квитанции упорядочены тем же состоянием порядка
  по `exec_seq`/`finished_at`; поздний failed остаётся актуальным,
  новый passed восстанавливает покрытие.

## Изменённый расчёт (раунд 2, после аудита A-01)

- Выбор последнего результата — состояние порядка
  `checks_select._choose_order_state` + `_merge_order_state` вместо
  парного `_latest_better`: `run_seq` — порядок резервации/старта
  исполнений, а НЕ завершения; при перекрывающихся прогонах seq=1
  может завершиться раньше seq=0 (проба аудитора A-01).
- Покрывающий `passed` принимается только когда `run_seq` строго
  больше `run_seq` любой непокрывающей seq-записи **и** `finished_at`
  не раньше метки любой непокрывающей записи (seq и legacy).
  Метка непокрывающего позже метки passed — доказанное противоречие
  → непокрывающий исход; равные метки не противоречат → решает
  `run_seq`. Равный `run_seq >= 0` — недоказанный порядок →
  непокрывающий исход; legacy-пара без `run_seq` упорядочена
  `finished_at`, при равной метке — непокрывающий исход.
- `checks_results` (индекс `order.v=1`, сверка `_claim_unaccounted`,
  rebuild) использует то же состояние — победитель индекса
  проверяется добавлением к сохранившимся записям; утрата
  seq-записи обнаруживается независимо от `finished_at`.
- `checks_gate._protected_receipts`: тот же `_choose_order_state`
  по pseudo-записям с `run_seq=exec_seq` — `exec_seq` есть порядок
  коммита квитанций в журнале, не доказывающий завершение
  перекрывающихся прогонов verifier'а.

## Изменённый расчёт (раунд 3, после аудита A-02)

- `_claim_unaccounted` больше не сверяет только верхнего победителя
  индекса: восстанавливается полное состояние `order.v=1` и
  проверяется воспроизводимость всех его свидетельств файлами
  (`_accounted_evidence`: result_id компонентов `pw`/`nw`/`lw`/`lnw`,
  `has_seq`, скалярные максимумы `ns`/`nf`). Индекс производный и не
  бывает «новее» файлов — любое невоспроизводимое заявление есть
  утрата/подмена, поэтому флаг не зависит от совпадения победителей:
  утрата `nf`-источника без смены исхода тоже обнаруживается, а
  rebuild не снимает блокирующий максимум. Подавление — только когда
  заявленный победитель сам является присутствующим на диске
  покрывающим `passed`: `_choose_order_state` возвращает его лишь при
  доминации над всем заявленным непокрывающим свидетельством,
  поэтому перекрытые утраченные максимумы исход не меняют; при этом
  `nf` сохраняется в состоянии и блокирует поздние passed с
  противоречащей меткой до passed с меткой не раньше `nf`.
  Устаревший, но не ложный индекс (заявленное воспроизводимо) corrupt
  не создаёт — PB-074 legacy-сценарии сохранены.
- `probe-loss-fixed.json` — повтор пробы аудитора A-02
  (`work/verification/PB-078/audit-02/probe_loss.py`): после удаления
  nf-источника `corrupt=['payment']`, gate закрыт, rebuild сохраняет
  свидетельство, stale реально перезапускает (attempts 3→4),
  passed с меткой не раньше `nf` восстанавливает покрытие.

## Изменённый расчёт (раунд 4, после аудита A-03)

- `rebuild_index` пересчитывал состояние только из файлов: после
  исцеления покрывающим passed `_claim_unaccounted` подавлял флаг,
  rebuild писал `nf` из файлов и терял перекрытый утраченный
  максимум — следующий passed с ранней меткой получал покрытие,
  невозможное при сохранённом файле (проба аудитора
  `probe_healed_rebuild.py`).
- Добавлен `_merge_claimed_blocking`: при пересборке блокирующие
  свидетельства прежней записи индекса (`has_seq`, скаляры
  `ns`/`nf`, компоненты `nw`/`lnw`) поднимают файловое состояние.
  Для честного устаревшего индекса заявленное ⊆ файлового — merge
  no-op; для утраченных перекрытых максимумов — сохранение.
  Покрывающие `pw`/`lw` не переносятся.
- Результат пробы на исправленном дереве:
  `probe-healed-rebuild-fixed.json` — `after_index.nf` остаётся
  `12:00`, исцеление `corrupt=[]`/`gate=true`, поздний passed
  `seq4/11:30` даёт `gate_ok=false` + `corrupt=['payment']`
  (согласовано с контролем `healed-control.json`, где история
  полна и `gate=false` по failed-победителю).
- Регрессия `test_a02_loss_without_winner_change_keeps_max`
  расширена: после исцеления явный `rebuild_index` сохраняет
  `nf=12:00`, последующий passed с меткой раньше `nf` снова
  открывает `corrupt`.

## Ограничения

- trust_mode=local — результаты диагностические; protected-граница
  OS/CI identity не подтверждается (как и прежде).
- Остаточная неоднозначность: равные `finished_at` у разных прогонов
  и перекрытие без противоречия меток разрешаются `run_seq` —
  при реальных часах с микросекундами совпадение меток
  маловероятно; задокументировано в design §6 и verification.md.
