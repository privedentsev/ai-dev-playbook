# PB-079 — проверка реализации

Исполнитель: Codex. Модель: GPT-6.1 Sol (Low).

A-07 воспроизведён настоящими verifier subprocess с валидными квитанциями на HEAD-модуле из временного каталога: passed→failed одного кандидата, исходный API gate ok=true ([before.json](before.json)). После исправления тот же сценарий даёт ok=false и реальный CLI rc=1 ([after.json](after.json)). История/подписи в этих пробах не редактировались. Стенд local, protected_confirmed=false; отдельная OS/CI identity не проверена.

Общий расчёт вынесен из checks_gate в checks_coverage.protected_receipts и используется обоими consumer. Источник — доверенный дом, не проектные копии. Порядок exec_seq/finished_at, исходные исполнения aggregate, TTL/always_run и task binding сохранены. Пропавшая выданная квитанция или непригодный журнал дают отказ; проектные подделки не создают и не отменяют доверие. Candidate/policy привязки квитанции дополнительно сверяются с доверенным журналом; объявленная политика должна совпадать с одобренной. У verifier gate добавлен --task; без проекции task-зависимое обязательство не покрывается. Manual остаётся вне эталонного consumer, а основной protected gate требует manual и доказанной identity для ok.

Постоянные тесты: tests/test_checks_verifier_gate.py — реальные signed passed→failed/timeout/blocked, CLI exit, восстановление, rename/delete проектных копий, несовместимый порядок завершения/выдачи, утрата/порча доверенного источника, порча журнала, candidate change, always_run, manual, task binding и CLI --task. Существующие ProtectedTtlTest и ProtectedLatestOutcomeTest теперь сравнивают покрытие обоих consumer: TTL/aggregate, равные часы, rollback. Сценарий несовместимого порядка задан метками последовательных реальных запусков; это не отдельный эксперимент с параллельными verifier subprocess. Остальная матрица checks включает race/overlap, replay/revocation, e2e/lifecycle/legacy.

Адресная проверка: 11 тестов, OK ([focused.log](focused.log)); 44 trust-теста, OK ([trust.log](trust.log)). Первый прогон матрицы checks: 360 тестов, два устаревших ожидания диагностики проектных файлов/replay; они согласованы с общим контрактом, отрицательное покрытие сохранено ([checks-initial.log](checks-initial.log)). Полный результат checks и штатного verify фиксируется в CHECK карточки. Независимая приёмка PB-079 и повтор AUDIT-009 остаются отдельными шагами; эта реализация их не заменяет. Commit/push не выполнялись.
