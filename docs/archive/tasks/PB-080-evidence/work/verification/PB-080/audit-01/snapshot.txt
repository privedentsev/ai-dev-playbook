## Задача

### Цель и границы

Устранить A-08 AUDIT-009: встроенный python-unittest адаптер не должен выдавать passed для изменённых исходников, исполнив старый timestamp-valid .pyc из исключённого __pycache__. Обеспечить связь фактического исполнения с текущим снимком; при недоказуемой связи — безопасный отказ. Архив PB-057–064/PB-073/PB-074/PB-078/PB-079 не переоткрывать и не переписывать. Код в сессии аудита не исправляется.

### Контекст

[AUDIT-009](AUDIT-009.md), [audit-05](../../work/verification/AUDIT-009/audit-05/report.md), [полный CLI-контрпример](../../work/verification/AUDIT-009/audit-05/probe_bytecode_cache_cli.py), [CLI-результаты](../../work/verification/AUDIT-009/audit-05/bytecode-cache-cli.json), [API-контроль и binding](../../work/verification/AUDIT-009/audit-05/bytecode-cache.json). Требования: [R-04/R-06/R-07/R-11/R-15, AC-02/AC-07](../specs/dependency-aware-verification.md).

Воспроизведение: `python3 work/verification/AUDIT-009/audit-05/probe_bytecode_cache_cli.py .`. Временный проект без Git, настоящий setup/apply и subprocess CLI, без mock/подмены отчётов/редактирования bytecode. Первый настоящий run генерирует обычный pyc для `value = 1`; затем исходник меняется на `value = 2` при прежних size/mtime. План видит изменённый SHA и выбирает run, reused=0, но второй тест наблюдает 1 и проходит; gate.ok=true, CLI rc=0. Удаление только этого временного cache и контрольный force на том же исходнике дают 2/failed/rc=1. Наблюдения [1,1,2]; binding.input_digest второго passed и контрольного failed одинаков. Это локальная надёжность исполнения, не заявленный обход реальной protected OS/CI границы.

Причина: checks_inventory исключает __pycache__ как service; checks_unittest.collect использует обычный Python child/env, а _load_suite импортирует модули без изоляции байткод-кэша. До/после хешируются новые исходники, хотя Python читает старый неучтённый cache. PYTHONDONTWRITEBYTECODE/-B сам по себе не доказывает отказ от чтения существующего кэша.

### Критерии приёмки

- [x] AC-01: В реальном CLI-сценарии source 1→2 при одинаковых size/mtime, неизменном тесте assert(value==1) и естественном кэше от первого run второй фактический run/stale/force не даёт passed по старому байткоду. Он исполняет текущий исходник и падает либо явно блокирует недоказанное исполнение; gate/status/handoff не объявляют готовность. Есть subprocess-счётчик/наблюдение actual=2; результаты/ожидаемые test IDs и counts не подделываются.
- [x] AC-02: Проверены кэши и проверяемых модулей, и самих тестов, прямые/пакетные импорты, предсуществующий __pycache__, обычный env и PYTHONDONTWRITEBYTECODE=1/-B, равные mtime/size и обычные изменения. Пользовательские кэши не удаляются автоматически; исключения не ослабляются ради успешного теста. Выбранная изоляция/контекст исполнения и ограничения для внешних зависимостей описаны явно.
- [x] AC-03: Старый unsafe passed, полученный предыдущим адаптером для неверно исполненного исходника, не становится пригодным доказательством нового контракта без нового фактического исполнения. Идентичность adapter/runner/контекста либо версия результатов обеспечивает безопасную миграцию; после успешного прогона нового корректного источника законный reuse, cross-task и release сохраняются. Покрытие local/protected не расширяется ложным утверждением; protected kind=test остаётся безопасно ограниченным.
- [x] AC-04: Пройдены адресные checks_unittest/run/gate/e2e и нужные legacy/lifecycle-регрессии, index/check/verify, self-manifest актуален после правок комплекта. Передача содержит новые доказательства, команды, среду и границы. Архивные доказательства побайтно сохранены; отдельный независимый аудит исправления предшествует повтору AUDIT-009.

### План

1. Прочитать audit-05, воспроизвести A-08 на CLI и сопоставить input_digest с фактическим источником исполненного кода; проверить текущую идентичность адаптера и возможность reuse прежних unsafe исходов.
2. Реализовать безопасный контекст выполнения/отказ с учётом исходников, тестов и bytecode, сохраняя policy/граф/каталог и пользовательские данные; добавить постоянные реальные регрессии.
3. Обновить документы, версионную/миграционную привязку и manifest; выполнить проверки и verify; записать EXEC/CHECK/HANDOFF для отдельного аудитора. После приёмки — повтор AUDIT-009.

### Ресурсы

Python stdlib, временные проекты вне репозитория, реальные unittest/CLI subprocess, осознанно сохранённые файловые mtime (системные часы не меняются). Бюджеты проекта null; длительность проверок оценить до полного запуска. Реальная отдельная OS/CI identity не подтверждена. Нет зависимости от незавершённой AUDIT-009. Commit/push/release — по отдельному поручению.
