## Задача

### Цель и границы

Граница доверия. Доверенный verifier/receipt adapter, deployment contract и тесты изоляции. Не получать доступ к аккаунтам и не настраивать production без отдельного поручения; выбор хостинга не навязывается.

### Контекст

[Спецификация](../specs/dependency-aware-verification.md): R-17–18,20; сценарии AC-07–08,11. [Design](../designs/dependency-aware-verification.md), [ADR-0006](../adr/0006-dependency-aware-verification.md), [план](../plans/dependency-aware-verification.md).

Подготовлено по поручению инженера 2026-11-07. Выполнение пока не разрешено. Перед стартом: принятие технического проекта, завершённые зависимости, актуальный card show/handoff затрагиваемых работ и назначение исполнителя. Исходные чужие изменения сохранять.

### Критерии приёмки

- [ ] AC-01: Реализовать verifier protocol и эталонный executor/consumer: одобренная policy, закреплённый runner, независимый пересчёт candidate, изолированный запуск, authenticated receipt. Клиентские результаты не подписываются как собственные.
- [ ] AC-02: Агент и тестовый процесс не имеют доступа записи к policy/history/ключам. Forgery/replay/cross-project/revocation/key replacement/local approved отклоняются; обычное расширение не разрешает новые недоверенные команды.
- [ ] AC-03: Инструкция реального OS/CI развёртывания и capability probe различают local/protected. Проверить реальную границу прав на доступном стенде; без неё зафиксировать ограничение и не объявлять защищённую эксплуатацию принятой.
- [ ] AC-04: Целевые поведенческие проверки и связанные регрессии пройдены; документация и self-manifest актуальны, EXEC/CHECK/HANDOFF содержат реальные доказательства и ограничения; передача зарегистрирована штатным CLI.

### План

1. Уточнить фактические интерфейсы зависимостей и связать изменения с критериями этой карточки.
2. Реализовать ограниченный объём, добавить постоянные позитивные и негативные проверки критериев AC-01–03; не подменять их структурной проверкой.
3. Обновить затронутые документы/шаблоны и self-manifest при изменениях комплекта; выполнить адресные проверки, index и check --ready.
4. Подготовить материалы и пройти действующие preflight/verify/handoff. До явного opt-in использовать прежний контракт; не отключать полный legacy suite ради экономии.
5. Записать EXEC/CHECK/HANDOFF и передать независимому аудитору; самостоятельно не закрывать.

### Ресурсы

Python и стандартная библиотека для основного CLI; локальные временные проекты и subprocess-счётчики. Новые зависимости защищённого executor обосновать в рамках принятого design. Фактические среда, policy_revision и бюджет фиксируются при старте; доступность отдельной OS/CI identity не предполагается.

Материалы: `docs/tasks/PB-061-evidence/`; команды воспроизведения и отчёты принадлежат этой карточке. Общие материалы и сквозная матрица — AUDIT-009/PB-064.

#### A-01 — Замечание
Серьёзность: P1
Критерии: AC-01, AC-02, AC-04
Проблема: verifier подписывает отчёт, который может целиком подделать недоверенный тестовый процесс. В checks_unittest.collect читается доступный этому процессу adapter.json; закреплённый путь скрипта не защищает происхождение событий.
Воспроизведение: запустить probes.py; ветка FORGED_ADAPTER заменяет tests/test_payments.py модулем без тестов, который при discovery берёт --out из sys.argv, пишет ожидаемый/фактический ID из одобренного каталога со статусом passed и завершает процесс os._exit(0).
Факт: run_ok=true, signature_ok=true, gate_ok=true при отсутствии определённых и выполненных тестов; sandbox-exec реально включён. Приём fabricated report происходит в checks_unittest.py:263–272, его подпись — checks_verifier.run.
Влияние: агент превращает клиентские выдуманные результаты в собственную authenticated receipt verifier; AC-01 и граница доверия обходятся без доступа к ключу.
Критерий исправления: исключить доверие к подменяемому тестовым процессом итоговому отчёту; обеспечить доказанное происхождение результатов либо блокировать защищённое подтверждение для такого adapter. Добавить негативный тест discovery→поддельный отчёт→os._exit(0): подписанный passed и положительный gate недопустимы.

#### A-02 — Замечание
Серьёзность: P1
Критерии: AC-02, AC-03, AC-04
Проблема: probe выводит separate/protected из неудачи создания marker только в корне home; не проверяет права на ключи/approved/history, возможность владельца менять права и работоспособность изоляции. Любой OSError считается доказательством отсутствия записи.
Воспроизведение: probes.py, ветка PROBE: обычный дом под тем же UID вне проекта, успешный прогон, chmod(home, 0555); открыть существующий keys/*.key на запись и вызвать probe/gate.
Факт: key_writable=true одновременно с capability=protected, agent_can_write=false и protected_confirmed=true. Владелец также свободно возвращает chmod 0755. Ошибочный вывод находится в checks_trust.py:388–408.
Влияние: локальная среда с подконтрольными агенту ключами объявляется защищённой; нарушен явный запрет R-20.
Критерий исправления: не выводить OS/CI boundary из одного marker; проверять реальную независимую identity, защиту чувствительных файлов/предков и изоляцию тестового процесса. При недоказанности возвращать local; добавить негативные проверки read-only корня с доступными ключами и ошибок probe, не связанных с правами.

#### A-03 — Замечание
Серьёзность: P2
Критерии: AC-01, AC-02, AC-04
Проблема: checks_runner.execute перезаписывает аргумент env результатом binding_environment на строке 346 и передаёт эту идентичность среды в subprocess на строках 480/484; scrub_env verifier не используется. Ошибка затрагивает и обычный runner.
Воспроизведение: probes.py, ENV печатает фактическое окружение subprocess; EXTERNAL_EXCEPTION запускает валидную политику с required_environment=['api'] и freshness=always_run.
Факт: HOME/TMPDIR/PATH отсутствуют вместо значений arena; в env попадает platform. С required_environment процесс падает с TypeError: expected str, bytes or os.PathLike object, not dict, поскольку external:api имеет значение dict.
Влияние: изоляция окружения не соответствует контракту; проверки с TTL/always_run не запускаются и не получают контролируемого результата.
Критерий исправления: разделить окружение процесса и binding identity; передавать scrubbed env только защищённому запуску и сохранять прежнее наследование обычного runner. Поведенчески проверить HOME/TMPDIR внутри arena, PATH и запуск с ttl/always_run.

#### A-04 — Замечание
Серьёзность: P1
Критерии: AC-01, AC-02, AC-04
Проблема: verify для aggregate не проверяет доверие к source_receipts; отзыв исходной квитанции не распространяется на подтверждения, переиспользовавшие её результаты.
Воспроизведение: probes.py, REVOCATION: run→aggregate→revoke исходного receipt; удалить только публичную копию отозванного оригинала из проекта, оставив aggregate; вызвать verify/gate.
Факт: original_ok=false, aggregate_ok=true, gate_ok=true. checks_verifier.verify:324–338 проверяет лишь текущую квитанцию, не её источники; исходные результаты при aggregate не исполнялись заново.
Влияние: результаты отозванного запуска продолжают подтверждать кандидата через агрегат; отзыв доверия обходится удалением недоверенной публичной копии.
Критерий исправления: проверять доверенные источники агрегата и их актуальные отзывы транзитивно либо отслеживать зависимые подтверждения в доверенном журнале; отозванный источник не должен покрывать обязательства через агрегат. Добавить проверку цепочки run→aggregate→aggregate и отзыва источника.

#### A-05 — Замечание
Серьёзность: P2
Критерии: AC-03, AC-04
Проблема: _home_writability передаёт сами существующие каталоги home, home.parent и keys в _writable(append=False); os.open с O_CREAT|O_EXCL проверяет существование пути и получает EEXIST, а не проверяет право создать файл внутри каталога (checks_trust.py:366,382–385).
Воспроизведение: probes.py, DIRECTORY_WRITABILITY: вызвать _home_writability для валидного дома. Отдельно chmod 0555 существующего каталога и os.open(catalog, O_WRONLY|O_CREAT|O_EXCL, 0600) также возвращает FileExistsError/EEXIST.
Факт: значения «дом», «родительский каталог», «ключи» равны null. Даже при отсутствии writable_points остаются unknown_points, agent_can_write=None, а protected требует agent_can_write=False. Probe не может положительно подтвердить доступную корректную границу прав через этот путь.
Влияние: исправление ложного protected сделало проверку каталогов неработающей; capability не различает подтверждённую независимую границу и ошибку её измерения.
Критерий исправления: проверять создание уникального безопасного marker внутри каждого каталога, удаляя только собственный marker; EACCES/EPERM учитывать как отказ прав, прочие ошибки — как неизвестность. Добавить поведенческие проверки доступного и недоступного для записи каталога; при доступном стенде проверить положительный protected с независимой identity. Отсутствие стенда явно сохранить как ограничение.

Для `python-unittest` происхождение исходов недоказуемо в принципе — тестовый код исполняется в том же процессе и читает любой канал (файл, stdout, ack из stdin), поэтому ack-протокол принципиально не защищает результат. `checks_verifier.run` теперь отклоняет политику с исполняемыми `kind=test` проверками до исполнения: квитанция не выпускается, gate остаётся непокрытым, подделанный «валидный» отчёт не может стать passed. Дополнительно `verify` разрешает каждый результат квитанции в хранилище дома по digest и отклоняет `kind=test` — квитанции, выпущенные до блокировки run, тоже не проходят (ретро-отклонение). Поведенческие тесты: marker создаётся и удаляется, chmod 0555 → False, EIO → None, probe доступного дома заполняет writable_points и не оставляет marker'ов; защищённость без отдельной identity не заявляется (capability=local).
