# Руководство пользователя ai-dev-playbook

`ai-dev-playbook` помогает организовать работу AI-агента над проектом: от обсуждения идеи до реализации, проверки и независимой приёмки.

Это руководство объясняет, как пользоваться комплектом. Внутренние правила для агента находятся в `ai-dev-playbook/rules/`, документы разработки самого комплекта — в остальных разделах `docs/`.

## Содержание

- [Режимы работы](modes.md) — восемь режимов, примеры запросов, результаты и переходы между этапами.

## Как поддерживается руководство

Исходники страниц хранятся здесь в Markdown. При добавлении сайта эти же файлы должны использоваться для его сборки, без отдельной копии текстов. Сейчас сайт и его публикация не настроены.

Руководство описывает действующие правила и не заменяет их. При изменении пользовательского процесса нужно обновлять соответствующую страницу вместе с правилами.

Этот раздел относится к репозиторию разработки playbook и не входит в шаблоны документов, создаваемые при подключении комплекта к другому проекту.

## Карточки для человека и приложения

Новые карточки — Markdown формата 2: задача с критериями AC-ID, вычисляемыми чекбоксами и журнал EXEC/CHECK/HANDOFF/AUDIT. Исправление — следующая EXEC-запись; передача ссылается на работу и проверки. Приёмку подтверждает acceptance, отдельный чекбокс аудита не нужен. [Формат и пример](../../ai-dev-playbook/rules/task-card-format.md).

Просмотр: `python3 ai-dev-playbook/scripts/playbook.py card show PB-040`; для приложения добавьте `--json`. Старые/будущие неподдерживаемые версии возвращают путь Markdown. Архив не мигрируется. Исторический accepted не означает текущую приёмку; приложение получает acceptance_state и причину неактуальности.

Галочка критерия подтверждает актуальную проверку, а не независимую приёмку. `card sync PB-040` показывает пересчёт, `card sync PB-040 --apply` сохраняет его. Handoff и accept обновляют отметки автоматически; check обнаруживает ручные/устаревшие отметки. После замечания аудита укажите затронутые AC-ID и выполните sync; вернуть галочку можно после исправления, новой проверки и закрытия находки повторным аудитом.

## Компактный контекст задачи

Начинай чтение задачи с `python3 ai-dev-playbook/scripts/playbook.py card show <ID>`: требования, актуальная передача/приёмка, открытые замечания и указатель записей. Передача вместе с исходными EXEC/CHECK и открытыми находками: `card show <ID> --handoff` (также `--json`); неподтверждённая передача и новая работа показаны явно. Подробности: `card show <ID> --entry EXEC-01` (также CHECK/HANDOFF/AUDIT и A-ID); полная история без служебного JSON — `--full`, полный структурированный контракт — `--json`. Вывод показывает команды продолжения; нужные доказательства читать по ссылкам выбранных записей. Неподдерживаемый формат возвращает путь Markdown. Аудитор самостоятельно выбирает проверки по требованиям и рискам; указатель не ограничивает область аудита. Полный файл можно читать при необходимости. Не перечитывай историю и неизменившиеся документы без причины.

Порядок одинаков для Codex, Antigravity и Claude Code; точки входа этих инструментов должны ссылаться на общие правила, а не содержать отдельные копии процесса. CLI читает файлы локально; в контекст агента попадает только выведенный текст.

## Внешнее хранение метаданных новых карточек

Новая карточка создаётся командой `python3 ai-dev-playbook/scripts/playbook.py card create <ID> --title "Название" --apply`; без `--apply` — preview. Создаются `<ID>.md` и соседний `<ID>.meta.json`, обновляется индекс одной восстанавливаемой операцией. Для команды требуется настроенный раздел documents. При ручном использовании шаблона необходимо копировать оба файла (`templates/task.md` и `templates/task.meta.json`), согласовать ID/имя Markdown и заполнить Created.

Маркер `<!-- playbook-meta:external -->` в шапке Markdown указывает на обязательный соседний JSON. JSON содержит прежние служебные метаданные, без копии шапки, требований и журнала. Разбор/валидация, verify, sync, handoff/accept и close/reopen читают одну пару; перенос в архив включает оба файла. JSON не является evidence или кэшем. Потеря/повреждение, symlink, orphan и два источника — ошибки, не основание для пустого состояния. Существующие inline/legacy-карточки продолжают работу без миграции; весь архив не переписывается. Не перемещайте и не редактируйте служебное состояние вручную.

## Завершение без повторного verify из-за статуса

До финального прогона заверши EXEC, документы и регистрацию материалов, подготовь Status: in_review и индекс; затем check --ready и verify. После passed допиши CHECK и самостоятельную HANDOFF, зарегистрируй передачу. Подготовленный статус не означает готовность к аудиту; при failed/stale работа продолжается. [Точный порядок](../../ai-dev-playbook/rules/verification.md#подготовка-финального-verify), [содержание записей](../../ai-dev-playbook/rules/task-card-format.md#журнал). Старые записи не сокращаются.
