## План: компактное чтение карточек и внешние метаданные

Согласовано инженером 2026-10-25. Работа независима от PB-040; существующая карточка не изменяется. Инженер отдельно разрешил реализацию 2026-10-25. Требования: [спецификация](specs/compact-task-context.md), решение: [design](designs/compact-task-context.md), выполнение: [PB-041](tasks/PB-041.md). Отдельная заметка обсуждения не требуется: согласованный объём сохранён здесь.

1. Вынести служебный JSON новых карточек в соседний `<ID>.meta.json`. Видимые поля шапки, требования и журнал остаются в Markdown; каждый факт имеет один источник. Смысл и гарантии существующих метаданных сохраняются, сокращение схемы и перепроектирование механизмов в объём не входят.
2. Расширить существующий `card show`: компактный вход содержит требования, план, актуальность передачи/приёмки, открытые замечания и ссылки на актуальные EXEC/CHECK/HANDOFF/AUDIT. Подробности доступны по ID записи, включая находки. CLI читает исходные файлы целиком, но передаёт агенту только выбранное представление; ручной файл сводки не создаётся. Полная история остаётся доступной.
3. Уточнить шаблоны и правила новых записей: EXEC описывает изменения, CHECK — фактические проверки и ограничения, HANDOFF связывает результаты и задаёт фокус аудита, AUDIT содержит независимые выводы. Между записями используются ссылки по ID вместо повторного пересказа; обязательные поля и достаточность доказательств сохраняются. Старую историю не переписывать.
4. Согласовать чтение через CLI в общих правилах и точках входа используемых агентов (Codex, Antigravity, Claude Code). Начальный вывод показывает доступные ID и команды продолжения; область независимого аудита этим выводом не ограничивается. Прямое чтение Markdown допускается при необходимости.
5. Подключить внешний JSON к созданию, валидации, индексированию, verify/freshness, handoff/accept, close/reopen, установке и обновлению. Обновление пары и её перенос выполняются существующим восстанавливаемым механизмом; JSON не является immutable-доказательством. Отсутствие/повреждение обязательного файла, конфликт встроенных и внешних метаданных, частичный перенос и восстановление должны иметь явное безопасное поведение.

### Совместимость и проверки

- Новое хранение применяется к новым карточкам после внедрения. PB-040, существующие активные карточки (включая PB-031–PB-037) и архив не требуют массовой миграции. Версия Markdown и способ хранения метаданных различаются.
- Существующие карточки со встроенным JSON и legacy-карточки продолжают выполнение, проверку, передачу, приёмку, закрытие и reopen по своим поддерживаемым правилам. Совместимость не освобождает от актуальных проверок и приёмки; изменение входов реализации может потребовать нового verify/handoff.
- Опциональная миграция, если потребуется, выполняется только явной восстанавливаемой операцией без двух действующих источников. Удаление встроенного блока — часть успешного переноса, а не отдельная ручная правка.
- До приёмки проверить смешанный проект: legacy, встроенный JSON и внешний JSON; полный цикл verify → handoff → accept → close → check → reopen → повторное закрытие. Проверить относительные ссылки, сохранность immutable-доказательств, отказы при конфликте/потере JSON и восстановление после прерывания. Старые реальные карточки проверять на временной копии без их закрытия в рабочем проекте.
- Проверить согласованность с незавершённым блоком PB-031–PB-037, особенно интеграцией lifecycle PB-034 и обновлением PB-036; границы и зависимости уточнить при постановке, порядок блока автоматически не менять.
- Сравнить полный Markdown и компактный вывод на синтетической многоитерационной карточке: объём входного контекста и достаточность для продолжения работы/аудита. Экономию токенов измерить, заранее процент не обещать.

Следующий шаг: реализация согласованного объёма в PB-041, затем независимый аудит. Текущие статусы задач остаются в карточках и индексе задач.

## Выборочные файловые операции и ограниченная история

Выполнение ожидает отдельного поручения; статусы только в карточках. Приёмка локальными временными сценариями, без обязательного пилота на реальном большом проекте.
