## Цель и границы

Сократить контекст восстановления работы без изменения гарантий проверки и приёмки. Основание: согласованный запрос инженера в текущем обсуждении 2026-10-25 и разрешение выполнения. Изменения не зависят от PB-040; существующие карточки не изменяются и не мигрируются.

## Требования

1. Новые карточки создаются парой `<ID>.md` и `<ID>.meta.json` одной восстанавливаемой операцией. В Markdown — шапка, требования, журнал и однозначный маркер внешнего хранения. В JSON — прежние служебные метаданные без копий видимых полей и текстов. Схема и смысл гарантий сохраняются.
2. Чтение поддерживает legacy, встроенный JSON и внешний JSON одновременно. Отсутствующий/повреждённый sidecar, symlink, два источника, orphan sidecar и занятое назначение вызывают отказ. Неподдерживаемый формат сохраняет Markdown fallback. Миграция существующих карточек не входит в объём.
3. `card show ID` выводит требования/план, актуальное состояние и указатель записей: последнюю передачу, последнее выполнение/проверку/аудит, открытые находки и связанные исправления. Вывод различает историю accepted и действующую CLI-приёмку, не скрывает работу после передачи. `--entry ID` возвращает полную запись или находку, `--full` — весь Markdown без служебного JSON. `--json` сохраняет прежний полный структурированный контракт; с `--entry` возвращает выбранную запись. Команды из текста никогда не исполняются; просмотр ничего не записывает.
4. Регистрация материалов, sync, verify/freshness, handoff/accept и close/reopen используют одно чтение метаданных. Все изменения пары и переносы выполняются существующим engine с общей блокировкой, staged/final checks и восстановлением. Sidecar не регистрируется как доказательство. Сохраняются защита истории и побайтовая неизменность immutable-доказательств.
5. Шаблон и CLI создания новых задач используют внешнее хранение. Установка/обновление распространяют нужные ресурсы, совместимость старых проектов сохраняется. Документы и точки входа агентов задают единый порядок чтения и допускают полный просмотр при необходимости.
6. Новые EXEC/CHECK/HANDOFF/AUDIT сохраняют обязательные поля, но не пересказывают друг друга; ссылки по ID заменяют повторы. История существующих карточек не редактируется. Независимый аудит сам выбирает область проверки.

## Проверки и приёмка

Постоянные тесты смешанного проекта, создания/preview/read-only, выбора записи и находки, работы после передачи; сохранности и отказов хранения. Полный сквозной цикл с относительными ссылками и evidence: verify/handoff/accept/close/check/reopen/повторное закрытие. Прерывание/ошибка записи восстанавливает оба файла. Проверить старый inline/legacy lifecycle прежними тестами, свежесть после изменения реализации, конфликт источников и сохранность байтов доказательств. Проверить установку и обновление. Экономию измерить на синтетической многоитерационной карточке по символам/байтам; токены заявлять только при доступном токенизаторе. Итог передаётся независимому аудитору.
