## Статус и границы

Требования согласованы; выполнение PB-044–PB-050 разрешено инженером 2026-10-28. Полный новый контракт остаётся планируемым до реализации и индивидуальной приёмки соответствующих этапов; состояние — в карточках. Исходная подготовка: Codex / GPT-6 Astra. Общий аудит блока инженер запустит самостоятельно.

Цель: ограничить подготовку и резервирование файлами конкретной операции, сохранить предварительные проверки и восстановление, прекратить бессрочное накопление рабочих копий. [Design](../designs/scoped-file-operations.md), [ADR-0005](../adr/0005-scoped-file-operations.md), [план](../plans/scoped-file-operations.md).

## Действующее поведение

`file_operations._prepare_staged` копирует проект с исключениями и дополнительно work/verification; затем применяет write-set и запускает staged-проверки. Backup уже ограничен затрагиваемыми путями. Engine сохраняет gate, pending, журнал, хеши, режимы доступа и автономный restore. `updating._stage_project` отдельно копирует проект, а `_run_staged_checks` запускает настроенные проверки продукта в копии. `find_completed` ищет квитанции по plan_id. Автоматический лимит истории и описанный ниже просмотр будущего состояния пока отсутствуют.

Git хранит закоммиченные версии. Backup операции сохраняет непосредственный пред-образ, включая незакоммиченные файлы. CLI не использует git reset/checkout как восстановление и не делает автоматических коммитов.

## Планируемые требования

| ID | Требование |
|---|---|
| R-01 | Документная операция явно описывает записи, удаления, перемещения, создание/удаление каталогов и зависимости чтения. Границы задаются конфигурацией и зарегистрированными материалами; пути не ограничиваются жёстко docs/. |
| R-02 | На диске staged хранятся только подготовленные новые версии затрагиваемых файлов. Код продукта, зависимости, ресурсы и вся work/ не копируются для операции документов. Потребление памяти ограничено буфером обработки и метаданными, без загрузки крупных материалов целиком. |
| R-03 | Предварительная проверка получает новые версии из staged, неизменяемые данные из проекта, удаления как отсутствие, перемещения по конечным путям. Проверяет карточки и sidecar, каталог, статусы, ссылки, индексы и защищённые материалы. При ошибке основные файлы не изменяются. |
| R-04 | Снимок входов содержит хеши прочитанных файлов, отсутствующие пути и состав просмотренных каталогов/коллекций. Добавление новой карточки или ссылки во время подготовки также делает план устаревшим. Сверки выполняются до backup и после его подготовки непосредственно перед записью. |
| R-05 | Поздний backup покрывает все перезаписываемые/удаляемые оригиналы, отсутствие создаваемых путей и состояние каталогов/прав. До первой записи проверены состав, хеши и соответствие исходному снимку; данные восстановления сохранены на диске. |
| R-06 | Применяются только запланированные изменения; итоговые хеши совпадают с проверенными staged-версиями, отсутствующие пути и каталоги соответствуют плану, структурные проверки повторены. Повреждение staged после проверки не может быть принято как успех. |
| R-07 | Сохраняются shared gate, порядок блокировок, pending, журнал, безопасные временные имена и автономный restore. Ошибка после записи вызывает восстановление; прерывание оставляет pending. Неполный откат, повреждённый backup или неизвестная фаза блокируют продолжение. Повторное восстановление безопасно. |
| R-08 | Чужие правки при восстановлении не уничтожаются: сохраняются как конфликт. CLI показывает причины удержания данных и действия для восстановления/разбора. Объявление конфликта разобранным возможно только явным подтверждением после сохранения нужных данных. |
| R-09 | storage.backup_retention_count в project.json — обязательное положительное целое (bool не число); отсутствие, null, строка, 0, отрицательное/дробное значение — ошибка без изменения проекта. Ни скрытого значения по умолчанию, ни unlimited. В шаблон и self-project при реализации записывается 15. |
| R-10 | Единый лимит N=15 действует на завершённые операции lifecycle и update вместе. Успешные и полностью восстановленные операции занимают одно место независимо от количества файлов. Порядок — время завершения, при равенстве op_id. Старые каталоги удаляются целиком: backup, журнал, квитанция, скрипт. |
| R-11 | Staged удаляется сразу после подтверждённого успеха или восстановления. Отмена до первой записи также убирает подготовку; если backup ещё не было, не создаёт долговечной истории. Незавершённое восстановление и неразобранные конфликты защищены и не вытесняют последние N обычных операций. |
| R-12 | Очистка имеет read-only preview, явный apply и автоматический запуск после безопасного завершения операции. Ошибка очистки не превращает успешную предметную операцию в failed и не вызывает её rollback; возвращается completed с предупреждением и возможностью повторить cleanup. Прерванная очистка возобновляема. |
| R-13 | Старый сохранённый план после удаления истории не может быть применён заново. Отсутствие квитанции не означает новый запрос. Новый запрос строит новый план; уже достигнутый и проверенный результат даёт no-op. Повтор известного плана проверяет фактическое состояние, а не только прежний receipt. |
| R-14 | Диагностика/restore доступны при отсутствующей новой настройке. Миграция существующей установки явно записывает 15 только при отсутствии параметра, сохраняет корректное пользовательское значение, отклоняет некорректное. Это версия миграции, не runtime-default. Для уже запущенного нового CLI предусмотрена явная команда установки настройки. |
| R-15 | Update также прекращает полное копирование проекта: проверяет кандидатный комплект/миграции и будущую документацию в ограниченной области. Продуктовые проверки verification не запускаются скрыто на основном проекте как часть восстановления update. Новый контракт явно отделяет структурный успех обновления от результата verify продукта. |
| R-16 | Старые backup/pending восстанавливаются прежним автономным скриптом или совместимым новым restore. Старые сохранённые планы перед переходом пересоздаются. Исторические каталоги очищаются только после явной классификации preview; неизвестные, повреждённые и используемые как доказательства данные не удаляются автоматически. |
| R-17 | Cleanup не удаляет tests, docs/tasks/*-evidence, архивные доказательства или work/verification. Новые долговечные ссылки/доказательства не привязываются к очищаемым каталогам операций: нужный отчёт сохраняется владельцу до финальной передачи. Для прежних ссылок показывается блокирующая очистку причина и путь материала. |
| R-18 | Реальный большой проект, внешний сервис, CI в чужом проекте, выделенный стенд и числовой SLA скорости не являются критериями приёмки. Достаточны воспроизводимые локальные временные проекты, синтетические данные и fault injection. Проверяется отсутствие полного обхода/копирования посторонних данных; скорость не обещается по микрозамеру. |

## Сценарии и критерии приёмки

| Критерий | Наблюдаемый результат и проверка | Требования |
|---|---|---|
| AC-01 | Архивация карточки с sidecar, индексами и входящей ссылкой: staged содержит только результат операции, чужие src/media/node_modules не читаются массово, не копируются и побайтно не меняются. | R-01–03 |
| AC-02 | Предварительная проверка ловит битую ссылку, коллизию пути и неверные метаданные до backup/записи; будущие удаления не подменяются существующим оригиналом. | R-03 |
| AC-03 | Изменение прочитанного документа, появление новой карточки и изменение оригинала во время backup отклоняют план; испорченный staged не применяется. | R-04–06 |
| AC-04 | Ошибка записи/финальной проверки, реальный SIGKILL и повторное прерывание restore восстанавливают байты, состав, права; коррупция backup и чужой pending сохраняют блокировку. | R-05–08 |
| AC-05 | Матрица настройки: missing/bool/null/строка/0/negative/fraction отвергаются; 15 и другое положительное значение принимаются; legacy migration, init, self-project и путь ремонта проверены. | R-09,14 |
| AC-06 | 16+ смешанных lifecycle/update операций оставляют последние 15 обычных; pending/conflicts и защищённые доказательства сохранены с причинами. Staged отсутствует у терминальных операций. | R-10–12,16–17 |
| AC-07 | Сохранённый старый план после очистки, его внешняя копия и подмена файла отклоняются; fresh-запрос и no-op работают; повтор после изменения результата не сообщает ложный already_completed. | R-13 |
| AC-08 | Cleanup preview не пишет; гонка apply/restore/cleanup не повреждает состояние; сбой/прерывание очистки не отменяет завершённую операцию и не активирует истёкший план. | R-07,12–13 |
| AC-09 | Обновление локального legacy-артефакта переносит настройку, проверяет кандидатный CLI, сохраняет recovery; посторонние файлы не копируются, произвольные продуктовые команды не запускаются скрыто. | R-14–16 |
| AC-10 | Локальный сквозной цикл index/create/close/reopen/update/cleanup и регрессия повторной генерации индекса проходят; текущие тесты и независимый аудит дают проверяемые отчёты без внешнего пилота. | R-01–18 |

## Влияние и ограничения

Изменяет предварительную подготовку в [действующей спецификации](workflow-and-document-lifecycle.md) и [design](../designs/workflow-and-document-lifecycle.md), уточняет [ADR-0002](../adr/0002-recoverable-lifecycle-operations.md). Старое описание остаётся действующим до реализации и отдельной приёмки; ADR-0002 сейчас не архивировать.

При реализации обновить правила update/verification, пользовательское руководство, архитектуру/карту кода, шаблон project.json и миграции. Результат нового update — проверка комплекта; passed продуктовых тестов подтверждается отдельным verify. Многофайловая запись не атомарна; внешние редакторы не блокируются, остаётся окно между последней сверкой и записью. Сбой питания и аппаратная порча не считаются автоматически доказанно покрытыми тестом SIGKILL. Лимит количества операций не является лимитом байтов одного backup.

Следующий этап подготовки выполнен в связанном design и плане. Выполнение PB-045–PB-050 разрешено поручением инженера 2026-10-28; AUDIT-008 оставлен инженеру.
