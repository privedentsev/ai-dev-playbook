## Статус и основание

Подготовлено 2026-11-07 по поручению инженера «подготовим все необходимое для реализации этой задачи так, как обсудили». Сохранены договорённости обсуждения; документы и карточки — проект реализации, не действующая политика. Технические решения и границы первого выпуска требуют принятия перед стартом. Кодирование, включение режима, commit/push/release этим поручением не разрешены.

Цель: автономный выбор необходимых проверок с проверяемыми результатами вместо решения агента «этого достаточно». Обычные задачи проверяют затронутый функционал; релиз требует весь обязательный набор актуальных успешных результатов, а не обязательно новый полный прогон.

[Design](../designs/dependency-aware-verification.md), [ADR-0006](../adr/0006-dependency-aware-verification.md), [план](../plans/dependency-aware-verification.md).

## Действующее поведение и отличие

Проверено по текущим verification.py, verification_policy.py и project.json. V2 уже содержит registry, applicability always/when_paths/checkpoint, default_inputs, снимки, coverage, выборочное reuse и lifecycle gates. Снимки применимости уже независимы от Git. Существующий v2 требует task-план, ссылающийся на обязательные registry IDs; он не строит автоматически граф модулей и семантическое покрытие тестами. Поиск reusable v2 ограничен задачей. Command-results проверяют запуск процесса, но не универсальный достоверный список тестов. Локальные метаданные не аутентифицируют инженера и не защищены от владельца файлов.

Self-project всё ещё использует legacy: self-check, preflight-regressions и полный unittest discover; task_workflow не включён. Новый контракт нельзя применять к этим задачам до явной миграции. Прежние принятия PB-031–037 не переоткрываются этой подготовкой.

## Планируемые требования

| ID | Требование |
|---|---|
| R-01 | Существуют версионированные определения модулей, подсистем, групп проверок, команд, входов и зависимостей; история результатов отделена. Стабильный ID отделён от понятного названия и описания проверяемого поведения. |
| R-02 | При настройке CLI обследует проект без Git, обнаруживает тесты поддерживаемым адаптером и предлагает конфигурацию. Предварительная карта не считается одобренной политикой. Начальная политика принимается инженером вне полномочий агента. |
| R-03 | Автоматический анализ зависимостей, явные связи ресурсов/API/конфигурации и наблюдения тестов объединяются. Наблюдения могут расширять, но не сужать статическую/явную карту. Версия анализатора и происхождение связи сохраняются. |
| R-04 | Учитываются транзитивные потребители, общие тестовые файлы, конфигурация, зависимости сборки, удалённые и новые связи. Циклы допустимы и обрабатываются без зацикливания. Динамические/неподдержанные зависимости обозначаются unknown, не как отсутствие влияния. |
| R-05 | Без Git отслеживаются состав каталогов, добавления, удаления, переименования как delete/add и SHA-256 учитываемых файлов; mtime/size не заменяют хеш. Ручная правка обнаруживается так же, как правка агентом. Потеря baseline приводит к консервативному выбору. |
| R-06 | Входы задаются по роли. Код, тесты, конфигурация, lockfiles, ресурсы и содержательные требования учитываются связанными проверками. Карточки/картинки/архивы не исключаются целиком по расширению; служебная запись в карточке не отменяет независимый продуктовый результат. |
| R-07 | Глобально исключаются только одобренные служебные пути с причиной. .gitignore не является политикой. Коллизия исключения с объявленным/обнаруженным входом — ошибка. Новые файлы в известном модуле наследуют правила; неизвестные классифицируются или вызывают расширение. |
| R-08 | Применимость и актуальность вычисляются раздельно. Выбор набора: задача — фактические изменения плюс сценарии приёмки; релиз — весь обязательный набор; явный all/force — весь запрошенный набор заново; stale — только обязательства без пригодного успешного результата в явно указанной области. |
| R-09 | Автономный fallback: модуль и потребители → подсистема и её потребители → весь проект при недоказанной границе влияния. Расширение объясняется. Оно не обесценивает доказанно независимые результаты; неизвестные связи инвалидируют потенциально зависимые, вплоть до всех. Полный fallback не доказывает наличие тестов нового поведения. |
| R-10 | Перед запуском вычисляются лимит времени/ресурсов и план. При превышении одобренного бюджета либо невозможности оценить дорогой fallback без разрешённого лимита требуется решение инженера; результат остаётся blocked, не passed. Точный бюджет задаётся при подключении, не выдумывается агентом. |
| R-11 | Reuse допускается только для успешного валидного результата с совпадающими значимыми входами, командой, адаптером, политикой, графом и средой. Для внешних систем — явная политика свежести (версия/TTL/always_run); неизвестная среда исключает reuse. Более поздний failed/timeout/неполный запуск для того же обязательства не скрывается старым passed. |
| R-12 | Повторное использование между задачами и при релизе возможно в пределах одной идентичности проекта/доверенного контура. Задачные требования учитываются отдельно; отсутствие task-specific доказательств нельзя закрыть глобальным результатом. История хранит provenance и причины reuse/run/blocked. |
| R-13 | Runner сам обнаруживает и исполняет ожидаемый набор тестов через адаптер; сопоставляет IDs/count/outcomes, ловит нулевой запуск, дубликаты, неожиданное исключение/skip, недописанный отчёт. exit 0 без требуемых доказательств не даёт passed. Для линтера/сборки действует отдельный тип command, без выдуманного количества тестов. |
| R-14 | Группа имеет понятное назначение, тест — стабильный ID и описание условия/ожидания. Отчёт различает passed, failed, reused, not_run, not_applicable, blocked и показывает причину. Существующие тесты мигрируют явно; описание не считается доказательством достаточности assertions. |
| R-15 | Результат связан с проверенным снимком. Входы не меняются для команды во время запуска: доверенный контур использует изолированный кандидат; локальный режим минимум сверяет до/после и явно сообщает более слабую гарантию. Перед передачей и release-ready текущий кандидат сверяется повторно. |
| R-16 | Готовность задачи/релиза требует всех применимых успешных доказательств и разрешённых ручных обязательств. Структурная проверка карточки не подменяет поведение CLI, ручное заявление не превращается в автоматическое доказательство. Коммит сам по себе не запускает повтор и не разрешает выпуск. |
| R-17 | Доверенная политика и подтверждения выполнения находятся вне записи агента. Команды тестов также не получают ключей/прав изменения доверенных данных. Подписанная/аутентифицированная квитанция привязана к project_id, candidate, политике, runner/adapter и результатам. Подмена/повтор для другого состояния/отзыв доверия отвергаются. |
| R-18 | Автоматическое расширение связей/контроля разрешено в пределах одобренных команд и бюджета. Ослабление исключений, удаление/отключение проверок, расширение допустимых skip, удаление значимых связей, изменение доверенного runner/политики требуют отдельного решения инженера. Поле approved в редактируемом JSON не является авторизацией. |
| R-19 | Обновление opt-in, версии схем/отчётов распознаются строго; legacy и v2 без новой настройки сохраняют поведение. Старые отчёты без нужных доказательств не становятся доверенными автоматически. Новые настройки применяются через preview/apply/recovery. |
| R-20 | Локальный режим доступен для разработки, но не называется защитой от намеренной подмены владельцем файлов. Защищённая готовность требует реальной границы OS/CI; без неё CLI явно блокирует соответствующее утверждение. Внешние commit/merge/release не блокируются без интеграции. |

## Первый выпуск и границы

Первый встроенный адаптер — Python/unittest: текущий проект, прямые/относительные импорты, общие fixtures и обработка неизвестных динамических импортов. Другие языки используют явно одобренные команды и консервативные группы; универсальный автоматический анализ всех технологий не обещается. Контракт адаптеров допускает расширение позже.

Защищённый контур входит в блок как протокол и эталонный изолированный executor с проверкой прав и квитанций. Развёртывание в реальном пользовательском CI/под отдельной учётной записью требует доступного окружения и отдельного разрешения; отсутствие развёртывания нельзя скрывать за успешным mock-тестом. Подключение защищённого режима — явный шаг инженера.

## Матрица приёмки

| ID | Сценарий и наблюдаемый результат | Требования |
|---|---|---|
| AC-01 | В проекте без .git ручная правка оплаты запускает оплату и checkout; корзина reused. Правка discounts затрагивает все три. Счётчики подтверждают фактические запуски. | R-03–05,08,11 |
| AC-02 | Добавление/удаление/rename файла и импорта, одинаковые mtime/size при других байтах, отсутствующий baseline, циклы и dynamic import не дают ложного reuse. | R-04–05,09 |
| AC-03 | Изменение лога не запускает продуктовые тесты; карточка запускает структурные проверки, изменение критерия приёмки — связанные содержательные. Используемые PNG/archive считаются входами. Неизвестный файл не теряется. | R-06–07 |
| AC-04 | Известная подсистема расширяет набор в своих доказанных границах, неизвестная — до проекта. Восемь независимых актуальных результатов сохраняются, два устаревших выполняются; при недоказанной независимости reuse запрещён. Бюджет останавливает запуск до превышения. | R-09–11 |
| AC-05 | Релиз собирает все обязательства из разных задач; all/force запускает всё; stale сохраняет пригодные результаты. Смена среды/команды/fixture/API-версии/TTL обесценивает связанные результаты; поздний failed не скрывается. | R-08,11–12 |
| AC-06 | exit 0 с нулём тестов, пропавший test ID, лишний skip, дубликат и повреждённый отчёт отклонены. Описания видны рядом с IDs и исходным временем reused-результата; rename label не выдаётся за новый тест. | R-13–14 |
| AC-07 | Изменение во время подготовки/после запуска не выдаёт текущий passed; изолированный кандидат связан с результатом, подмена снимка и квитанции обнаруживается. | R-15,17 |
| AC-08 | Редактируемые approved=true, удаление проверки/связи, подмена ключа, поддельная квитанция и запись из тестового процесса не обходят доверенный gate. Отзыв ключа/политики, другой project_id и replay для других входов блокируются. | R-17–18,20 |
| AC-09 | Новое поведение без тестов не считается доказанным от полного старого suite; ручное обязательство остаётся ручным. Handoff/accept/release-ready используют один расчёт; архивирование не теряет provenance. | R-12,16 |
| AC-10 | Legacy неизменен, opt-in preview read-only; миграция сохраняет обязательства; неподдержанная версия/прерывание/restore/повреждённая история безопасны. | R-19 |
| AC-11 | Самоприменение на временной копии репозитория: стоимость измерена количеством запусков, файлов/байтов хеширования и временем, без заранее обещанного процента. Отчёт различает локальные тесты и реальный защищённый прогон. | R-01–20 |

## Затронутые документы и следующий шаг

При реализации обновляются verification/workflow/tasks, конфигурационные шаблоны, архитектура и code-map, руководство, install/update-контракт и CI-интеграция. Требования развивают [proportional-workflow](proportional-workflow.md); принятый ADR-0003 не переписывается. Текущие правила и self-config при этой подготовке не меняются.

Сначала принять технический проект и разрешить PB-057. Первый этап фиксирует версии схем и CLI-контракт; конкретный бюджет и размещение доверенного контура задаются при подключении. Внешний rollout не является скрытой зависимостью локальной подготовки.
