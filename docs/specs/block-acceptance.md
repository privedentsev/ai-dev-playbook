## Статус и действующее поведение

Предлагаемое изменение; документ и change — draft. Подготовка не разрешает кодирование, изменение рабочей конфигурации, приёмку или закрытие задач. Текущие правила продолжают действовать до реализации и явного подключения.

Сейчас каждая подзадача большого плана проходит отдельную приёмку; зависимости требуют done. Правила предписывают reopen при дефекте закрытой подзадачи. CLI блокирует активных зависимых и отвергает граф, где done зависит от незавершённого. Сам аудит автоматически архив не возвращает. Приёмка инженером предусмотрена, но не отменяет gate проверок, передачи и записи accepted в журнале Markdown v2.

## Цель и границы

Разрешить агенту выполнить согласованный план без остановки на аудите каждой задачи, сохранив проверки каждой реализации и независимую приёмку конечного результата. Исправлять находки итогового аудита отдельными задачами без изменения закрытых карточек и их доказательств.

Не входит: фоновый запуск агентов, новый планировщик/оркестратор, автоматическая реализация исправлений без поручения, изменение модели доверия, commit/push/merge/release. Одна команда готовности не выполняет независимый аудит и не выдаёт разрешение закрытия.

## Планируемые требования

| ID | Требование |
|---|---|
| R-01 | При подготовке плана агент предлагает per_task (каждая задача), final (итоговый) или mixed (с контрольными точками). Инженер утверждает вариант вместе с составом и порядком плана; основание фиксируется. Отсутствие настройки сохраняет прежний порядок. |
| R-02 | У плана есть единственный источник политики приёмки: неизменяемый ID, ревизия, задачи, итоговый AUDIT, зависимости и checkpoints. Карточки ссылаются на него; несовпадения, циклы, повторное членство в активных блоках и неизвестные ID отвергаются. |
| R-03 | per_task сохраняет отдельную приёмку каждой задачи. final разрешает последовательную реализацию по проверенным передачам. mixed использует те же передачи внутри этапа, но запрещает старт следующего этапа до независимой приёмки checkpoint. Внешняя зависимость требует done. |
| R-04 | Каждая задача проходит реализацию, предусмотренные проверки, CHECK/HANDOFF и CLI-передачу; остаётся in_review до приёмки. Ошибка/неполная проверка/непринятые требования не дают продолжить. Самопроверка не является аудитом. |
| R-05 | Существующий Depends-On остаётся строгой зависимостью done. Для совместной приёмки вводится отдельная зависимость от проверенной передачи внутри плана; она не превращает handoff в done. Все потребители графа используют общий evaluator, включая check, start, handoff, audit-ready, accept и lifecycle plan/apply. |
| R-06 | Переход дальше привязан к реально использованной передаче предшественника и её результату. Перед стартом она должна быть текущей. Изменение значимых входов после старта инвалидирует затронутые результаты; зависимые задачи требуют повторной проверки. История и baseline не заменяются. |
| R-07 | Итоговый аудит допускается после проверенных передач всех участников и принятых checkpoints. Карточка итогового аудита не требует заранее done от задач совместной приёмки: иначе возникает цикл. Приёмка аудита и закрытие требуют выполнения более строгих условий R-08–12. |
| R-08 | Блок проверяется на едином конечном candidate: требования, политика, состав, код, тесты, среда и доказательства связаны отпечатками. Поздние задачи могут изменить ранний код, поэтому историческая передача сама по себе не доказывает актуальность. Нужна матрица критериев каждой задачи с актуальными проверками конечного candidate. |
| R-09 | Исторические передачи/отчёты не переписываются и не переименовываются в свежие. Блок хранит новые доказательства текущего результата. Reuse разрешён лишь действующим runner при совпадении значимых входов; новый цикл аудита не означает безусловный полный прогон всего проекта. Неизвестная область влияния требует консервативной проверки. |
| R-10 | Независимый аудитор в отдельной сессии либо инженер проверяет каждую задачу и совместную работу. Успешный общий протокол содержит verdict по всем критериям и является основанием записей приёмки задач. Для Markdown v2 создаются штатные audit-записи; устаревшие индивидуальные handoff нельзя принять простым обходом прежнего gate. |
| R-11 | Acceptance привязана к ревизии политики и конечному candidate. Изменение значимых входов до accept/close снимает готовность затронутой области, запрещает закрытие и требует revalidate/аудит изменений. Понижение порядка контроля после старта требует явного решения инженера и нового аудита затронутого scope. |
| R-12 | При успешном аудите и разрешении инженера CLI закрывает участников и AUDIT по согласованному плану, затем архивирует допустимые общие документы. Dry-run проверяет конечный граф и доказательства без записи; apply повторно проверяет входы. Частичное применение восстанавливаемо; успешная приёмка сама по себе не означает архивирование. |
| R-13 | При отрицательном содержательном аудите создаётся одна задача исправлений на итерацию с перечнем findings, исходными задачами, критериями, проверками и связью с AUDIT. Техническая неготовность/сбой preflight не считается находкой и не создаёт пустую задачу. Независимые крупные исправления допускается явно разделить с полным покрытием findings. |
| R-14 | Создание исправления, связи, индекс и блокирующее обязательство AUDIT записываются одной восстанавливаемой операцией. Повтор той же итерации не создаёт дубликаты; несовпадающий payload/занятый ID отвергается до записи. Созданная задача — draft, без назначенного исполнителя. Создание не разрешает реализацию. |
| R-15 | До принятия исправления и повторной общей проверки итоговый AUDIT не может быть принят/закрыт. Исправление зависит от конкретного протокола находок, а не от done итогового AUDIT; циклическая зависимость запрещена. Отмена исправления не устраняет замечания. |
| R-16 | Независимый аудитор сначала принимает исправление, затем проверяет интеграцию и регрессию блока. Это разрешено за один запуск аудитора при соответствующем поручении. Непринятое исправление возвращается в работу той же карточки; новый дефект после её закрытия создаёт новую задачу/итерацию. |
| R-17 | Архивные исходные карточки, Closed, прежние приёмки и immutable evidence не меняются от новых находок. Связи на них хранятся в новых активных материалах. Reopen остаётся явным отдельным пересмотром прежнего закрытия, но не обычным способом исправления находок блока. |
| R-18 | Нет обязательного отдельного агента-аудитора: инженер может лично принять результат с автором/основанием и нужными записями. Исполнитель не подменяет инженера и не выдаёт собственную проверку за независимую. Ранее данное явное разрешение закрыть при успехе учитывается без повторного запроса. |
| R-19 | Новая механика подключается явно; legacy, inline/external metadata и задачи без политики не меняют поведения. Обновление не мигрирует архив и существующие планы молча. Неизвестная версия политики не означает разрешение пропустить аудит. |
| R-20 | card show и block status объясняют: что реализовано, что проверено, что принято, какой checkpoint/находка/stale-вход мешает и какое следующее действие допустимо. Политика не копирует статусы карточек в план. |

## Сценарии приёмки

| ID | Сценарий и ожидаемый результат |
|---|---|
| AC-01 | Пять задач final: последовательные start/verify/handoff без индивидуального аудита; все in_review, один независимый аудит, общая приёмка и разрешённое закрытие. |
| AC-02 | Те же задачи per_task и без политики требуют done предшественника; final не разрешён одним текстовым обещанием агента. |
| AC-03 | Mixed: внутри этапа передача разрешает продолжение, за checkpoint не пройти без актуальной независимой приёмки; внешний Depends-On остаётся строгим. |
| AC-04 | Failed/timeout/пустой CHECK, stale/чужой handoff, отменённый предшественник, цикл или неодобренная политика запрещают старт/приёмку с объяснением. |
| AC-05 | Поздняя задача меняет общий код: исторические передачи сохранены, финальная матрица заново подтверждает затронутые ранние AC на конечном candidate; независимые результаты reuse только по правилам runner. |
| AC-06 | Изменение candidate/политики/среды после подготовки или accept запрещает close; архивирование не ломает валидные исторические ссылки и хеши. |
| AC-07 | Отрицательный итоговый аудит с тремя findings создаёт одну draft-задачу; повтор команды не создаёт дубль, конфликт/сбой/конкурентная запись не оставляют половину связей. |
| AC-08 | Исправление проходит собственный аудит и общую регрессию в одном запуске; провал оставляет обязательство открытым. Новая находка после закрытия исправления создаёт следующую задачу. |
| AC-09 | Находка касается архивной задачи: ни она, ни её зависимые архивные задачи не возвращаются; байты карточек/evidence и даты закрытия сохранены, активный AUDIT заблокирован. |
| AC-10 | Групповая приёмка/close dry-run, apply, повтор, прерывание, restore и concurrent edits проверены на временном проекте; нет обхода AC или неразрешённого закрытия. |
| AC-11 | Установка/обновление opt-in; отсутствие/неизвестная версия, legacy и оба способа хранения метаданных проверены. Документация не объявляет draft-поведение действующим. |
| AC-12 | Инженер может принять лично; исполнитель не присваивает себе его роль. Отчёт различает проверено/принято/архивировано и объясняет допустимый следующий шаг. |

## Влияние на документы

После реализации обновить workflow.md (маршруты и остановки), tasks.md (зависимости, общая приёмка, замена обычного reopen задачей исправлений), verification.md (конечный candidate и freshness), task-card-format.md (общий протокол/связи), шаблоны плана/карточек, user-guide/modes.md, architecture.md/code-map.md и совместимое обновление. Действующие спецификации workflow-and-document-lifecycle и proportional-workflow развиваются через отдельные changes/ревизии; принятые требования и ADR не переписывать задним числом.

## Пользовательский порядок

При подготовке нового плана агент объясняет выбор одного из трёх вариантов, инженер согласовывает его. Для final поручение «Выполни все задачи плана, проверь и передай, остановись перед аудитом» разрешает последовательную реализацию без промежуточной независимой приёмки. Это не разрешает реализацию ещё не согласованных требований.

Затем отдельной сессии: «Проведи итоговый аудит; при успехе прими и закрой блок» — если инженер действительно поручает и закрытие. При замечаниях аудитор создаёт draft-задачу исправлений; выполнение требует поручения, которое может быть дано заранее. После исправления: «Проверь исправления и при успехе сразу повтори общую проверку». Одно поручение аудитору допускает оба этапа, но не смешивает их результаты.
