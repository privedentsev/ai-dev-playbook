## Статус и архитектурное решение

Draft; интерфейсы ниже проектируемые, сейчас CLI их не предоставляет. [Требования R-01–20](../specs/block-acceptance.md), [ADR-0007](../adr/0007-block-acceptance.md). Расширять действующий lifecycle и общий gate, не вводить второй движок статусов.

## 1. Единый источник политики

Предлагается версионированное поле acceptance_policy в метаданных plan (расширение схемы документов с явной capability). Карточки получают только ссылку на plan ID/revision. Проект без capability сохраняет прежние строгие зависимости. Точный номер схемы и совместимое представление фиксируются PB-065; неизвестные поля/версии старым кодом не игнорируются. Не добавлять эти поля в рабочие метаданные на этапе подготовки.

Политика содержит mode=per_task|final|mixed, revision, approved_basis (автор, время, источник решения), members, final_audit и checkpoints. Каждый checkpoint задаёт уникальный ID, точный scope задач и обязательную приёмку перед стартом следующего этапа. Граф ацикличен, проверяется полнота покрытия; задача принадлежит не более одному активному блоку совместной приёмки. Членство и статусы не дублируются в тексте плана.

Depends-On сохраняет done-семантику для внешних и строгих внутренних рёбер. Новое implementation_edges в политике задаёт from/to и required=verified_handoff. Между парой не допускаются противоречивые типы. Финальный AUDIT перечислен отдельно: его review-readiness требует передач, acceptance/close — подтверждённого конечного результата и устранённых findings. Он не зависит строгим done-ребром от ещё не принятых members. Исправление ссылается на report/iteration, а AUDIT имеет обязательство дождаться его приёмки: это не взаимные Depends-On.

## 2. Общая оценка готовности

Выделить чистый evaluator графа (например, block_workflow.py): evaluate(operation, task, policy, candidate, evidence) возвращает allowed, reason_codes, obligations, consumed_receipts. Его вызывают start, check --ready, verify/handoff, audit-ready, accept, close и lifecycle future-state validation. Не дублировать упрощённую проверку «in_review достаточно» в отдельных командах.

Для start: согласованная политика, разрешение реализации, строгие зависимости done, внутренние предшественники с актуальными проверенными передачами, выполненные checkpoints. Start сохраняет receipts использованных передач и baseline. Для последующего revise разрешается устранять stale/failed, не требуя пройти невыполнимый gate собственного исправления. Проверки перехода и успешного завершения разделены.

Не вводить новый основной статус: draft/ready/in_progress/in_review/done остаются. Block status вычисляется: awaiting_work, awaiting_checkpoint, review_ready, changes_requested, accepted, archived; это отображение, не второй редактируемый status. Blocked в карточке применяется только штатным переходом с причиной; диагностический отказ не меняет файлы автоматически.

## 3. Конечный candidate и история передач

Блок получает immutable review package у владельца AUDIT: policy revision/hash, состав, проекции требований/критериев, receipts исходных передач, значимые входы/среда, матрица task+AC → current result/report/manual evidence и candidate hash. Служебные записи журнала/индекса и перенос путей не меняют семантический candidate; новый код/требования/политика меняют. Граница исключений берётся из действующего verification, не произвольного списка расширений.

block prepare-review сначала объясняет обязательства и stale-область, затем явный revalidate запускает необходимые проверки. Исторические handoff остаются историческими. Если поздняя реализация изменила ранний код, пакет содержит новые доказательства ранних критериев на конечном candidate. Старый отчёт пригоден только при разрешённом runner reuse. Нельзя пересчитать хеш старого passed и назвать его новым запуском.

Если у runner нет доказанной карты влияния, применять консервативный scope, вплоть до полного прогона. Не внедрять здесь selector из PB-057–064. Имеющийся v2/legacy runner адаптируется через общий контракт evidence. Настоящий независимый аудит, manual obligations и task-specific сценарии сохраняются даже при reuse общего suite.

Перед review, accept и первым write close повторно сверяются candidate/read-set. Изменения после start помечают зависимые evidence stale; уже начатые задачи требуют revalidate перед следующим потребителем. Нельзя требовать вечной текущести всех старых передач: нормальное изменение общего файла последующей задачей покрывается финальным пакетом. Состав пакета и invalidation объясняются CLI.

## 4. Findings и задача исправлений

Отрицательный протокол имеет стабильные report_id, iteration, author/session, candidate, verdict=changes_requested и findings с ID, source_tasks, affected_AC, reproducer/evidence, expected, severity. Технический сбой подготовки не создаёт содержательного verdict.

Предлагаемый интерфейс: block create-fix <AUDIT-ID> --report <путь> --task <новый-ID> [--apply]. Без apply — preview. Команда требует ранее записанного отрицательного независимого протокола и права на постановку исправлений. Ключ идемпотентности: block ID + report ID/iteration; payload фиксируется хешем. Повтор возвращает существующую карточку, иной payload требует нового протокола, занятый ID — отказ.

Одна recoverable-операция создаёт Markdown+sidecar draft-карточки, критерии по всем findings, ссылки на источники, запись obligations в активном AUDIT и индекс. В текущий архив не пишет. Сохраняет связь finding → fix → accepted evidence; разделение крупных исправлений явно покрывает все findings без потерь. Отмена/удаление/переименование fix не закрывает обязательство; снятие finding требует мотивированного независимого протокола и повторной оценки блока.

Выполнение исправления требует отдельного или ранее данного явного поручения. По непринятому fix аудит возвращает его в in_progress; дубликат задачи не создаётся. После закрытого fix новая находка получает новую итерацию и новую карточку. Принятый fix добавляет актуальное evidence, но не означает успех итоговой регрессии.

## 5. Приёмка, закрытие и общие документы

Независимый аудитор/инженер записывает два различимых результата: аудит исправления и итоговый аудит блока. Они могут быть одной сессией, но имеют собственные scope/receipts. Исполнитель не принимает своё исправление. Успех блока требует всех task+AC в конечной матрице, закрытых finding obligations и checkpoints.

Предлагаемый block accept готовит индивидуальные accepted-записи и общую квитанцию как единую recoverable-операцию. Каждая ссылается на package/candidate/policy и конкретный verdict по AC. Для Markdown v2 добавляются штатные audit-записи. Существующие task_cards.receipt/criterion_view/_close_evidence расширяются явным block receipt, не флагом skip и не fake-refresh индивидуальных handoff. Уже закрытые участники получают только новые ссылки в активном AUDIT; их архив не переписывается.

Предлагаемый block close --dry-run / --apply использует существующий lifecycle plan/apply: целевой граф закрывает members, fixes и AUDIT, для каждой приёмки проверяет конечный пакет. Закрытие требует явного поручения инженера, включая ранее данное условное «закрой при успехе». Promotion требований и архивирование плана/общих документов происходят только при своей допустимости и scope. Ошибка promotion не объявляется полным завершением блока.

Операции используют общий gate, read-set, preview, поздний backup и restore фактически принятого file_operations/scoped_operations engine. До записи повторно сверяют входы и отсутствие конфликтов ID. Идемпотентный повтор после успеха не создаёт новые receipts; незавершённая операция требует restore/resume штатным способом. Сбой не оставляет выборочную приёмку без восстановимого журнала.

## 6. Предлагаемая поверхность CLI

PB-065 фиксирует окончательный синтаксис и JSON-схемы до потребителей. Минимальные функции:

| Функция | Ввод и результат |
|---|---|
| policy preview/apply | Режим, members, edges, checkpoints, основание инженера; проверенный план без статусов-копий |
| block status | Задачи/передачи/приёмки, stale и findings, объяснение следующего шага; read-only |
| block prepare-review / revalidate | Конечный candidate, матрица AC и список проверок; запись/запуск только явно |
| block create-fix | Отрицательный протокол → одна draft-карточка и obligations; preview/apply |
| block accept | Независимый протокол → связанные индивидуальные и общая приёмки |
| block close | Разрешённый lifecycle-план → dry-run/apply и восстановление |

Не создавать фоновый агент-runner: агент следует готовности, читает card show/block status и запускает обычные команды. CLI проверяет условия, но не удостоверяет личность человека полем role; сохраняется существующая модель атрибуции, независимость подтверждается протоколом сессии/инженером.

## 7. Совместимость и риски

Без настройки — прежнее поведение, старый архив не мигрируется. Явная конверсия существующего плана требует согласования, проверки графа и сохранения прежних receipts; понижение после старта не снимает находки/failed проверки. Quick остаётся инженерным маршрутом; совместная приёмка не обход его правил. Установка/обновление переносит новые схемы и шаблоны без автоподключения self-project.

Пересечения: PB-041 (sidecar/card show), PB-046–050 (recoverable операции), PB-057–064 (verification/lifecycle). Перед реализацией читать актуальные handoff; не импортировать ещё не принятый API молча. Автоматический selector и protected executor не обязательные зависимости нового блока.

## 8. Проверка решения

Unit: схемы/граф/переходы/idempotency. CLI на временных проектах: AC-01–12 спецификации, включая stale общего кода, архивные исходники, multi-fix, mixed checkpoints, legacy и внешний JSON. Fault injection: до/после каждой записи, concurrent edits между prepare и apply, повтор/restore, занятый ID. Проверять байты архива и evidence до/после; структура check --ready не доказывает поведение. Сквозная матрица у PB-071, независимая оценка у AUDIT-010.
