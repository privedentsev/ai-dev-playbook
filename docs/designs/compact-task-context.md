## Решение

Соседний `<ID>.meta.json` определяется именем Markdown, без реестра расположений. Маркер `<!-- playbook-meta:external -->` обязателен для внешнего хранения: исчезновение JSON не превращает карточку в legacy. Маркер не содержит дублируемых полей.

На границе ввода/вывода используется единый адаптер: он читает пару и передаёт существующим парсеру/engine прежнее представление с JSON-блоком в памяти. Перед сохранением это представление разделяется на исходный Markdown с маркером и JSON. В файловой системе двух источников нет; схема и алгоритмы receipt/проекции не перепроектируются. Адаптер не меняет глобальное поведение pathlib. Сохранение и перенос включают оба файла в write/remove/input-set до расчёта плана, поэтому общий engine обеспечивает прежнюю защиту от stale plan и восстановление.

## Совместимость и свежесть

Inline и legacy остаются на прежнем пути. Проверка каталога отклоняет orphan sidecar и конфликт источников. При verify sidecar включается в снимок и при явном входе Markdown; исключение текущей карточки при разрешённых служебных изменениях распространяется на её sidecar, при этом проекция требований и execution_state проверяются прежними алгоритмами. Другие входы не исключаются. Кэш или альтернативный источник состояния не вводится.

## Представление

Парсер уже имеет ID и связи. Компактный вывод использует их, показывает текущую работу после передачи и открытые находки, содержит команды `--entry` и `--full`. Полный JSON-контракт сохраняется. Полный Markdown скрывает только реальный служебный блок, а не fenced-примеры. Версия Markdown остаётся 2: способ хранения не является новой грамматикой журнала.

## Риски

Парная запись/перенос, конфликт источников, исключение sidecar из freshness, сохранность immutable-материалов и упаковка ресурсов требуют поведенческих тестов. Используется существующая восстанавливаемая файловая операция; отдельного транзакционного или кэширующего механизма нет. Существующие рабочие карточки не используются как изменяемый пилот.

## Уточнение по A-01

Распознавание внешнего маркера возвращает позицию строки вне fenced-блоков. Чтение пары и создание новой карточки используют один метод вставки по этой позиции. Текстовое упоминание маркера в заголовке или примере не является местом вставки; заголовки внутри fenced-примеров не ограничивают расположение настоящего маркера. Регрессии проверяют чтение, создание, roundtrip и sync.
