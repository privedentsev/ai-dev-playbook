## 1. Исходное состояние и контекст

Основание: [спецификация](../specs/proportional-workflow.md), [обсуждение](../discussions/proportional-workflow.md). Требования согласованы запросом инженера «Давай дальше» после представления спецификации; разрешён этап проектирования.

По исходникам: playbook.py разбирает фиксированную шапку карточки; documents.py валидирует дополнительные метаданные; verification.py формирует один общий снимок и report schema_version=1; lifecycle.py отдельно пишет handoff/acceptance, проверяет свежесть и строит архивный план. file_operations.py уже предоставляет общий gate, staged-проверки, journal/backup и restore. Используем эти механизмы, не строим второй task engine.

Текущее описание архитектуры местами содержит исторические сведения. Для этого решения опорой служат актуальные функции read_tasks, verification.run/inputs_fresh, lifecycle.card_projection/_close_evidence/handoff_command и существующий движок операций. Их изменение — будущая работа.

## 2. Предлагаемое техническое решение

### 2.1. Данные задачи и включение механики

Сохранить шапку, ID, статусы и каталоги задач. Маршрут хранить в дополнительном блоке метаданных как `workflow.route`: `quick | small | medium | large`; рядом — reason и история переходов. Шапку не расширять полем Route: её строгий regex и существующие инструменты иначе придётся менять без необходимости. Это уточняет предложенный ранее пример `Route: quick`.

Добавить опциональный блок `task_workflow` версии 2 в project.json. Он включает поддержку новых карточек, реестр проверок и политику контрольных точек. Старый `verification` сохраняется для старого пути. Новая карточка имеет task metadata schema_version=2; весь существующий envelope relations/materials остаётся. Старые версии должны явно отклонять новый schema_version. Полное отсутствие нового блока и новых метаданных сохраняет прежнее поведение.

Сокращённая карточка quick сохраняет обязательную шапку, цель/границы, приёмку, блок метаданных и краткий журнал результата. Машиночитаемые проверки и маршрут в метаданных — единственный источник; не поддерживать вторую обязательную копию команд в тексте. Человеческое резюме может ссылаться на ID проверок.

Переходы draft → ready → in_progress → in_review → done сохраняются. Команда начала работы может согласованно пройти ready/in_progress, но не делает draft готовым при незаполненной цели, приёмке, зависимостях или проверках. Сохраняются отмена, blocked и reopen. Изменение маршрута оформляется отдельным событием с причиной; понижение требует инженерского основания.

### 2.2. План проверок задачи

В metadata schema_version=2 добавить `verification_plan`: revision, rationale, scope (явные корни влияния), checks, decisions. В каждой checks: стабильный task-local ID, ссылка на запись реестра либо ручной сценарий, назначение, inputs, обязательность выбранной проверки. Состав плана — часть содержательного отпечатка.

Реестр в task_workflow содержит ID, kind (`command`/`manual`), argv/сценарий, timeout, default_inputs и применимость. Команда выполняется только по ссылке на разрешённый реестр; произвольный argv в карточке не исполняется. Новую команду добавляют в доверенную конфигурацию в рамках разрешения инженера. Реестр — перечень инструментов, а не профили задач.

Обязательность проекта: `always`, `when_paths` или `checkpoint`. `when_paths` — список относительных glob по нормализованным POSIX-путям, без eval и shell. Сравнивается объединение заявленного scope и фактических добавленных/изменённых/удалённых файлов между базовым снимком и текущим состоянием. Если scope шире паттерна — проверка применяется консервативно. Результат вычисления обязательности показывается в preflight.

Базовый снимок снимается при начале работы CLI, не зависит от чистоты Git и различает исходные незакоммиченные правки и изменения сессии задачи. Scope остаётся необходим: по файловому diff нельзя доказать все связи. При отсутствии надёжной базы автоматическая неприменимость не допускается. Новые изменения/файлы повторно проверяются перед передачей, а изменение политики обязательности инвалидирует её вычисление.

Решение «неприменима» хранит основание и состояние входов. Исключение после провала требует записи инженерского решения; нельзя превратить failed в passed. Необоснованное исключение остаётся ошибкой. Политику нельзя автоматически ослабить при миграции.

Входы поддерживают file, directory, task_projection, policy_projection и список environment facts. Отсутствующий точный путь фиксируется как absent (для будущего создания/удаления), каталог — с составом. Это позволяет обнаруживать появление новых файлов. Ссылки наружу, symlink и пути work не допускаются как исходники, кроме специально проверяемых зарегистрированных immutable-материалов.

### 2.3. Команды и нормальный путь

Предлагаемые дополнения к CLI (синтаксис подлежит окончательной фиксации при планировании):

| Операция | Действие |
|---|---|
| `lifecycle start ID` | Валидирует готовность, фиксирует baseline и начинает работу; карточка и индекс пишутся одной операцией |
| `lifecycle route ID --to ... --reason ...` | Меняет маршрут с историей, при понижении требует основание инженера |
| `verify ID --preflight` | Без записи и запуска команд показывает готовность, применимые проверки, отсутствие доказательств и ошибки |
| `verify ID` | Перед запуском делает preflight, исполняет только требуемые автоматические проверки, переиспользует свежие результаты |
| `verify ID --record-manual FILE` | Регистрирует заявление о ручной проверке по разрешённому сценарию и актуальному снимку |
| `lifecycle handoff ID` | Регистрирует все известные материалы, проверяет покрытие и свежесть, согласованно пишет in_review и индекс |
| `lifecycle revise ID --reason ...` | Возвращает in_review в in_progress, сохраняет старую передачу/приёмку как историю, снимает их актуальность |
| `lifecycle accept ID ...` | Регистрирует приёмку конкретной передачи и результата от имени инженера/аудитора |
| `close ID` | Проверяет приёмку/доказательства и архивирует тем же lifecycle engine |

Preflight до прогона допускает будущие отчёты и ожидаемые материалы, но блокирует ошибки схемы, статуса, зависимости, путей и обязательности. Обновление производного индекса выполняется как подготовительный шаг до снимка тестов, с явным сообщением; read-only preflight только показывает устарелость и предлагаемое исправление. При неучтённых материалах handoff регистрирует распознаваемые прогоны автоматически; неизвестные материалы требуют явного решения о роли, не удаляются.

Нормальный quick-путь: создать обычную карточку по сокращённому шаблону → start → правки/просмотры → verify/ручные результаты → handoff → приёмка инженером → close. Это действия агента и CLI, не семь обязательных обращений к пользователю. Промежуточные итерации не требуют handoff; если передача уже сделана, revise возвращает задачу в работу без нового ID.

При явном «принимаю, закрывай» агент может последовательно зарегистрировать приёмку и close. Не объединять запуск тестов и искусственную инженерскую приёмку одной командой. Успешная команда проверки никогда сама не создаёт acceptance.

### 2.4. Отчёты и покрытие обязательных проверок

Report schema_version=2 содержит task_id, plan_revision/hash, route, policy hash, run_id, at, results и coverage. Каждый результат имеет check_id, definition hash, kind, status, actor, environment, input snapshot, начало/конец, результат/ограничения, ссылки на логи/материалы. Для command — exit_code и before/after; для manual — scenario hash, наблюдение, время проверки и зафиксированный snapshot предъявленной версии.

Ручной результат не может привязываться к версии, которой инженер не видел. Агент заранее фиксирует candidate snapshot при предъявлении; подтверждение инженера ссылается на этот кандидат. Если файлы изменились между предъявлением и записью результата, нужен новый просмотр. Для среды без браузера допускается заявление инженера по сценарию; отсутствие такого подтверждения остаётся not_run. CLI проверяет согласованность заявления, а не личность/факт просмотра. В runner v2 поле `candidate_snapshot.sha256` связывает предъявление с task_id, check_id, definition_hash, scenario_hash и policy_hash. Регистрация passed требует точного совпадения кандидата с валидным исходным отчётом той же задачи и совместимых хешей; изменение сценария, определения или политики требует нового предъявления и подтверждения.

Проверка достаточности в handoff/close: для каждого применимого обязательного ID есть актуальный passed либо обоснованный not_applicable; failed, timeout и not_run закрытие блокируют. Не использовать нынешний принцип «найден хотя бы один свежий passed-отчёт». Результаты могут быть собраны из нескольких прогонов, но только одной совместимой версии плана/политики. Изменение одного независимого check не требует перезапускать остальные, если неизменность их определения/входов доказана.

Отчёты immutable. Повторный запуск создаёт новый результат, решения об исключениях — отдельное событие с автором и основанием, не редактирование старого лога. История выполнения хранится в work/verification и регистрируется для переноса в материалы задачи.

### 2.5. Три независимых отпечатка

1. **Проверка:** определение конкретной проверки, её значимые входы, среда и применимая политика. Состав/хеши файлов и проекций сравниваются до/после и при повторном использовании.
2. **Переданный результат:** требования, маршрут/границы, план проверок, scope, актуальная реализация и набор доказательств. Acceptance ссылается на handoff ID и этот hash; изменение результата требует новой приёмки даже при частичном переиспользовании тестов.
3. **Файловая операция:** полный снимок затрагиваемых путей и scan-set, как в существующем lifecycle plan. Изменения после plan блокируют apply независимо от свежести тестов.

Для задачи исключаются только известные служебные поля из семантической проекции; цель, критерии, маршрут/план из metadata включаются явно. Не использовать исключение всего metadata, как нынешняя card_projection: там будет значимый план. Проекция policy включает команды, правила обязательности и условия среды; не включает названия несвязанных проектов и даты логов.

Индекс получает отдельную структурную проверку при каждом переходе. Для проверки исходного Markdown файл хешируется целиком по умолчанию. Проекции применяются только к явно объявленным управляемым служебным данным; это не глобальное исключение docs. Перемещение доказательств разрешается через проверенную moves/relocation карту, исходные байты не меняются. Код, который использует путь файла как поведение, не объявляется независимым от переноса автоматически.

### 2.6. Регрессия и компоненты

Контрольные точки `merge`/`release` — явная политика проекта и read-only оценка её доказательств. Локальное close не проставляет успешную контрольную точку. CI/инженер вызывает проверку контрольной точки отдельно; без интеграции внешняя платформа не блокируется самим playbook.

Распределение изменений:

- playbook.py: маршрутизация CLI, распознавание версии режима, готовность и короткий вывод.
- documents.py: metadata v2, маршрут/план/история, результаты, строгая валидация и индекс.
- verification.py: отдельные результаты, ручной путь, coverage, переиспользование, отчёты v2.
- lifecycle.py: start/route/revise, согласованный handoff, актуальность приёмки, закрытие и перенос.
- file_operations.py: переиспользовать gate, транзакционную запись, backup и restore; не ослаблять проверки входов.
- Новый небольшой модуль verification_policy.py: чистые функции применимости, проекций и покрытия, общие для runner и lifecycle. Исключает расхождение логики verify и close.

## 3. Альтернативы и компромиссы

- Новый тип quick-задач отклонён: дублирует индексы, статусы и архив.
- Универсальные профили отклонены: слишком зависят от проекта. Реестр команд и конкретный план задачи решают другую задачу.
- Только текстовое обоснование без машинного покрытия отклонено: close не сможет выявить пропущенную обязательную проверку.
- Хеш всего проекта прост, но заставляет повторять несвязанные тесты. Выбраны явные входы с консервативной инвалидизацией при неопределённости.
- Только Git diff не подходит для незакоммиченных и негитовых проектов. Выбран baseline содержимого плюс явный scope.
- Полностью автоматическая оценка влияния не обещается: полноту scope и достаточность проверки оценивают агент и принимающий.

## 4. Обработка ошибок, риски и безопасность

Отказы до записи: неизвестная версия, route/check ID, неверные пути, незавершённая операция, неподтверждённая модель, отсутствующие зависимости, политика без однозначной применимости. Отказы до handoff/close: неполное покрытие, устаревшие входы, изменённый кандидат ручного просмотра, неучтённые материалы, отсутствующая либо чужая приёмка.

Частичный прогон сохраняет отчёт с реальными failed/timeout/not_run. Изменение command/policy не маскируется служебной записью. Исключение после провала не переписывает результат. Обоснование и подтверждение инженера проверяются как данные; CLI не является системой аутентификации инженера. Подмена актором имени инженера сама по себе технически не доказывает полномочия — это существующая доверительная граница локального агента.

Все изменяющие операции: gate → специализированный lock; staged-валидация → backup → запись → проверка. Прерывание и restore не должны создавать дубли событий или acceptance. Изменившиеся входы требуют пересборки плана операции, но не обязательно повторного теста реализации.

Главные риски: неполный scope, ошибочные glob и environment facts, избыточно широкие входы и рост сложности схем. Снижение: консервативные defaults, explain-вывод обязательности, явный план и негативные сценарии. Универсальный детектор риска не включать.

## 5. Совместимость, миграция и восстановление

Старый metadata/report v1 и verification сохраняют прежний кодовый путь. Новая механика требует task_workflow v2 и явного перевода карточки в metadata v2. Нельзя смешать старый успешный report с новым планом и автоматически считать его достаточным. Возможно оставить старый отчёт историческим материалом; для новой модели нужны результаты с явным покрытием.

Включение v2 не отключает старые обязательные команды: первоначально они переносятся как always. Сужение применимости — отдельное согласованное изменение конфигурации с diff. Это безопасно, но не даёт ускорения до настройки проекта; ограничение нужно явно объяснить инженеру.

Внедрение проводится с версией комплекта, объявленным updates_from и проверкой минимального поддерживаемого CLI до записи миграции. Старый CLI обязан отказать на metadata/report v2. Внешний downgrade без manifest-проверок не поддерживается как безопасный путь. Update restore восстанавливает целостный пред-образ, отчёты и материалы — через штатные операции, не удаление вручную.

Конкретные версии релиза, схемы migration и ADR выбираются перед реализацией. Данное решение пока draft; отдельный принятый ADR не создаётся до согласования архитектурных решений.

Updates schema 2 с minimum_cli_version=0.2.0 отделяет новый артефакт от прежнего updater; новый CLI сохраняет чтение schema 1. Init/update по умолчанию legacy, enable-v2 и migrate-card явные, через общий gate/engine и restore. ## 6. Сопровождающие материалы и доказательства

Все артефакты реализации закрепляются за будущими карточками/общим аудитом. Прогоны v1/v2 и ручные результаты сохраняются immutable, baseline/candidate snapshots регистрируются, если на них ссылаются активные доказательства. После закрытия ссылки разрешаются по moves, журналы восстановления не объявляются материалами задачи.

Проверка проектирования сейчас: сопоставление со спецификацией и актуальными функциями, валидация схемы самого design-документа и ссылок. Это не поведенческая проверка предложенной механики. Прототипы и замеры пока не выполнялись.
