## 1. Исходное устройство и выбранный подход

Изучены `playbook.py` (`config`, `read_tasks`, `render_index`, `close_task`, функции ссылок), `verification.py` (`snapshot`, `run`), `updating.py` (`update_apply`, backup/restore) и [контракт обновления](../../ai-dev-playbook/rules/update.md).

Карточки читаются из Markdown-шапки; metadata хранит связи, материалы, handoff и acceptance. documents.py строит каталог; document_links.py вычисляет ссылки и индексы; lifecycle.py планирует переносы и проверяет приёмку; file_operations.py обеспечивает общую блокировку, backup, журнал и восстановление. При настроенном documents close использует lifecycle engine; legacy-политика сохраняется явно. verify пишет отчёты в work/verification/.

Сохранены файловая модель и Python standard library. Полномочия и смысл решений определяет агент/инженер; CLI проверяет структуру, связи, допустимость операции и результат. Индексы вычисляются из источников; отдельной БД не требуется. Историческое описание устройства до PB-021 сохранено в приложенном снимке подготовки.

## 2. Данные документа

В новом документе после заголовка находится один явно ограниченный блок JSON. Его читают и человек, и CLI; Markdown ниже содержит требования/обоснование. У задач существующая шапка остаётся единственным источником `ID`, `Status`, дат и исполнителя. Дополнительный блок задачи содержит только связи, материалы и сведения передачи/приёмки, не копии шапки.

Пример формата спецификации (это пример формата, не регистрация текущих документов):

Контракт полей:

- `document_id` неизменяем и уникален среди документов, например `spec:notifications`, `design:notifications`, `adr:0001`. Это отдельное пространство от ID задач; реестр префиксов задач не расширяется. Имя файла — читаемый slug, для ADR сохраняется номер. Переезд не меняет ID.
- `kind`: `discussion | spec | design | adr | plan`. Заголовок документа — источник названия для индекса.
- `state`: для обсуждения `open | resolved | deferred | cancelled`; для spec/design/ADR `draft | accepted | superseded | cancelled`; для плана `draft | accepted | completed | cancelled`.
- `archive`: `null` либо объект `at`, `reason`, `successor` (ID или `null`), `operation_id`, `original_path`. Архивность определяется метаданными вместе с расположением, а не подменяет смысловой статус.
- `relations`: список `{relation, target}`; relation — `changes | replaces | cancels | based_on`, target — ID документа. Ссылка на файл в тексте служит человеку, отношение по ID — проверкам. Обратные связи вычисляются, вручную не дублируются. Несколько преемников задаются несколькими `replaces`, в архивном поле `successor` допускается `null` с объяснением в причине.
- `tasks`: ID связанных карточек. Для плана перечисляются его задачи и общая AUDIT-карточка; их статусы в документ не копируются.
- `created_at`, `updated_at` и даты действий — ISO 8601 со смещением. Старые документы без метаданных не получают вымышленных дат: при регистрации источник/неизвестность прежней даты отмечается отдельно, дата регистрации реальна.
- `changes` содержит изменения текущей возможности (§3), `materials` — принадлежащие документу материалы (§4).

Парсер требует ровно один блок, валидный JSON, известную версию схемы, неповторяющиеся ключи и ID. Примеры в fenced-блоках не считаются реальными метаданными. Несогласованность статуса с архивом, дубли ID, потерянные обязательные отношения — ошибки. Наличие цикла само по себе не запрещает произвольные тематические связи; цепочки `replaces` и зависимости задач обязаны быть ацикличны.

### Каталоги и конфигурация

В `project.json` вводится необязательный объект `documents` со своей `schema_version: 1` и `collections`. Для каждого kind задаются `active`, `archive`, `index`. Значения по умолчанию — из спецификации; архив задач по-прежнему берётся из `paths.archive`, а не вычисляется из строки `docs/archive/tasks`.

Коллекции находятся в `paths.docs`, не пересекаются с активными задачами, не перекрывают друг друга; индексы исключены из поиска документов. Поиск задач по имени/шапке сохраняется. Регистр имён и Unicode-коллизии проверяются с учётом ФС до создания/переноса. Все пути проверяются на выход из корня и symlink.

Документы без блока вне зарегистрированных коллекций остаются обычными проектными файлами. В коллекции они видны как `legacy/unregistered`: их не теряем из обзора, но не архивируем автоматически. Прицельная регистрация добавляет метаданные с сохранением тела и истории. Неизвестный будущий `schema_version` не трактуется как legacy.

## 3. Действующие и планируемые требования

Принятая спецификация или design имеет раздел текущей ревизии и отдельно предложения изменений. В `changes` запись содержит `id` (локально уникальный), `state: draft | approved | implemented | accepted | cancelled`, `section` (стабильный маркер раздела), `basis`, `tasks`, `acceptance` (ссылка на запись аудита либо `null`).

`basis` различает `engineer_approval` и `authorized_scope`: кто/когда, содержание разрешения и его источник. Разрешение продолжить работу не превращается в запись «инженер прочитал и согласовал текст».

Текущее описание не редактируется под будущую реализацию. Исполнитель дополняет раздел предложения и ставит `implemented`, когда изменение готово; аудитор сверяет фактический результат. В составе завершения приёмки подготовленная новая текущая редакция становится `current_revision + 1`, а предложение — `accepted`. Предыдущие требования и основание изменения сохраняются в истории документа/материале ревизии. Точное итоговое содержимое входит в проверяемый план операции; CLI не сочиняет редакцию требований.

При полной отмене работающей возможности текущая спецификация остаётся до фактического удаления. После приёмки архивируется целиком с причиной; частичное удаление SMS обновляет текущую редакцию общей спецификации, не архивируя действующие email-требования. Если меняется ADR, создаётся новый документ; исходное обоснование прежнего не переписывается.

## 4. Владение сопровождающими материалами

Материал регистрируется в метаданных одного владельца: карточки, общей AUDIT-карточки или документа. Запись: `id`, `role` (`report | log | screenshot | probe | other`), `source` (относительный путь или внешний URI), `storage` (`local | external`), `required`, `immutable`, `used_by` (ID потребителей). Внешний URI не содержит секретов; для внешнего материала дополнительно — описание способа доступа и проверенная доступность.

Дубли владения, пересечение каталогов двух владельцев и ссылка на отсутствующий обязательный материал блокируют завершение. У материала-каталога при планировании фиксируется полный состав файлов, размеры и SHA-256. Скрытый файл не пропускается; symlink не разыменовывается. Появление/исчезновение файла до записи делает план устаревшим.

Правила размещения:

- локальные материалы задачи/аудита по умолчанию — рядом с карточкой, `<ID>-evidence/`;
- материалы документа — `<slug>-evidence/` рядом с ним; в архиве сохраняется тот же относительный layout;
- общий материал закреплён за владельцем всего блока, потребители используют ссылки. Активный потребитель не мешает переносу, если владелец завершён и ссылки остаются доступны; необходимость материала для ещё не завершённой общей приёмки означает, что его владелец ещё не завершён;
- `work/verification/...` остаётся рабочим выходом runner. При передаче агент выбирает необходимые прогоны и регистрирует их. Операция завершения переносит зарегистрированные локальные прогоны в evidence владельца, сохраняя дерево; это может быть прямой перенос в архив при закрытии. Она не забирает весь `work/`;
- обнаруженные `<ID>-evidence/` или `work/verification/<ID>/` без учёта выводятся как кандидаты. Закрытие новой управляемой карточки останавливается до их разбора. Это защита от известных мест хранения, не обещание найти любой файл на диске;
- постоянный тест или код продукта не является сопровождающим материалом. Включение такого пути в перенос отклоняется по настроенным границам компонентов; неоднозначное назначение разбирается до apply.

Исторические логи, JSON-отчёты, снимки входов и разовые скрипты с `immutable: true` сохраняются побайтно. Автопереписывание путей внутри них запрещено. При переносе создаётся сопровождающая таблица `original_path → archived_path` с SHA-256 и список материалов с кликабельными текущими ссылками. Это позволяет найти логи по старым путям из отчёта, не выдавая их за новый прогон. Если нужен повтор старого скрипта с прежним layout, его разворачивают в отдельной временной копии; архивный оригинал не правят.

Обычный rewrite исключает immutable-материалы. Для их ссылок check использует исходное расположение из таблицы и преобразует найденную цель через карту переносов; такой исторический адрес не считается текущей битой ссылкой лишь из-за смены каталога. Отсутствующая запись отображения или недоступная цель остаётся ошибкой. Новые навигационные ссылки на сам материал указывают на его текущий путь. Карту переносов хранят с владельцем как служебные метаданные, она участвует в следующем переносе/возврате и не считается неизменяемым результатом теста.

Крупный обязательный внешний материал не «перемещается» локальным CLI: архивируется запись доступа; недоступность остаётся блокером. Восстановительные backup/journal незавершённой операции не перемещаются вместе с владельцем; после завершения долговременное подтверждение операции записывается в evidence, а служебная backup остаётся до отдельной очистки. Автоматической очистки в этом изменении нет.

## 5. Каталог, индексы и ссылки

`documents.py` строит в памяти каталог по метаданным и существующим карточкам. Он проверяет уникальность, разрешает ID в пути, строит обратные связи и список материалов. Индексы генерируются из этого каталога и не служат вторым источником состояния. Обновление — детерминированное; повторный запуск на тех же входах даёт те же байты.

Индексы коллекций: актуальные сверху, архив ниже; название-ссылка, состояние документа, дата. Индекс планов: план и задачи, без дублирования их статусов. Главный индекс содержит только разделы. Существующие ручные индексы не перезаписываются целиком: генерация действует в явно выделенной области `playbook-index:start/end`; первое выделение области показывается как отдельный diff при регистрации коллекции. Проверка сравнивает ожидаемую генерацию с файлом, но ничего не исправляет сама.

Для переноса строится карта всех `old_path → new_path` сразу. Каждая ссылка разрешается относительно старого расположения источника, затем адресат ищется в карте, затем вычисляется путь от нового расположения источника. Это покрывает входящие, исходящие, взаимные ссылки, ссылки на самого себя и на файлы evidence; последовательное применение замен строк недопустимо.

Поддерживаемый контракт первого выпуска: Markdown inline-ссылки и изображения, reference definitions, ссылки в `<...>`, пробелы/URL encoding, query и fragment с сохранением. Кодовые блоки и inline code не редактируются. Чистый `#fragment` сохраняется при переносе того же документа. Существование файла проверяется автоматически; переименование заголовка требует отдельной проверки якорей/ручных anchor. Парсер ссылок единый для rewrite и check, вместо расширения нынешних регулярных выражений отдельными несовместимыми путями.

Область поиска: `paths.docs`, корневые README/AGENTS и явно объявленные дополнительные проектные Markdown-файлы. Управляемое ядро комплекта в перенос проектных документов не включается: если входящая ссылка оттуда требует изменения, план показывает блокирующую зависимость, её исправляют отдельной работой над комплектом с manifest. Ссылки из незаявленных файлов не считаются проверенными. Обнаруженный неподдерживаемый формат с затронутым путём (например wikilink или HTML) — конфликт для ручного разбора; CLI не заявляет универсальный анализ произвольного кода/бинарных файлов.

## 6. CLI: действующий интерфейс

Ниже — проект новых команд, они пока отсутствуют. Запускаются через `python3 ai-dev-playbook/scripts/playbook.py`; примеры аргументов — условные.

| Команда | Контракт |
|---|---|
| `document create <kind> <slug> [--apply]` | Предпросмотр нового документа и индекса; запись только с apply, отказ при коллизии |
| `document register <path> --metadata <json> [--apply]` | Прицельное подключение существующего документа; показывает diff, не заменяет тело шаблоном |
| `document impact <document-id>` | Связанные требования, обратные отношения, задачи, материалы и потенциальные последствия; без записи |
| `document materials <owner-id>` | Текущие пути материалов и отображение старых путей из доказательств; без записи |
| `index --documents` / `index --all` | Индексы документов / документов и задач; прежний `index` сохраняет смысл индекса задач |
| `lifecycle plan <request.json> [--save]` | Проверяет и показывает точный diff завершения/архивирования; save сохраняет уникальный план и возвращает его путь |
| `lifecycle apply <plan.json>` | Применяет только неизменившийся валидный план, с backup, журналом и проверкой итогового состояния |
| `lifecycle status` | Показывает pending, владельца, живость операции и путь восстановления |
| `lifecycle restore` | После прерывания восстанавливает исходное состояние по проверенному backup; не принимает произвольный старый каталог операции |
| `close <ID> [--status done\|cancelled] [--dry-run]` | Сохраняет привычный вызов; строит операцию для одной карточки и её учтённых материалов, использует тот же механизм |
| `check --ready` | Дополнительно проверяет зарегистрированные документы, материалы, связи, состояние индексов; не доказывает смысл требований или независимость агента |

`close` с документами общего блока не угадывает область: их окончательный список приходит из явно подготовленного `lifecycle request`. Для современной карточки `close` требует запись приёмки; `cancelled` требует основания отмены, а не успешных тестов. Совместимость старых карточек описана в §9.

### Запрос операции и план

`request.json`: `schema_version`, `actor` (имя, модель либо null для инженера, роль, session/reference), `basis`, `scope`, `actions`. В actions допускаются:

- `close_task`: ID, итог `done/cancelled`, ссылка на приёмку/отмену;
- `archive_document`: ID, причина, преемник при наличии, ссылка на основание;
- `promote_change`: ID документа/изменения, итоговая редакция как строка payload в запросе, запись приёмки;
- `reopen`: ID, причина, связанный аудит/решение, статус возобновления;
- сопутствующие перемещения материалов и переписывания ссылок вычисляются и явно показываются в плане.

Payload разрешён только для зарегистрированного документа в scope, его хеш входит в план. Произвольные команды, произвольная запись файлов и удаление пользовательских данных через actions запрещены. План содержит полный набор входов (включая конфиг, scan-set ссылок, содержимое/состав каталогов и отсутствие будущих путей), их SHA-256, финальные байты/хеши записей, удаления старых путей, перемещения, проверки, временную метку и версию инструмента. При чтении план заново валидируется, его пути/действия сверяются с запросом и заново вычисленным результатом; JSON не считается доверенным только из-за наличия хеша.

Предпросмотр без save не пишет файлы. Save создаёт только служебный план в `work/lifecycle/plans/<id>.json`. Apply не использует «последний найденный» план. Сохранённые запросы/планы, необходимые как доказательство завершения, включаются в материалы владельца, без секретов.

## 7. Безопасная запись и восстановление

Многофайловую операцию не называем атомарной транзакцией ФС. Гарантия — проверка до записи, блокировка конкурирующих команд, журналирование и проверяемое восстановление пред-образа; до успешного завершения нельзя объявлять задачу закрытой.

1. Проверить синтаксис запроса/плана, пути, владельцев, причины, приёмку и допустимость переходов; определить точный набор чтения/записи.
2. Взять общую блокировку изменяющих команд проекта; проверить маркеры `update` и `lifecycle`. Повторно сверить входы, включая новые файлы и коллизии.
3. Создать каталог `work/lifecycle/<operation-id>/`, маркер `work/lifecycle/pending.json` с владельцем, долговременный журнал и автономный `restore.py`. Подготовить изменяемые файлы в staged-копии. Проверки не запускают команды из request/payload.
4. В staged-состоянии проверить карточки/зависимости, метаданные, ссылки, материалы, индексы и ожидаемые финальные хеши. Все применимые проверки до записи должны пройти.
5. Сохранить backup и индекс всех заменяемых/удаляемых путей: исходные байты, режимы доступа, хеши; отдельно — отсутствовавшие пути и созданные каталоги. Повторно сверить входы и полноту backup. Служебные записи сбрасываются на диск до изменения проектных файлов.
6. Записывать финальные файлы через временный файл в целевом каталоге и replace; удалять старые пути только после наличия проверенного нового содержимого. Записывать события, обновлять индексы в той же операции. Статус `done` на диске в промежуточной фазе не считается завершением, пока есть pending.
7. Повторить структурные проверки и сверку финального состава. Сохранить квитанцию с картой переносов/хешами, пометить completed, снять только собственный pending. Повторный apply этого же успешно завершённого плана сообщает completed и не создаёт второе архивирование.
8. При ошибке восстановить все затронутые пути, удалить только созданные операцией файлы/пустые каталоги, проверить пред-образ. При неполном восстановлении оставить pending и ненулевой результат. После прерывания доступен restore, повторяемый до полного восстановления.

Restore проверяет соответствие operation-id маркеру, принадлежность путей корню, точный состав backup, хеши и непересечение исходных/новых путей. Утрата копии, чужой pending или некорректный индекс — отказ без снятия маркера. Автономный восстановитель не импортирует файлы установленного комплекта. Журнал полезен для объяснения, но восстановление опирается на полный backup-index, а не на потенциально оборванную последнюю строку журнала.

Общий gate подключается к `close`, `index`, создающим/регистрирующим команды, `adopt --apply`, `update apply/restore` и lifecycle. `verify` удерживает тот же gate на время запуска как команда, создающая доказательства. Read-only status и подходящий restore остаются доступны при pending; обычный check не объявляет смешанное состояние готовым. Существующий update-lock/restore сохраняются, порядок блокировок фиксирован: общий gate, затем специализированный lock. Одновременно использовать старый CLI, не знающий общего gate, не поддерживается; запуск новой версии при старом update pending допускает только его восстановление/status.

Блокировка CLI не останавливает внешние редакторы. План проверяется при входе и непосредственно перед записью, но остаётся окно внешней правки после последней сверки. Во время apply не следует редактировать затронутые файлы. При восстановлении неожиданное содержимое, не совпадающее ни с пред-образом, ни с запланированным итогом, сохраняется как конфликтный материал и требует разбора; молчаливое уничтожение поздней внешней правки не допускается. Потеря всего каталога backup не покрывается обещанием восстановления; он не заменяет внешний бэкап.

## 8. Приёмка, идентичность входов и возвраты

В новой карточке есть запись передачи: состав проверяемого изменения, требования, ограничения, сценарии, ссылки на отчёты и отпечатки входов. `verify` остаётся проверкой исполнителя. Протокол аудитора — отдельная запись со временем, моделью, ссылкой на другую сессию или указанием инженера. CLI проверяет наличие и непротиворечивость записи; он не способен доказать личность человека или фактическую независимость произвольной сессии по самозаявлению.

Для closing нужны два разных снимка:

- **проверяемая реализация**: код, постоянные тесты, конфиги и содержательные требования в охвате аудита;
- **входы операции закрытия**: целые текущие документы, включая протокол и статус, индексы и материалы.

После добавления протокола hash всей карточки закономерно меняется. Для первого снимка допускается только объявленная проекция с исключением строго выделенного блока результатов аудита и служебных полей статуса/дат; цель, границы, приёмка, план, требования и сами списки входов всегда включены. Исключать карточку целиком нельзя. Для legacy без разделимых областей аудитор фиксирует полный снимок после записи протокола; CLI не ссылается на старый hash как на текущий. Артефакт снимка не включает сам себя, но его хеш входит в план закрытия.

Архивирование, переписывание ссылок и смена служебного статуса не считаются изменением продуктовой реализации. Все такие изменения перечислены в плане и проверяются как трансформация принятого состояния; новая редакция требований при promotion проверяется аудитором до apply и включается в область принятого diff. Любая иная правка содержательных входов требует повторной затронутой проверки/аудита.

При повторном аудите записи не затираются. Внутри активной карточки замечания возвращают её в `in_progress`. Находка итогового аудита в уже закрытой подзадаче требует управляемого `reopen`: история Closed/приёмки сохраняется записью события, текущий Closed сбрасывается, карточка и её локальные материалы возвращаются в активный каталог, ссылки/индексы пересчитываются тем же механизмом. Зависящие активные задачи и аудит блока, для которых зависимость перестала быть завершённой, возвращаются в `blocked` в той же операции, с причиной и прежним состоянием. Уже завершённые зависимые работы автоматически не переоткрываются: impact сообщает конфликт, инженер/аудитор определяет область нового разбора; apply не оставляет недопустимый граф статусов.

Для общей AUDIT-карточки различаем diagnostic (принятие протокола инженером не означает исправления всех находок) и acceptance (приёмка блока требует отсутствия блокирующих находок). Закрытие аудита не закрывает проверяемые карточки неявно: каждая заявлена в actions и имеет собственное основание.

## 9. Совместимость и внедрение

Верхняя схема `project.json` остаётся 1; `documents` — необязательная возможность с собственной схемой. Без неё старые установки продолжают читать существующие карточки/индекс и не получают массовой проверки нового формата. Подключение коллекций и преобразование ручных индексов показывается отдельным diff; `init` новых проектов создаёт согласованные шаблоны и конфигурацию.

Старые карточки можно закрывать с существующей шапкой и обычным текстовым протоколом по прежней политике. Запись выполняется новым восстанавливаемым механизмом, но наличие независимого аудита legacy-протокола остаётся человеческой проверкой и не объявляется машинно подтверждённым. Обнаруженные сопроводительные каталоги требуют явного учёта перед переносом; ради совместимости терять материалы нельзя. Завершённый исторический архив не переписывается массово и не обязан получать метаданные.

Новые модули/правила/шаблоны входят в управляемый состав manifest, проектные документы и evidence — нет. Переход версии объявляется в `updates.json`, проверяется существующим staged-контуром обновления; версия релиза определяется при планировании релиза, здесь не назначается. При правках файлов комплекта self-manifest обновляется по AGENTS.md; правки только проектных документов состава комплекта не меняют.

Пилоты: свежая установка; существующая 0.0.2 с собственными путями и документами; legacy-карточка без metadata; закрытый архив без новых полей; собственный репозиторий с незакоммиченными файлами; восстановление после ошибки. Конфликт чужого файла на месте нового индекса — остановка с diff, не перезапись.

Старый раздел обследования при изменении workflow переносится в отдельную справочную процедуру с пометкой «существующий порядок; переработка интеграции отложена». Это сохранение текущих функций, не проектирование новой интеграции. Удаление режима «Новый проект» не удаляет необходимые проверки setup_status.

## Уточнение контракта PB-026: AUDIT-006-A1/A2

Общее закрытие и архивирование плана проверяются по конечному графу всей операции. Каждая закрываемая карточка проходит собственные проверки приёмки и свежести; незавершённая задача плана вне scope запрещает перенос.

Для `promote_change` поле `acceptance` обязательно и содержит путь относительно проекта к JSON-протоколу. Формат: `schema_version: 1`, `document`, `change`, `revision` (исходная ревизия), `result: accepted`, `kind: acceptance`, `actor: {name, role: auditor|engineer}`, `at` (ISO-время с часовым поясом), `document_sha256` (SHA-256 исходного файла документа), `payload_sha256` (SHA-256 точной UTF-8 строки payload). Отсутствующая, отрицательная, diagnostic, чужая или устаревшая запись отклоняется до записи. Это проверка согласованности протокола, не удостоверение личности участника.

Протокол входит в snapshot входов плана; любое изменение после plan требует нового плана. Копия проверенной записи сохраняется внутри immutable companion `promote-<plan_id>.json`; принятый change ссылается на companion. История прежней редакции сохраняется. Концевые переводы строк тела при записи нормализуются по прежнему правилу CLI.
