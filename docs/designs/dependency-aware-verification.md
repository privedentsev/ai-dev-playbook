## Статус

Проект решения; реализация не начата. Основание — [требования R-01–20](../specs/dependency-aware-verification.md). [План](../plans/dependency-aware-verification.md), [ADR-0006](../adr/0006-dependency-aware-verification.md). Предложения API ниже ещё не существуют; PB-057 закрепляет их версии до разработки зависимых этапов.

## 1. Поток данных

```text
Одобренная политика + текущие файлы
  → inventory и снимок → анализаторы → граф с provenance/unknown
  → обязательства (task/release/all/stale) → выбор и explain
  → сравнение ключей результатов → reused / run / blocked
  → runner + адаптер → фактические outcomes → квитанция
  → общий gate handoff / accept / release-ready
```

Разделить обязательность (что должно быть подтверждено) и свежесть (какое доказательство подходит). Reused — способ получения покрытия, не новый запуск passed. Задачный scope может добавлять обязательства, но не сужать вычисленный по файлам набор. Проверка всех тестов не создаёт отсутствующие сценарии приёмки.

## 2. Интеграция с имеющимся кодом

- verification_policy.py сохраняет чистый расчёт coverage/reuse; добавить модели графа/обязательств отдельными модулями, не дублировать правила в lifecycle.
- verification.py сохраняет preflight, остановку process group и историю; новые adapters/discovery/results подключаются через версионированный интерфейс.
- lifecycle.py вызывает тот же расчёт для передачи, приёмки и готовности релиза; снимок операции закрытия остаётся отдельным от тестовых входов.
- project_view.py можно переиспользовать для чтения/состава, но не объявлять его песочницей исполнения: это read-only интерфейс, а тесты — исполняемый код.
- playbook.py получает preview/enable/plan/run/status-интерфейсы; согласованные имена и схема определяются PB-057. Нельзя добавлять неизвестные поля непосредственно в текущий task_workflow.schema_version=2: его валидатор строгий.

Новая политика хранится отдельным версионированным документом, ссылка включается явной миграцией проекта. Версии формата карточки, workflow, policy, receipt и протокола адаптера независимы. Старый CLI обязан отказать при активном неподдерживаемом режиме, а не silently fallback на legacy passed.

## 3. Предлагаемый формат политики

| Сущность | Поля и смысл |
|---|---|
| project | Устойчивая project_id, schema_version, trust_mode, approved_policy_digest |
| module | id, title, subsystem_id, paths; пересечение путей либо явное совместное владение, либо ошибка |
| check | id, title, purpose, kind=test/command/manual, modules, adapter, approved argv, timeout, inputs, applicability |
| dependency | consumer, dependency, kind, source=analyzer/explicit/observed, evidence, analyzer_version |
| exclude | path pattern, reason, origin, approval; конфликт с входом отклоняется |
| environment | toolchain/dependency identity, политика внешних сервисов и времени свежести |
| fallback | Порядок расширения, одобренные команды, лимит времени и правило для неизвестной оценки |
| test catalog | adapter, stable test_id, condition/expected description, group, discovery fingerprint, разрешённые skip |

Анализаторы не меняют argv и не исполняют найденные команды при обследовании. Python AST-анализ read-only; discovery unittest импортирует код и поэтому выполняется только как одобренная изолированная операция. Для неподдерживаемого языка нет фиктивной точной карты.

## 4. Inventory и снимки без Git

Обход всех не исключённых каталогов строит inventory путей/типов и правила принадлежности. Байты читаются только для объявленных и вычисленных входов; неизвестные файлы после fallback входят в консервативную область снимка. Отсутствующий вход фиксируется явно. Новый путь внутри glob учитывается через состав каталога, а не только прежний список файлов.

Хеширование потоковое, SHA-256, один файл один раз в одном устойчивом снимке. Удаление/ослабление правила исключения и сокращение списка входов сравниваются с одобренной политикой до расчёта кеша; неизвестное изменение политики блокирует reuse. Между запусками mtime/size не являются достаточным ключом кеша. Ошибка чтения/изменяющееся дерево → блокировка, не частичный success. Ссылки за пределы корня, циклические symlink и неоднозначные пути в первой версии отклоняются; тип файла и путь значимы. Внешние зависимости представляются отдельной identity, не неконтролируемым обходом диска.

.git и собственные runtime-каталоги исключаются явно. Нельзя исключить tests/docs/assets целиком из-за размера. Служебные поля карточки отделяются существующей semantic projection, но проверки структуры читают соответствующий полный документ. Долговечные evidence не помещаются в автоматически очищаемую runtime-историю.

## 5. Граф и алгоритм выбора

Ребро consumer → dependency означает: изменение dependency затрагивает consumer. Для выбора пройти обратные рёбра транзитивно. Использовать объединение прежнего и нового графа: удаление файла или импорта не должно терять прежних потребителей. Циклы сворачиваются в компоненты связности.

Unknown содержит причину и доказанную область: модуль/подсистема/проект. Если граница подсистемы не доказана, нельзя ограничивать fallback её именем. Прямой полный fallback допустим по одобренной политике; он не разрешает незнакомые команды и не снимает ограничения бюджета. Explain показывает цепочку changed path → dependency → check и reuse/run/blocked.

Для задачи сравнение включает baseline задачи и свежесть актуальных входов; для релиза область — все обязательные checks. Потеря baseline → широкая применимость. Потеря графа/неизвестная независимость → связанные кеши не используются. Если группа остаётся доказанно независимой, расширение списка само по себе её результат не отменяет.

## 6. Ключ результата и история

Ключ проверки включает project_id, stable check ID, definition/adapter/runner version, входы и их состав, dependency closure, значимую проекцию политики, среду и применимые task requirements. Не хешировать всю политику для каждого независимого изменения, но глобальные обязательства и trust revision учитывать обязательно. Смена карты расширяет closure до решения о reuse.

Хранить append-only результаты с исходным run_id/time, фактическими test IDs/outcomes, input digest, логами и provenance. Индекс кеша — производный: повреждение → восстановление из проверенных записей или новый прогон. Последний failed/timeout/not_run для того же обязательства не маскируется старым passed; очистка не превращает удалённую историю ошибок в разрешение старого reuse. Индекс последовательности/актуального результата защищён на стороне доверенного сервиса.

Общие результаты можно использовать между задачами; требования новой задачи покрываются отдельным binding/scenario. Изолировать кеши проектов и доверенных сред. TTL проверяет доверенный clock; откат локальных часов не продлевает внешнее доказательство. Секреты и значения чувствительной среды в отчёт не записывать.

## 7. Адаптер unittest и понятные отчёты

Адаптер выдаёт ожидаемый catalog IDs и actual results через TestResult: started/success/failure/error/skip/expected failure/unexpected success/subtests. Политика явно определяет допустимые skip/expected failure; неожиданный успех ожидаемого падения не превращается автоматически в зелёный результат. Дубликаты, неполный набор, crash и ноль обязательных тестов блокируют passed.

Описание хранится рядом с тестом либо в каталоге адаптера с привязкой к stable ID. CLI требует непустое описание и показывает условие/ожидание; смысловую истинность названия он не доказывает. Переименование ID — изменение набора; массовое переименование тестов не требуется, можно добавить описания существующим IDs. Одобренный каталог обнаруживает удаление/skip, а изменение assertions остаётся предметом независимого анализа.

kind=command предназначен для сборки/линтера с определённым postcondition/exit-контрактом; нельзя пометить тестовый suite как command ради обхода inventory. kind=manual сохраняет факты и ограничения v2, не получает автоматическую доверенную подпись о просмотре человеком.

## 8. Защищённый контур

Локальные файлы не могут аутентифицировать владельца. Режим local выдаёт диагностические результаты с честным trust=local. Режим protected принимает только квитанции от отдельно контролируемого verifier.

Verifier работает вне прав агента: одобренная политика, закреплённый runner/adapter, доверенный журнал и ключ находятся вне доступной ему записи. Исполняемые тесты запускаются как недоверенный процесс без доступа к ключам, политике и управлению verifier; контейнер под тем же доступным агенту daemon сам по себе границей не считается. Минимальный deploy contract требует отдельной OS identity или CI с раздельными правами и недоступными тестам секретами. Выбор конкретного хостинга не входит в подготовку.

Протокол: инженер через независимый канал одобряет digest политики → сервис проверяет candidate manifest → материализует изолированный снимок → сам вычисляет inventory/graph/plan → запускает одобренный adapter → проверяет результат → подписывает receipt. Проверяется project_id, candidate_digest, policy revision, engine identity, outcomes/log digests и issuer. Не принимать сообщённый агентом digest без сверки байтов. Ключ/allowlist нельзя заменить редактированием project.json. Для reuse между кандидатами verifier заново сверяет per-check входы, граф и политику и выпускает агрегированное подтверждение текущего candidate с ссылками на исходные receipts; старый receipt не переименовывается и не выдаётся за запуск на новых байтах. Запрос force/budget override не может выдавать разрешение на иные команды.

Квитанция доказывает происхождение и выполнение, но не семантическую добросовестность тестов. Даже runner вне проекта не делает произвольный тест честным: анализ ослабления assertions и соответствие требованиям остаются отдельным контролем. Сервис никогда не подписывает присланный клиентом итог как собственный запуск.

Потребитель релиза также проверяет доверенный gate. Локальный агент может переписать свой CLI, поэтому локальная надпись release-ready не обеспечивает блокировку внешнего выпуска. Эталонный consumer и инструкция подключения входят в PB-061/062; публикация и настройка реальных аккаунтов — отдельное поручение.

## 9. Предлагаемый пользовательский интерфейс

Это обозначения семантики, не работающие команды; PB-057 закрепляет окончательный синтаксис:

- setup preview/apply: обследование, неизвестные пути, diff политики, независимое одобрение.
- checks plan TASK: read-only объяснение required/reused/run/blocked и стоимости.
- checks run TASK --mode stale: выполнить обязательства задачи без пригодных результатов.
- checks run RELEASE_TASK --checkpoint release --mode stale: все релизные обязательства, reuse разрешён.
- checks run TASK --scope project --mode force: весь набор заново по явному поручению.
- checks status TASK: покрытие, фактические проверки и ограничения доверия.

Область task/project и режим stale/force не смешиваются. Неопределённое «перезапусти тесты» разрешается по контексту задачи либо уточняется; явное «все» всегда force. CLI не создаёт карточку на каждый запуск: текущая задача владеет прогонами; самостоятельная проверка и релиз получают обычную карточку при постановке. Название коммита не распознаётся как авторизация выпуска.

## 10. Включение, восстановление и проверка

PB-063 делает явный opt-in с сохранением прежних обязательных checks. Схему/отчёты нельзя менять задним числом; unknown format отклоняется. Preview не пишет и не запускает discovery-код. Apply/миграция через существующие gate/recovery; новые результаты только в совместимом формате. Старые local-результаты не импортируются как protected.

Проверки: матрица AC-01–11 спецификации, isolated temporary projects, subprocess counters, fault injection, forged receipts, read/write denied под реальной отдельной identity для подтверждения защиты. Без доступного изолированного окружения тест протокола можно выполнить локально, но защищённая эксплуатация остаётся неподтверждённой и этап не заявляет её готовность. Эффективность измеряется количеством команд и прочитанных байтов; нет обязательства фиксированного процента ускорения.
