## Статус

Планируемая архитектура; код не изменён. [Требования](../specs/scoped-file-operations.md), [ADR](../adr/0005-scoped-file-operations.md), [план](../plans/scoped-file-operations.md). Техническая детализация предназначена для реализации после отдельного разрешения; не является приёмкой поведения.

## Планируемое решение

### 1. План и подготовка на диске

Разделить данные операции: read-set (прочитанные файлы и снимки состава коллекций), write-set (конечные пути с источниками подготовленных байтов), removes и directory-actions. Ввести уникальный идентификатор выдачи плана отдельно от хеша содержимого. Хеши исходных байтов фиксируются при чтении, а не повторным несвязанным чтением после построения результата.

Новые версии лежат в work/lifecycle/<op>/staged/<конечный путь> либо work/update/<op>/staged/. Сами планы содержат пути, размеры и хеши, а не все payload в RAM. Крупные материалы копируются и хешируются потоково. Адаптировать не только engine, но и вызывающие функции, сейчас собирающие writes как dict[rel, bytes]. Не сохранять большие исходные/новые версии одновременно в памяти.

### 2. Представление будущего состояния

Ввести узкий read-only интерфейс ProjectView: чтение текста/байтов потоком, exists/is_file/is_dir, список путей каталога, безопасное разрешение ссылок. Реализации: текущее дерево и FutureView(root, staged, plan). FutureView сначала проверяет write-set/removes/directory-actions, затем читает неизменённый путь из root. Удаление и перенос скрывают исходный путь; перечисление объединяет исходные имена с добавлениями и исключает удаления. Относительные ссылки разрешаются относительно конечного документа.

Проверки task_cards/documents/document_links и каталога используют этот интерфейс; нельзя передавать staged как самостоятельный полный root. Отсутствующий dependency не маскируется пустым файлом. Ссылку на неизменённый исходник можно проверить через exists, не загружая код. Изменение прочитанного файла или состава коллекции обнаруживается снимком. Не делать symlink/hardlink-копии живых изменяемых файлов: они связывают запись с оригиналом.

Сначала реализовать API и проверки без переключения рабочих команд, затем включить engine. Сравнить результаты FutureView с физически построенным ожидаемым деревом на небольших тестовых fixtures; полная копия допустима в тестовом oracle, но отсутствует в рабочих операциях.

### 3. Протокол записи

Последовательность: план → staged → precheck → сверка read-set → поздний backup → валидация backup и staged → повторная сверка read-set → записи/удаления → финальные проверки на реальном дереве → receipt/completed → снятие pending → cleanup под gate.

Shared gate удерживается при подготовке/применении и служебных переходах; специализированные locks берутся в текущем порядке. До первой записи существуют полный backup-index, пред-образы и автономный restore. Файлы/метаданные восстановления сбрасываются на диск в правильном порядке; успешность отдельного replace не объявляется атомарностью всех файлов. Конкретный контракт fsync и доступные гарантии платформы зафиксировать тестами и описанием.

Backup индексирует файлы и каталоги, права, absent/added, прежние и ожидаемые итоговые хеши. Записывать из проверенного staged потоком через собственный temp+replace; повторно сверять фактический итог. Обычная ошибка после записи запускает rollback. Прерывание до/после записи различается устойчивой фазой; lost/corrupt metadata не разрешает опасный pre-write fast-path. Сохраняются защита временных файлов, владелец pending и независимость restore.py от установленного кода.

### 4. План, квитанция и ограниченная история

Квитанция receipt фиксирует завершённую операцию; её наличие само по себе не доказывает соответствие текущего дерева. Для saved plan нужен компактный реестр только живых планов: уникальный ID, digest содержимого/read-set, вид операции, состояние и ссылка на operation. Его целостность и запись защищены gate и атомарной заменой. Исторические записи удаляются вместе с окончанием срока действия плана; бессрочные tombstone не требуются.

Новый прямой запрос выдаёт новый ID под gate. Preview остаётся read-only, save регистрирует конкретный план. apply принимает лишь зарегистрированный ID с точным digest; отсутствие/повреждение реестра — отказ, а не автоматическая регистрация переданного JSON. Повтор completed проверяет целевое состояние: совпадение — already_completed, расхождение — устаревший план и предложение нового запроса. После rollback нужен новый план. Новый запрос при уже достигнутом результате даёт no-op без долговечной операции; совпадение хеша старого желаемого результата не блокирует новое изменение (регрессия PB-042).

Перед очисткой revoke старого плана фиксируется устойчиво; только затем удаляются его receipt/backup и сохранённый исполнимый экземпляр. Скопированный наружу JSON после revoke не получает право исполнения. Материал-доказательство с содержимым плана может остаться у владельца, но не является авторизацией apply. Явное expire/cancel удаляет неисполненный план из реестра; очистка терминальной истории не должна копить отдельную безграничную историю идентификаторов. Ошибка cleanup допускает состояние «старый план уже недействителен, каталог ещё сохранён».

### 5. Настройка и совместимость

Единственная настройка — storage.backup_retention_count, обязательный integer >=1, исходно 15. Конфигурацию не дублировать отдельным файлом. Обычные изменяющие команды новой версии при missing/invalid завершаются до создания operation; read-only диагностика сообщает ошибку, restore остаётся доступным. Предлагаемый интерфейс ремонта: storage configure --backup-retention-count 15 --apply (без --apply только diff). Это узкая восстанавливаемая операция установки настройки, без запуска GC до валидного значения; не обход для других изменений.

Init нового комплекта записывает явное значение из шаблона. Миграция старой установки в update показывает добавление 15 в diff, только если поле отсутствует; валидное пользовательское значение сохраняется, некорректное требует исправления. Миграция и bootstrap должны переживать SIGKILL и не требовать уже существующего параметра для restore. Self-project и шаблон меняются в PB-047, сейчас рабочая конфигурация остаётся прежней.

Существующие pending/backup обрабатываются старым форматом до переключения; старые исполняемые планы не импортировать молча. Существующие архивные evidence не переписывать. Согласовать зоны verification.py/lifecycle.py/updating.py с PB-031–PB-037 и PB-041/PB-044 при старте, не меняя их приоритетов и не объявляя их выполненными.

### 6. Обновление комплекта

Отдельный adapter использует те же принципы без немедленного объединения всех legacy backup-форматов. Кандидатный CLI загружается из проверенного локального релиза, а FutureView передаёт мигрированные настройки и будущий каталог. В рабочую область допускаются необходимые исполняемые файлы кандидата и новые версии управляемых файлов; вся исходная codebase/tests/media не копируется. Выборочная зависимость явно объявлена, несоответствие — ошибка до записи; fallback на copytree(root) запрещён.

Новый контракт update: структурная совместимость кандидата обязательна до записи; recovery покрывает перечисленные файлы комплекта, настроек и документов. Пользовательские verification-команды отделены в verify и не выполняются скрыто внутри update или автоматически на основном проекте. В плане обновления явно показать смену этого контракта: прежние staged product checks больше не входят в результат обновления, ожидаемые проверки продукта перечислены как отдельный шаг. Старый CLI, применяющий переходный релиз, может ещё использовать прежний staged-протокол; подтвердить этот переход локальным fixture и не обещать изменения старого исполняемого кода задним числом.

### 7. Очистка и конфликты

Предлагаемые команды: storage status; storage cleanup (preview); storage cleanup --apply; storage resolve-conflict <op-id> --path <путь> --apply. Resolve подтверждает разбор и сохранение нужной версии; не выбирает содержимое автоматически и не применяет его к проекту. Сначала пользователь/агент по отдельному поручению переносит нужные данные, затем подтверждает обработанные конфликты. Cleanup при read-only запросе не запускается.

Единый список завершённых lifecycle/update сортируется по completed_at/op_id. Последние N обычных операций сохраняются целиком. Pending, живые locks, unresolved conflicts, неизвестное/повреждённое состояние и зарегистрированные evidence защищены и показаны отдельно с причиной/действием; превышение лимита из-за защиты явно видно. Долговечные материалы новых операций помещаются в owner-evidence до handoff, а не удерживаются ссылками внутри operation. Legacy-ссылки сначала требуют явного переноса/регистрации по обычному lifecycle; GC сам не переписывает принятую историю.

Очистка под shared gate: классификация → повторная проверка защищённости → revoke plan → фиксация списка удаления → удаление только проверенных принадлежащих operation путей. Прерванное удаление распознаётся по собственному GC-состоянию и продолжается, не трактуется как pending предметной операции. Не обходить symlink и не трогать неизвестные файлы/чужие каталоги. После завершения удалять временное GC-состояние; не создавать бесконечные tombstones. Ошибка даёт warning после completed, а не rollback предметной операции.

Удаление staged возможно после подтверждённого terminal state; при pending оно защищено. При pre-write отказе без backup подготовка очищается без долговременной записи. После восстановленной операции с backup история считается завершённой. Снижение N показывает последствия в preview; следующие разрешённые cleanup применяют новое значение.

### 8. Проверки и пределы

Матрица требований — в спецификации. Все поведенческие испытания локальные: temporary projects, synthetic files, subprocess SIGKILL, повреждение метаданных, конкурирующие команды и внешняя правка. Большой реальный проект/внешний пилот не требуется. Факт отсутствия копирования проверять составом staged и инструментированными чтениями, не только секундомером. Для streaming использовать ограниченный синтетический файл и контролируемое чтение, без требования гигабайт RAM/диска.

Сохраняется окно внешней гонки между сверкой и записью; shared gate защищает только участников CLI. Полный сбой питания не равен SIGKILL. Количество операций ограничено, размер одного зарегистрированного материала — нет. Tests продукта и доказательства приёмки имеют собственное хранение и не входят в GC этого блока.
