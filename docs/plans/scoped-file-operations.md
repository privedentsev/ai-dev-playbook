## Проверки и доказательства

Каждая задача содержит наблюдаемую приёмку, целевые тесты, затем текущий verify и свежую передачу. Проверить index --all, check --ready и diff; после изменения файлов комплекта обновить self-manifest. Структурный PASS не заменяет fault injection или проверку реального CLI. Полный набор тестов запускается с достаточным временем и диагностикой; заданный сейчас timeout unit-tests 600 секунд нельзя выдавать за успешный результат при превышении.

Материалы каждой задачи принадлежат ей, общие сквозные результаты — PB-050, независимые — AUDIT-008. До handoff зарегистрировать нужные immutable материалы. GC не касается evidence/verification и ссылок на принятые доказательства. Ни audit, ни исполнители не требуют предоставления инженером большого реального проекта: достаточно локальных временных fixtures и синтетических входов.

## Переход, риски и завершение

До реализации сохранить совместимость прежнего restore. Missing новой настройки не должен блокировать восстановление; default запрещён, явный bootstrap/migration обязателен. Договорённость о verify при update отражается в preview и документах до переключения. Исторические каталоги не удалять по одному возрасту: сначала классификация, признаки завершения и проверка ссылок/конфликтов.

Риски: неполный read-set, ошибочное перечисление FutureView, поздняя внешняя правка, разрыв receipt/GC, рекурсивное удаление чужого пути, остановка во время очистки. Покрываются сценариями спецификации и отдельным аудитом.

Завершение блока: задачи реализованы и независимо приняты; AUDIT-008 подтверждает AC-01–10; открытых блокирующих замечаний нет. Затем по явному разрешению закрываются карточки/план штатным lifecycle с проверкой архива и ссылок. При подготовке планирования ничего из этого не объявляется выполненным.
