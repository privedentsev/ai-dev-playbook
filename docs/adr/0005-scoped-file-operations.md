## Контекст

Полная копия подключённого проекта ради операции над документами требует места/времени, зависящих от чужих данных. Точечный backup и восстановление уже есть. Нужно сохранить проверку будущих ссылок и индексов до записи, ограничить историю и не зависеть от чистого Git-дерева.

## Планируемое решение

Выборочный staged на диске с новыми версиями затрагиваемых файлов; read-only FutureView объединяет его с неизменяемой частью основного проекта. Поздний backup после precheck и сверки входов, проверка backup, повторная сверка, точечное применение и финальная проверка. Откат сохраняет незакоммиченный пред-образ; Git отвечает за историю разработки.

Обязательное storage.backup_retention_count первоначально 15; runtime-default отсутствует. После терминального состояния staged удаляется. Последние N обычных завершённых операций lifecycle/update хранятся целиком; старые удаляются с отзывом права исполнения сохранённого плана. Незавершённые/конфликтные и защищённые доказательства требуют разрешения причины до GC. Бессрочные квитанции не вводятся.

Настроенные проверки продукта отделяются от update; план обновления явно отражает смену гарантии. Новый контракт не объявляет их пройденными по структурному успеху. Подробности — [design](../designs/scoped-file-operations.md).

## Альтернативы

- Полный staged с немедленной очисткой: устраняет накопление, но сохраняет стоимость копирования всей codebase.
- Все новые версии в памяти: проще для маленьких текстов, но требуется отдельный контроль больших материалов и сложнее осмотр.
- Только запись в основной проект с последующей проверкой: увеличивает количество откатов и теряет предварительное обнаружение документных ошибок.
- Ранний backup: безопасен при тех же сверках, но делает лишнюю копию при precheck-отказе; преимуществ для выбранного порядка нет.
- Git reset как восстановление: не сохраняет незакоммиченный пред-образ и может затронуть чужие изменения.

## Последствия и статус

Инженер согласовал направление и подготовку до задач, но запретил выполнение на данном этапе. ADR остаётся draft; архитектурная детализация подлежит проверке при реализации и независимом аудите. Реальный большой проект не является условием приёмки; испытания выполняются локально на временных проектах.
