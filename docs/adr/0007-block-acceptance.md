## Контекст

Строгое требование done на каждом ребре не позволяет агенту выполнить связанный план до единого независимого аудита. Reopen старой задачи ради нового дефекта может потребовать возврата завершённой цепочки. Одновременно поздняя реализация способна сделать доказательства ранних задач историческими.

## Предлагаемое решение

1. Выбирать per_task/final/mixed при согласовании плана; по умолчанию сохранять прежнюю строгую приёмку.
2. Сохранить Depends-On как done; добавить явные внутренние рёбра checked handoff и checkpoints. Один evaluator для всех gate и будущего графа.
3. Принимать совместный результат по immutable пакету конечного candidate и матрице всех критериев, сохраняя историю индивидуальных передач.
4. Создавать новую задачу исправлений на итерацию отрицательного аудита; старый архив не менять. Reopen — явное исключение пересмотра закрытия.
5. Использовать существующий lifecycle/recovery для общей приёмки и архивирования. Разрешение выполнения/закрытия и независимость аудита сохраняются.

## Рассмотренные альтернативы

- Оставить только аудит каждой задачи: сохраняет остановки, которые инженер хочет убрать.
- Считать in_review равным done: даёт ложную приёмку и не подтверждает актуальные проверки.
- Только отменить проверку зависимостей у start: оставляет несовместимые gate handoff/check/accept/close и циклы.
- Закрывать задачи исполнителем до общего аудита: скрывает отсутствие независимой приёмки.
- Переписывать ранние handoff после поздних правок: теряет историю и provenance.
- Всегда reopen исходную цепочку: смешивает новую коррекцию с историей принятого результата.

## Последствия

Нужны схема политики, типизированные рёбра, конечный review package, общая приёмка и obligations исправлений. Выбор final сокращает остановки, но переносит независимую оценку на конец; риск ограничивается checkpoints, самопроверкой и консервативной регрессией. Экономия числа аудитов не обещает отсутствие повторных тестов.
