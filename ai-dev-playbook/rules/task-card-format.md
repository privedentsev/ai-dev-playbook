# Формат Markdown-карточек

Новые карточки создаются по `templates/task.md` с `card_format_version: 2` внутри playbook-meta. Это версия Markdown, независимая от `schema_version` служебного JSON и workflow/verification v2. Старые файлы не мигрируются: прежний CLI продолжает их обслуживать; `card show <ID>` / `card show <ID> --json` возвращает для отсутствующей, явной 1 или неизвестной будущей версии unsupported и путь исходного Markdown. Будущее приложение может открыть этот файл напрямую. Невалидный маркер версии (строка, null, bool, неположительное число) — ошибка.

## Задача

Шапка сохраняет ID, Status, Priority, Depends-On, Executor, Model, Created, Closed. Неизвестные, повторные поля и посторонние строки в шапке отклоняются парсером. Два раздела второго уровня: `## Задача` и `## Журнал`.

В задаче ровно пять подразделов третьего уровня в этом порядке: Цель и границы, Контекст, Критерии приёмки, План, Ресурсы. Любые другие структурные заголовки вне fenced-примеров отклоняются валидатором. Их содержимое непустое. Критерии задаются строками `- [ ] AC-01: описание`; ID уникальны. Галочка [x] — вычисляемое подтверждение актуальной проверкой, не независимая приёмка. Вручную её не редактировать. Прежний v2 с `- AC-01: описание` читается; только целевой card sync/handoff переводит его на галочки. Не добавлять критерий «аудит проведён»: приёмку подтверждает служебная acceptance актуальной передачи. Условия проверки продукта остаются критериями; их подтверждение записывается в проверках/аудите через ID.

## Журнал

Каждая запись начинается с `### <ID> — <Название>`. ID уникален внутри карточки; номер положительный, минимум две цифры. Пустой журнал допустим для новой задачи. В каждой записи обязательны:

```text
Время: 2026-10-24T12:00:00+03:00
Исполнитель: Codex
Модель: GPT-6.1 Sol
```

Время — ISO с часовым поясом. Имя и модель точные, для инженера модель `—`; правила маркера `(не подтверждено)` сохраняются. Порядок полей свободный. Поле записывается `Название: значение` либо `Название:` и затем текст/список/код. Продолжение, похожее на новое поле, отступить пробелами. Fenced-примеры не создают записи/поля. Неизвестные/повторные/пустые поля, другие заголовки и неразрешённые ссылки отклоняются валидатором. Произвольные пояснения помещаются внутрь соответствующего поля.

| Заголовок | Обязательные поля помимо атрибуции | Дополнительные поля |
|---|---|---|
| EXEC-01 — Выполнение | Изменения, Файлы | Замечания |
| EXEC-02 — Исправление | Изменения, Файлы, Замечания | — |
| CHECK-01 — Проверка | Результат, Критерии, Среда, Факт, Доказательства, Ограничения; минимум Команда или Сценарий | Команда, Сценарий |
| HANDOFF-01 — Передача | Выполнение, Проверки, Состояние, Фокус аудита | — |
| AUDIT-01 — Аудит | Передача, Результат, Критерии, Независимо проверено, Доказательства, Ограничения | Закрытые замечания, Замечания |

Результат проверки: passed, failed, not_run. Результат аудита: accepted, changes_requested. Ссылки перечисляются через запятую: `Критерии: AC-01, AC-02`. Локальные связи указывают предыдущие записи нужного типа. Передача требует passed-проверок. Аудит относится к последней передаче; после новой работы сначала нужна новая передача. Межкарточные ссылки оформляются обычными Markdown-ссылками в описаниях, без смешивания с локальными ID.

Исправление — разновидность выполнения: второй/третий EXEC называется «Исправление» и ссылается на находки. Новая проверка/передача/аудит добавляются новыми записями. EXEC описывает изменения реализации, причины существенных решений/компромиссы и файлы; команды, фактические результаты, доказательства и ограничения проверки находятся в CHECK. Последняя HANDOFF не пересказывает выполнение и тесты: явные ссылки на все нужные EXEC/CHECK, текущее состояние со следующим шагом и конкретный фокус проверки. Она достаточна для продолжения работы вместе с задачей и связанными записями: за обязательным контекстом нельзя отправлять в прежнюю HANDOFF. Это правило для новых записей, без эвристических запретов свободного текста и переписывания истории. Доказательства лежат в материалах, в карточке — ссылки на них. Не копировать свободный текст журнала в JSON.

## Пример записей

```markdown
### EXEC-01 — Выполнение
Время: 2026-10-24T12:00:00+03:00
Исполнитель: Codex
Модель: GPT-6.1 Sol
Изменения: добавлен preview.
Файлы:
- example.py

### CHECK-01 — Проверка
Время: 2026-10-24T12:10:00+03:00
Исполнитель: Codex
Модель: GPT-6.1 Sol
Результат: passed
Критерии: AC-01
Команда: `python3 -m unittest discover -s tests -v`
Среда: Python 3.12; временный проект.
Факт: 8 тестов пройдено.
Доказательства:
- [Журнал](TASK-001-evidence/tests.log)
Ограничения: проверено на macOS.

### HANDOFF-01 — Передача
Время: 2026-10-24T12:15:00+03:00
Исполнитель: Codex
Модель: GPT-6.1 Sol
Выполнение: EXEC-01
Проверки: CHECK-01
Состояние: dev; изменения не закоммичены; следующий шаг — независимый аудит.
Фокус аудита: preview не должен менять файлы.

### AUDIT-01 — Аудит
Время: 2026-10-24T12:30:00+03:00
Исполнитель: Инженер
Модель: —
Передача: HANDOFF-01
Результат: changes_requested
Критерии: AC-01
Независимо проверено: preview на пустом каталоге.
Доказательства: журнал независимой CLI-пробы.
Ограничения: проверен один сценарий.

#### A-01 — Замечание
Серьёзность: P2
Критерии: AC-01
Проблема: preview создаёт каталог.
Воспроизведение: запустить preview на пустом проекте.
Факт: появился каталог output.
Влияние: нарушено отсутствие записи.
Критерий исправления: дерево проекта не меняется.
```

Находки находятся внутри соответствующего AUDIT: ID `A-01`, заголовок четвёртого уровня, поля Критерии (AC-ID через запятую), Серьёзность (P0–P3), Проблема, Воспроизведение, Факт, Влияние, Критерий исправления. ID уникальны по карточке. changes_requested требует находку. accepted запрещён при открытых находках.

Далее добавляются EXEC-02 — Исправление (`Замечания: A-01`), CHECK-02, HANDOFF-02, AUDIT-02. В AUDIT-02 поле `Закрытые замечания: A-01` разрешается только после записи исправления; старую находку не редактировать. Третье исправление — EXEC-03 — Исправление. Все поля атрибуции повторяются у каждой записи.

## Связь с CLI и защита истории

До финального verify исполнитель подготавливает статус in_review и индекс по [порядку проверки](verification.md#подготовка-финального-verify). После успешного verify дописывает CHECK и самостоятельную HANDOFF, затем запускает обычный `lifecycle handoff <ID> --summary HANDOFF-01 --actor <имя> --model <модель>`. В формате 2 CLI хранит summary как ID передачи, `entry_id` и `journal_sha256`; имя/модель должны совпадать с записью. Этап завершён только при свежей зарегистрированной передаче; подготовленный in_review этого не подтверждает.

Независимый аудитор дописывает AUDIT, затем выполняет `lifecycle accept`: для result=accepted нужен последний accepted-аудит актуальной передачи и совпадающая атрибуция. Для инженера используются `--role engineer --actor <имя>`, модель в журнале `—`, аргумент --model опускается. Сохраняются `audit_id` и `audit_sha256`. Протокол сам по себе не открывает close. Отдельная сессия/роль остаются процессным требованием; CLI не удостоверяет личность.

Проекция сохраняет требования, исключая журнал. Отдельный хеш защищает переданную историю до HANDOFF включительно; добавление аудита не делает передачу несвежей. Правка старых записей, новые EXEC/CHECK/HANDOFF, изменение требований/реализации требуют повторных проверок и передачи. Close проверяет обе связи, хеши, freshness и прежние gate; после accept обязателен close --dry-run, реальное закрытие — по команде инженера.

`card show --json` возвращает разделы, критерии, записи, находки, ID последней передачи/аудита, открытые находки и acceptance_state: current либо not_current с причиной. Current подтверждается проверками close evidence, включая свежесть verify. Для архива — historical: текущее соответствие перемещённых файлов прежним снимкам не утверждается. Последний текстовый accepted не равен актуальной приёмке CLI.

Служебные события close/reopen хранятся в существующих immutable companion-материалах и шапке; не подмешиваются в авторские записи журнала. Reopen очищает текущие handoff/acceptance, сохраняя старые записи в журнале и историю в материалах. Старые Markdown-карточки и их доказательства не переписывать ради нового просмотра.

## Вычисляемые чекбоксы

`card sync <ID>` показывает план без записи, `card sync <ID> --apply` сохраняет его через общий gate, staged/final checks и rollback. Перед verify выполняется сброс устаревших отметок (без привязки новых CHECK), затем runner делает снимок. После verify добавьте CHECK и HANDOFF: handoff автоматически привяжет новые проверки и пересчитает галочки. После changes_requested выполните card sync --apply: affected-критерии станут [ ]; после повторного accepted-аудита lifecycle accept также синхронизирует отображение. Исправление без новой проверки не возвращает [x].

Расчёт един для файла и JSON (`criterion_states`, `checkbox_mismatches`, `rendered_markdown`). Последний CHECK каждого критерия определяет результат. [x] требует passed, свежего неизменённого отчёта verify, неизменённых CHECK/требований, отсутствия новой EXEC после CHECK и открытой находки по критерию. Отсутствие проверки, failed/not_run и устаревание дают [ ]. Находка приоритетнее passed до закрытия повторным аудитом. Новая EXEC консервативно требует перепроверки критериев; область влияния кода автоматически не угадывается. Одна находка сама по себе не сбрасывает незатронутые критерии.

В JSON-метаданных `criterion_evidence` CLI хранит только ID отчёта и хеши CHECK, требований и отчёта; текст/результат проверки не дублируется. Новая CHECK привязывается один раз к свежему успешному verify при sync/handoff. Новое verify само по себе не перепривязывает старый CHECK: добавьте новую CHECK-запись. Переписывание старого CHECK/отчёта не восстанавливает отметку. Для старых находок без AC-связей при явном переводе прежнего v2 CLI сохраняет только их ID в checkbox_legacy_findings и использует критерии исходного аудита; история не редактируется. Новые находки обязаны указывать Критерии явно.

Нормализуются только галочки в настоящем разделе критериев — в проекции требований и в снимках verification. ID/текст, примеры в fenced-блоках, история журнала и другие файлы защищены прежними отпечатками. Добавление служебных привязок/протокола собственной карточки учитывается через её проекцию и хеши журнала; прочие входы verify не исключаются. Синхронизация не делает старый accepted актуальным.

Read-only card show ничего не пишет: показывает вычисленное состояние и расхождения с файлом. check отклоняет расхождение с подсказкой card sync --apply. Архив показывает историческое подтверждение без заявления о текущей свежести; reopen очищает текущие привязки и снимает отметки. Массовой миграции прежних карточек нет.

## Внешнее хранение метаданных новых карточек

Новая карточка создаётся командой `python3 ai-dev-playbook/scripts/playbook.py card create <ID> --title "Название" --apply`; без `--apply` — preview. Создаются `<ID>.md` и соседний `<ID>.meta.json`, обновляется индекс одной восстанавливаемой операцией. Для команды требуется настроенный раздел documents. При ручном использовании шаблона необходимо копировать оба файла (`templates/task.md` и `templates/task.meta.json`), согласовать ID/имя Markdown и заполнить Created.

Маркер `<!-- playbook-meta:external -->` в шапке Markdown указывает на обязательный соседний JSON. JSON содержит прежние служебные метаданные, без копии шапки, требований и журнала. Разбор/валидация, verify, sync, handoff/accept и close/reopen читают одну пару; перенос в архив включает оба файла. JSON не является evidence или кэшем. Потеря/повреждение, symlink, orphan и два источника — ошибки, не основание для пустого состояния. Существующие inline/legacy-карточки продолжают работу без миграции; весь архив не переписывается. Не перемещайте и не редактируйте служебное состояние вручную.

Сокращённая пара `templates/task-quick.md` / `templates/task-quick.meta.json` сохраняет те же пять подразделов, шапку и формат журнала. Создание через `card create --template quick` требует явно включённый workflow v2, --reason и --verification-plan; формат Markdown и workflow.schema_version не взаимозаменяемы. Маршрут и план проверок не дублируются в тексте. [Порядок](tasks.md#сокращённая-обычная-карточка-quick).
