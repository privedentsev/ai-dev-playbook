# Режимы работы

| Просьба | Режим | Результат |
|---|---|---|
| Обсудим идею | Обсуждение | Варианты, ограничения, вопросы |
| Запиши задачу | Запись | Краткий draft, без реализации |
| Спланируем | Планирование | Предложенный план, зависимости, критерии приёмки |
| Начинаем проект | Новый проект | Продукт, архитектурные предложения, карта, первый набор задач |
| Подключи к проекту | Обследование | Проверенные факты, расхождения, адаптированные документы |
| Выполни задачу | Выполнение | Реализация и доказательства проверок |
| Проверь / аудит | Аудит | Замечания, серьёзность, воспроизведение, критерии исправления |

Режим выводится из запроса. «Проверь и исправь» разрешает исправления; отдельный аудит — нет. Планирование не запускает кодирование. Явный запрос инженера может одновременно принять план и разрешить выполнение: не просить повторного подтверждения. Крупную задачу при планировании разделяй на подзадачи с аудитом блока по [правилам задач](tasks.md).

## Режим в ответе

Первое сообщение на каждый запрос инженера и итоговый ответ начинай с `Режим: <название>`; название бери из таблицы выше. Если ответ состоит из одного сообщения, достаточно одной метки. В промежуточных сообщениях повторяй метку только при смене режима.

Для составного запроса указывай режим текущего этапа, при переходе — новую метку. Метка описывает работу и не даёт разрешения на действия: границы планирования, аудита и выполнения сохраняются.

## Новый проект

1. Уточнить назначение, пользователей, сценарии и ограничения.
2. Разделить согласованное, предложения и неизвестное.
3. Предложить архитектуру, стек, этапы и проверки. Не выдавать шаблон за принятое решение.
4. После принятия инженером заполнить документы и подготовить первый исполнимый набор задач.
5. Указать реальные пути/команды в `project.json`, завершить первичную настройку.

## Обследование существующего проекта

Полное обследование по шагам ниже выполняется только в режиме «Обследование» и при первичном подключении (`setup_status: needs_review`). Обычная задача его не запускает: читай карточку, индекс и связанные материалы по [правилам чтения](context.md).

1. Сначала действующие инструкции, Git-состояние, структура, конфигурация сборки и тестов.
2. Составить карту подсистем. Исследовать порциями; записывать область обследования и непроверенное.
3. Сопоставить код, документацию и доступные проверки. Записать расхождения, не переписывать намерения под найденный баг.
4. Сохранить полезные документы на существующих путях, объединить дубли осознанно, обновить ссылки.
5. Заполнить карту, индекс, архитектуру и задачи на пробелы. Не объявлять обследование полным, пока остаются неизученные существенные области.

CLI не сливает чужие документы. При конфликте развернуть комплект отдельно и переносить согласованные изменения через diff. Не удалять существующие файлы ради успешной установки.

## Контрольная точка

После логического шага, перед передачей/завершением или при смене ограничений: актуализировать карточку, проверки и следующий шаг. При смене версии ресурсной политики пересмотреть оставшийся план, не переписывая историю выполненного.

Для аудита контрольная точка обязательна даже без изменений кода: соблюдай [порядок сохранения и завершения](verification.md). Итоговый ответ содержит ссылку на сохранённые результаты либо явное сообщение о невозможности записи.
