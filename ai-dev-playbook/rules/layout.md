# Код, тесты, миграции

Общее разделение:

- Корень: `AGENTS.md`, README, CHANGELOG, конфигурация сборки/CI.
- `ai-dev-playbook/`: правила, настройки, шаблоны и инструменты процесса.
- `docs/`: продуктовая и техническая документация, задачи, решения, история.
- Исходники, тесты и миграции: в каталогах приложения согласно его стеку.

## Тесты

Для нового проекта допустимы `tests/unit/`, `tests/integration/`, `tests/e2e/`. Если стек использует тесты рядом с кодом, сохранить это соглашение. Фикстуры располагать рядом с соответствующими тестами; не использовать реальные секреты/данные пользователей.

В `project.json` для каждого компонента перечислять путь к коду, каталоги тестов и путь миграций или `null`. Для монорепозитория — несколько компонентов. Документировать общие команды и требования к среде, не дублировать каждый тест в Markdown.

## Миграции БД

Путь определяется инструментом: например, `db/migrations/`, `prisma/migrations/` или `supabase/migrations/`. Это альтернативы, а не каталоги, которые нужно создавать все сразу. Если БД нет — `null`.

- Применённую миграцию не редактировать: исправление отдельной миграцией.
- Разделять миграции схемы, начальные данные и тестовые фикстуры.
- Перед изменением оценить совместимость кода/схемы и сохранность данных.
- Проверять в изолированной временной БД. Способ восстановления описывать явно; обратная миграция не всегда возможна.
- Общая/продуктивная БД — отдельное разрешение и процедура проекта.

Не переносить существующие исходники, тесты и миграции только ради шаблона. При добавлении компонента сначала определить реальные пути и проверки, затем обновить карту проекта и документацию.
