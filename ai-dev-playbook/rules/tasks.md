# Задачи

Шаблон: [task.md](../templates/task.md). Одна карточка — один самостоятельный проверяемый результат.

## Создание

1. Проверить индекс на дубли и связанные задачи. Архив искать по теме только при необходимости.
2. Назначить уникальный постоянный ID `<ТИП>-<номер>`: префикс — тип из [реестра](#типы-и-префиксы-id), номер — следующий свободный внутри префикса. Одноимённый файл. ID не использовать повторно и не переименовывать.
3. Записать цель, границы, приоритет с причиной, зависимости, документы и приёмку.
4. Для «запиши задачу» достаточно draft с неизвестными деталями. Не придумывать требования.
5. Обновить индекс CLI. Для этапа roadmap добавить ссылку без дублирования статуса.

## Типы и префиксы ID

Префикс показывает тип задачи по её основному результату:

- `TASK` — тип не определён или смешанный.
- `DEV` — код и логика.
- `UI` — интерфейс.
- `AUDIT` — аудит и проверки.
- `DOC` — документация.
- `PB` — развитие этого комплекта.

Новый тип вводится записью в этот реестр, а не молча. Существующие карточки не переименовываются.

## Приоритет

- P0: авария, критическая уязвимость или полная блокировка необходимой работы.
- P1: ближайшая обязательная работа.
- P2: плановая работа.
- P3: отложенное улучшение.

При одинаковом приоритете учитывать зависимости и согласованный порядок. Заблокированная P0 не становится исполнимой. Агент предлагает приоритет; существенное изменение очередности согласует с инженером. Не оценивать срочность только по размеру задачи.

## Статусы

`draft → ready → in_progress → in_review → done`

- `ready`: понятны границы и проверяемая приёмка, необходимые решения приняты, зависимости завершены.
- `in_progress`: есть исполнитель; проверены рабочая ветка, исходное состояние и ресурсы.
- `in_review`: реализация готова, собственные проверки и ограничения записаны.
- `done`: обязательные проверки/аудит приняты, документы обновлены, открытых блокирующих замечаний нет.
- `blocked`: указаны причина и условие продолжения. После снятия — в соответствующее состояние.
- `cancelled`: причина отмены сохранена. Зависимость от cancelled не считается выполненной.

Возврат с проверки — `in_progress`. Автопроверка статического файла не доказывает историю переходов или качество реализации.

## Исполнение и передача

До работы проверить владельца задачи. Не брать занятую задачу без координации. Параллельные изменения вести в отдельных ветках/checkout; общий JSON или Markdown не является блокировкой.

В конце этапа записать: выполненное, решения, команды и результаты проверок, непроверенное, блокеры, следующий шаг, ветку/коммит и несохранённые изменения. Модель указывать фактическую, если известна; не угадывать.

Новые проблемы вне границ записать отдельными draft и связать с исходной задачей. Не расширять реализацию молча.

## Разделение крупной задачи

Крупную задачу — несколько компонентов `project.json` или подсистем, больше одного самостоятельного проверяемого результата, явная просьба инженера — при планировании разделять на связанные подзадачи, а не одну карточку. При сомнении предложить разделение инженеру, не расширять молча.

Вместе с подзадачами блока создаётся карточка аудита типа `AUDIT` с зависимостью от всех подзадач блока. Она становится исполнимой после их завершения и запускается по обычным правилам задач. Аудит блока проверяет результат целиком и не заменяет проверки подзадач; сам по себе он исправлений не разрешает.

## Архив

Закрытую done/cancelled карточку можно перенести в `docs/archive/tasks/` с тем же ID и именем. Обновить входящие ссылки и индекс. Значимые факты до переноса внести в актуальные документы. Зависимости разрешаются и на архивные карточки.

Простой дефект может иметь одну короткую карточку без отдельной спецификации и ADR. Сложную возможность разделять на связанные задачи и добавлять только нужные документы.
