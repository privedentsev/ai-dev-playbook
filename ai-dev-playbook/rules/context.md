# Контекст и документы

## Чтение и навигация

Начало работы: `AGENTS.md` → `card show <ID>` для текущей задачи → главный индекс `docs/index.md` → специализированные документы и код. Политику ресурсов (`resources.json`) читать при запуске, смене исполнителя и на контрольных точках. Не перечитывать неизменённые документы внутри одного этапа без причины.

Комплект организует проектные документы по коллекциям:
- **Обсуждения** (`docs/discussions/`, архив `docs/archive/discussions/`): контекст, согласованные тезисы, открытые вопросы.
- **Спецификации** (`docs/specs/`, архив `docs/archive/specs/`): проверяемые требования и пользовательские сценарии.
- **Дизайны** (`docs/designs/`, архив `docs/archive/designs/`): архитектура и устройство возможностей.
- **ADR** (`docs/adr/`, архив `docs/archive/adr/`): ключевые архитектурные решения.
- **Планы** (`docs/plans/`, архив `docs/archive/plans/`): этапы, зависимости и проверки групп задач.
- **Задачи** (`docs/tasks/`, архив `docs/archive/tasks/`): карточки отдельных проверяемых результатов.
- **Материалы** (`docs/tasks/<ID>-evidence/`, для документов `<slug>-evidence/`): логи, снимки, отчёты проверок.

Главный индекс `docs/index.md` содержит разделы и условия чтения. Индексы отдельных коллекций генерируются CLI (`playbook.py index --documents` или `index --all`). Индекс задач поддерживается командой `playbook.py index`.

## Источники истины

- **Действующие и планируемые требования**:
  - Принятая спецификация и design описывают **текущее фактическое поведение** системы.
  - Планируемые изменения оформляются в разделе предложений и регистрируются в блоке `changes` метаданных документа (`draft → approved → implemented → accepted → cancelled`). Действующее описание не перезаписывается до фактической реализации и независимой приёмки (`promote_change`).
  - При частичном изменении возможностей (например, прекращении поддержки одного формата) обновляется действующая редакция общей спецификации. Документ не архивируется, пока он описывает сохраняющие силу требования.
- **Архитектурные решения (ADR)**:
  - Фиксируют контекст, выбранный вариант и обоснование.
  - Принятый ADR не редактируется под новое решение. При смене подхода создаётся новый ADR со ссылкой `replaces` на прежний. Прежний ADR архивируется только после того, как описанный механизм фактически выведен из эксплуатации.
- **Планы реализации**:
  - Фиксируют порядок, этапы и проверки для блока задач.
  - Статусы выполнения задач в план не копируются: единственный источник статуса задачи — её карточка. Отдельный план архивируется после завершения всех задач и приёмки блока.
- **Карточка задачи**:
  - Единственный источник статуса задачи, исполнителя, модели, дат, записей передачи (`handoff`) и приёмки (`acceptance`).
- **Сопровождающие материалы**:
  - Каждый материал (отчёт runner, лог, снимок) принадлежит ровно одному владельцу (`owner`).
  - Общие доказательства блока закрепляются за общим аудитом или планом блока и не архивируются до завершения всей группы задач.
  - Неизменяемые доказательства (`immutable: true`) не редактируются при переносе; CLI сохраняет карту соответствия исходных и архивных путей (`move-map`).
- **Архив**:
  - Архив документов и карточек хранит историю принятых решений и проверок.
  - Архив не входит в обязательное чтение активной задачи: он читается по явным ссылкам, при аудите, расследовании регрессий и восстановлении контекста.

Код показывает реализацию, автоматические тесты — проверенное поведение в конкретном окружении. При расхождении между кодом и документацией фиксируйте противоречие; реализация не считается эталоном требований автоматически.

## Обновление и инструменты CLI

- Изменение поведения → обновить спецификацию (или зарегистрировать изменение в `changes`).
- Изменение архитектуры или границ модулей → обновить design, `architecture.md` и `code-map.md`.
- Значимое архитектурное решение → зафиксировать новый ADR (`playbook.py document create adr ...`).
- Анализ связей и последствий → `playbook.py document impact <document-id>`.
- Проверка учтённых материалов → `playbook.py document materials <owner-id>`.
- Генерация и синхронизация индексов → `playbook.py index --all`.
- Изменение внешних каталогов, команд или настроек runner → `project.json`.

Текст документов держите кратким и структурированным. Длинные логи, дампы и детальные протоколы сохраняйте в материалах задачи/документа, оставляя в тексте ссылки на доказательства.

## Компактный контекст задачи

Начинай чтение задачи с `python3 ai-dev-playbook/scripts/playbook.py card show <ID>`: требования, актуальная передача/приёмка, открытые замечания и указатель записей. Для продолжения работы или аудита используй `card show <ID> --handoff`: одним read-only вызовом получишь тот же контекст, полные исходные EXEC/CHECK из последней HANDOFF, саму передачу и открытые находки. Выбираются только явные связи; обязательный контекст не должен требовать обхода прежних HANDOFF. `--handoff --json` возвращает context и entries; без флага прежний --json остаётся полным контрактом. --handoff несовместим с --entry/--full. Отсутствие передачи, not_current/historical и работа после неё показаны явно; последняя HANDOFF журнала не обязательно является актуальной CLI-передачей. Подробности: `card show <ID> --entry EXEC-01` (также CHECK/HANDOFF/AUDIT и A-ID); полная история без служебного JSON — `--full`, полный структурированный контракт — `--json`. Вывод показывает команды продолжения; нужные доказательства читать по ссылкам выбранных записей. Неподдерживаемый формат возвращает путь Markdown. Аудитор самостоятельно выбирает проверки по требованиям и рискам; указатель не ограничивает область аудита. Полный файл можно читать при необходимости. Не перечитывай историю и неизменившиеся документы без причины.

Порядок одинаков для Codex, Antigravity и Claude Code; точки входа этих инструментов должны ссылаться на общие правила, а не содержать отдельные копии процесса. CLI читает файлы локально; в контекст агента попадает только выведенный текст.
