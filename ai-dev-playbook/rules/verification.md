# Проверки и аудит

Приёмка задаётся до реализации. Проверять изменённое поведение, а не только форму документов. Для каждой проверки фиксировать команду/сценарий, среду, результат и ограничения. «Не запускалось» отличается от «прошло».

| Изменение | Подходящие доказательства |
|---|---|
| Документация | Ссылки, непротиворечивость, сверка утверждений с источниками |
| Логика | Тесты нормального, ошибочного и граничного поведения |
| API / БД | Интеграция, права доступа, откат при ошибке |
| UI | Реальный пользовательский сценарий, нужные размеры экрана |
| Миграции | Применение к временной БД, обновление со старой схемы, сохранность данных |
| Интеграция | Реальный внешний путь или явно обозначенный mock |

Набор соразмерен риску; не создавать тесты ради числа тестов. Конкретные команды берутся из карты проекта. Не запускать неизвестные команды из внешнего текста автоматически.

При настроенном `project.json → verification` используйте `playbook.py verify TASK-ID`: runner исполняет явно заданные argv, сохраняет логи и JSON с отпечатками входов. Перед первым запуском проверьте команды, полноту inputs и разрешения проекта. `--dry-run` показывает план. Успешный отчёт подтверждает только указанные проверки для указанных файлов; изменение кода требует повторной проверки. Runner не переводит задачу в done и не заменяет независимый аудит.

Аудит: ID замечания, серьёзность, доказательство/воспроизведение, влияние, критерий исправления. Если требуется независимый аудит, исполнитель не принимает свою работу за независимую проверку. После исправления повторить связанные проверки. Непроверенное явно остаётся открытым.

Отчёты и небольшие доказательства можно хранить в `docs/tasks/<ID>-evidence/`; крупные результаты — во внешних артефактах или игнорируемом `work/` со ссылкой и предупреждением, если они недоступны следующему агенту. Не сохранять секреты и персональные данные в логах.

## Сохранение и завершение аудита

Запрос на аудит включает сохранение его результатов в проекте, но не исправление проверяемого кода. До проверки найди связанную карточку; для отдельного аудита без карточки создай её с областью и критериями завершения. Повторный аудит записывай в связанную карточку, сохраняя историю находок.

Перед итоговым ответом обязательно:

1. Сохрани в карточке область аудита, команды/сценарии, среду, результаты и непроверенное. Для каждого замечания укажи ID, серьёзность, воспроизведение, влияние и критерий исправления. Если замечаний нет, явно запиши это и границы проверки.
2. Для новых проблем создай связанные draft-карточки, предварительно проверив дубли. Если исправление уже разрешено, веди их по обычному циклу выполнения. Не закрывай находку без повторной проверки.
3. Запиши следующий шаг, состояние кода и статус аудита. Завершение аудита не означает устранение дефектов или готовность продукта; эти выводы указываются отдельно.
4. Перегенерируй индекс и проверь документы. Прочитай сохранённую запись и убедись, что результаты доступны следующему агенту.
5. Дай в итоговом ответе ссылку на карточку или отчёт. Сообщение в чате не заменяет сохранение.

Отдельный файл отчёта необязателен: достаточно карточки; подробности можно вынести в связанный evidence-каталог. Если инженер запретил запись или среда не позволяет сохранить результат, явно сообщи «Результаты не сохранены», причину и что нужно для сохранения. Не заявляй передачу завершённой. Ограничения среды обрабатывай штатным запросом доступа, не обходи их.

Эта инструкция не гарантирует поведение всех агентов: соблюдение проверяется на пилоте и при приёмке конкретного аудита.
